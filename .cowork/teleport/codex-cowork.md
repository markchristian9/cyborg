## 1. 결론 요약

지정된 작업공간은 게임 저장소가 아니라 Claude 플러그인 캐시이며, Flutter + Flame/SpacetimeDB 게임 코드는 없습니다 (`.cowork/teleport/.prompt.md:29-34`).

이 캐시에 텔레포트 기능을 구현하는 것은 제품 코드에 반영되지 않으며, 구체적인 파일명·좌표·함수를 제시하면 환각이 됩니다.  
실제 게임 저장소를 작업공간으로 다시 지정한 뒤 클라이언트와 SpacetimeDB 모듈을 함께 분석해야 합니다.

## 3. 상세 분석

1. **게임 UI 메뉴 구조**

   현재 자료로는 HUD가 Flame `Component`인지, `GameWidget.overlayBuilderMap` 계열의 Flutter 오버레이인지, 일반 Flutter `Stack`인지 판단할 수 없다. 인벤토리·캐릭터·리더보드 구현도 존재하지 않아 화면을 여는 함수, 메뉴 버튼 컴포넌트, 아이콘 크기·간격·상태관리 패턴을 특정할 수 없다.

   캐시의 `ComicModalBottomSheet` 예제는 `showModalBottomSheet`와 일반적인 `ListView` 구성을 설명하지만 (`thruthesky-skills/flutter-skill/1.0.0/references/comic-design.md:295-363`), 이 게임이 해당 스킬을 채택했다는 근거는 없다. 이를 게임 컨벤션으로 적용해서는 안 된다.

2. **월드 좌표와 다섯 목적지**

   맵 크기, 월드 경계, 타일 크기, 원점, 아이소메트릭 변환, 이동 가능 영역을 정의하는 자료가 없다. 따라서 중앙을 `(width / 2, height / 2)`로 둘 수 있는지, 동·서·남·북이 타일 축인지 화면 방향인지, 좌표가 타일 단위인지 픽셀/실수 단위인지 확인할 수 없다.

   기존 세이프존의 위치와 범위 역시 미확인이다. 임의의 `(0, 0)`이나 맵 크기의 절반을 목적지로 지정해서는 안 된다. 특히 아이소메트릭 화면상의 상·하·좌·우와 논리 타일 좌표의 축 방향은 같다고 가정할 수 없다.

3. **위치 변경과 멀티플레이 동기화**

   SpacetimeDB 테이블, 생성 코드, reducer, 구독 처리, 로컬 플레이어 컴포넌트가 없으므로 현재 위치의 authoritative source를 확인할 수 없다. 기존 이동 reducer의 이름이나 호출 경로도 특정할 수 없다.

   [판단] 실제 게임이 서버 권위형이라면 텔레포트는 로컬 Flame 컴포넌트의 `position`만 바꾸는 방식이 아니라 서버 reducer를 통해 검증·반영하고, 테이블 구독 결과가 로컬 및 다른 플레이어에게 전달되게 해야 한다. 이것은 일반적인 구현 방향이며 현재 코드에서 확인된 사실은 아니다.

   [판단] 순간적인 큰 좌표 변화에는 다음 후처리 지점이 필요할 가능성이 있다.

   - 이동 입력·현재 경로 중단
   - 이동 보간을 장거리 `lerp`하지 않고 즉시 snap
   - 카메라 추적 대상 재고정 또는 즉시 이동
   - 청크·관심 영역 구독 및 렌더 대상 갱신
   - 타깃, 몬스터 어그로, 전투 거리 판정 재평가
   - 텔레포트 이전 좌표를 기준으로 한 미완료 이동 업데이트 무효화

   그러나 실제로 어떤 처리가 필요한지는 각 시스템의 구현을 확인해야 한다.

4. **충돌과 안전한 도착 지점**

   충돌 맵, 이동 가능 타일 판정, 플레이어 스폰 선정 함수가 없으므로 재사용 가능한 로직을 식별할 수 없다.

   [판단] 목적지는 단순 좌표보다 “기준 지점 주변에서 서버가 확정한 이동 가능 좌표”로 처리하는 편이 안전하다. 기존 스폰 지점 검증 또는 nearest-walkable 탐색이 있다면 그것을 재사용하고, 없다면 서버 측 공통 위치 검증 계층을 두는 방안을 검토해야 한다. 실제 함수명과 탐색 규칙은 게임 코드 확인 전 결정할 수 없다.

5. **PK 및 밸런스**

   [판단] 무제한 즉시 텔레포트는 전투 중 도주, 추격 무력화, 위험 지역 이동 비용 회피, 파밍 동선 단축에 이용될 수 있다. 반대로 cooldown, 전투 중 사용 금지, 시전 시간 등을 요구사항 없이 추가하면 기능 범위를 바꾼다.

   따라서 최초 구현 범위에는 임의의 제한을 넣지 말고, 전투 중 허용 여부와 cooldown은 제품·게임 디자인 결정으로 분리해야 한다. 서버 reducer는 향후 정책을 적용할 수 있는 권위 지점으로 설계하는 것이 바람직하다는 정도만 권고할 수 있다.

6. **파일 단위 구현 계획의 현재 경계**

   현재 작업공간에는 수정할 게임 파일이 없다. 실제 저장소가 제공되면 다음 역할을 담당하는 기존 파일을 먼저 찾아 그 파일명을 기준으로 계획을 확정해야 한다.

   - 게임 화면과 `GameWidget` 또는 HUD 오버레이 구성 파일
   - 인벤토리·캐릭터·리더보드 메뉴 버튼 및 화면 호출 파일
   - 월드 크기·타일·아이소메트릭 좌표 변환 파일
   - 세이프존·스폰·충돌 또는 이동 가능 좌표 판정 파일
   - 로컬 플레이어 이동 및 카메라 추적 파일
   - SpacetimeDB 연결·구독·생성 binding 파일
   - 플레이어 테이블과 이동 reducer를 정의한 서버 모듈
   - 청크, 보간, 몬스터 어그로 관련 파일
   - 기존 테스트 구조와 동일한 클라이언트·서버 테스트 파일

## 4. 리스크 · 함정

- 플러그인 캐시를 수정해도 실제 게임에는 기능이 추가되지 않으며, 캐시 갱신 과정에서 변경이 사라질 수 있다. 현재 자료는 플러그인임이 명시돼 있다 (`RevenueCat/RevenueCat/2.0.0/README.md:1-9`).
- 범용 Flutter 스킬의 bottom sheet 디자인을 게임의 기존 디자인 시스템으로 오인할 위험이 있다 (`thruthesky-skills/flutter-skill/1.0.0/references/comic-design.md:295-363`).
- [판단] 클라이언트 위치만 변경하면 서버 및 다른 플레이어 화면과 좌표가 불일치하거나 다음 서버 업데이트에서 원위치로 되돌아갈 수 있다.
- [판단] 중앙·방향 좌표를 하드코딩하면 맵 크기 변경, 화면/타일 축 차이, 장애물 배치로 인해 잘못된 위치에 도착할 수 있다.
- [판단] 일반 이동용 보간을 텔레포트에도 적용하면 플레이어가 월드 전체를 빠르게 가로지르는 것처럼 보이거나 중간 청크·어그로 판정을 연속으로 유발할 수 있다.
- cooldown이나 전투 제한을 독단적으로 포함하면 요청 범위를 벗어난다. 반대로 서버 검증 지점 없이 구현하면 이후 부정 사용 방지가 어려워진다.
- 실제 파일 없이 구체적인 파일명·함수명·좌표를 제시하는 것은 작업공간 근거가 없는 추측이다.

| 5 | 기존 이동 reducer를 확장할지 별도 teleport reducer를 만들지 서버 코드를 보고 결정하며, 최종 좌표는 서버가 검증·갱신하게 한다. | SpacetimeDB 서버·클라이언트 binding | 관련 모듈 미확인 | 클라이언트 단독 변경 시 동기화·치팅 문제 |
| 6 | 서버 위치 갱신을 받은 클라이언트가 보간을 snap하고 카메라·청크·타깃 상태를 갱신하도록 기존 위치 변경 흐름에 텔레포트 분기를 연결한다. | Flame 런타임·멀티플레이 | 관련 자료 미확인 | 장거리 보간, stale chunk, 어그로 오작동 |
| 7 | 전투 중 허용, cooldown, 비용, 시전 시간은 구현 범위와 분리해 명시적인 게임 디자인 결정으로 확정한다. | 밸런스·서버 정책 | 사용자 요구사항에는 제한이 없음 (`.cowork/teleport/.prompt.md:113-130`) | 임의 제한은 범위 초과, 무제한 허용은 PK 밸런스 악용 가능 |

## 6. 불확실 · 미확인

- 실제 Flutter + Flame 게임 저장소의 경로와 접근 가능 여부
- `pubspec.yaml`, 게임 진입점, `GameWidget`, HUD 및 overlay 구성
- 인벤토리·캐릭터·리더보드 메뉴의 실제 파일과 호출 방식
- 맵 크기, 좌표 원점, 타일 크기, 월드 경계 및 아이소메트릭 변환식
- 세이프존의 실제 좌표·범위와 동·서·남·북 목적지의 기획상 의미
- 플레이어 위치 테이블과 이동 reducer, 클라이언트 binding 및 구독 경로
- 충돌·스폰·nearest-walkable 처리의 존재 여부와 서버/클라이언트 책임 경계
- 카메라, 청크 로딩, 이동 보간, 몬스터 스폰·어그로·전투 상태 구현
- 전투 중 텔레포트 허용, cooldown, 비용 및 재사용 대기 정책
- 위 자료가 제공되기 전에는 정확한 수정·신규 생성 파일명과 코드 스타일을 확정할 수 없다.
