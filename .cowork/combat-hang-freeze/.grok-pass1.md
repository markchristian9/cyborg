## 1. 결론 요약

**전투 hang 의 진짜 주원인은 가설 (1) 이 맞다.** 커밋 `15fa510` 기준 `meleeTargets()`/`projectileTargetsForPlayer()` 가 `sync*` 로 `enemies` 를 지연 순회하고, 순회 중 처치 → `onEnemyKilled` → `enemies.remove` 가 `ConcurrentModificationError` 를 낸다. 이 예외는 Flame `update` 안에서 터지므로 프레임이 멈춘 것처럼 보인다.  
**현재 워킹트리(미커밋)는 이미 `List` 스냅샷으로 그 경로를 고친 상태**이므로, “지금 디스크의 최신 파일”만 보면 가설 코드와 다르게 보인다.  
**(2) 플레이어 사망 → `_refreshMonsterStreaming` 은 같은 *즉시* CME 재현 경로는 아니나**, update 콜스택에서 `enemies` 를 구조 변경하는 취약 패턴은 남아 있다.  
**(3) while(true)/레벨업 while/오디오는 이 hang 의 주원인이 아니다.**  
**(4) 회귀 테스트는 sync* 패턴 단위 재현 + 근접 다수 처치·사망 스트리밍 통합 테스트로 잠가야 한다.**

## 3. 상세 분석

### 3.1 범위·권위

- **대상 코드베이스**: `/Users/thruthesky/tmp/games/actionrpg` (Cyborg / Flutter+Flame).

- **권위**: 런타임 동작은 **현재 워킹트리 소스**. 증상 재현·원인 설명은 **마지막 커밋 `15fa510` 의 `sync*` API** 가 핵심. 스냅샷 수정은 **미커밋** (`git blame`: Not Committed Yet).

### 3.2 (1) CME 경로 — 주원인 (커밋 기준 성립)

호출 체인:

1. `ActionRpgGame.update` → `super.update` → `Player.update` → `_updateMelee` → `_resolveMeleeHit`
2. `for (target in meleeTargets())` — **커밋**: `Iterable` 이 `enemies` 에 묶인 lazy iterator
3. 첫 적 처치: `Enemy.applyDamage` → `_die` → `onEnemyKilled` → **`enemies.remove`**
4. for 의 다음 스텝에서 Dart 가 리스트 수정을 감지 → **`ConcurrentModificationError`**
5. 예외가 `update` 스택을 뚫고 나가 해당 프레임(및 이후 루프)이 깨짐 → UI 상 hang/freeze

동일 구조가 **원거리**에도 있음: `Projectile.update` → `projectileTargetsForPlayer()` (커밋: 역시 `sync*`). 탄은 보통 1킬 후 `return` 이라 다수 순회 CME 빈도는 근접보다 낮을 수 있으나, **목록이 2+ 이고 첫 대상 처치 후 다음 대상 검사 전에 리스트가 바뀌는** 경우 동일 클래스 버그다(스냅샷 전).

**현재 워킹트리**는:

```dart
List<Damageable> _damageableTargets() => <Damageable>[
  ...enemies.where(...),
  ..._destructibles.where(...),
];
```

`...` 가 순회 **전에** 복사하므로, 순회 중 `enemies.remove` 해도 for 는 스냅샷을 돈다. 가설 (1) 의 수정 방향과 일치하며, 로컬 CME 실험에서도 `SNAPSHOT OK`.

### 3.3 (2) 플레이어 사망 → 스트리밍

경로:

- `Enemy._resolveMeleeStrike` / 적 탄 / hazard → `Player.applyDamage` → `onPlayerDied`
- `onPlayerDied`: 리스폰(맵 중앙 안전지대) + `_refreshBlockStreaming` + `_refreshMonsterStreaming`
- 스트리밍: 멀어진 상주몹 `enemies.remove`+`removeFromParent`, 근처 시드 `enemies.add`+`world.add`

**왜 “같은 CME”로 단정하기 어렵나**

| 요소 | 사실 |
|---|---|
| Dart 스레드 | 싱글 스레드, 컴포넌트 `update` 순차 |
| 사망 시점 phase | `strike`/탄/지형 — **`_moveToward` 의 `for enemies` 밖** |
| 다음 적 update | 이미 바뀐 `enemies` 로 separation 시작 → 실험상 OK |
| Flame children | add/remove 큐잉 → 트리 즉시 CME 가능성 낮음 |

**남아 있는 위험 (구조)**

- `Enemy._moveToward` 은 여전히 **라이브** `for (game.enemies)`.
- 사망·텔레포트·주기 스트리밍(0.3s) 모두 **임의의 타이밍**에 `enemies` 를 바꾼다.
- 나중에 처치/사망/스트리밍이 “누군가 `enemies` 를 for 중인 콜백” 안으로 끼면 CME 재발.
- 리스폰 순간 대량 add/remove + `world.addAll` 은 **프레임 스파이크**(프리즈 체감)를 만들 수 있으나, 이는 CME 와 별개의 **성능** 이슈 `[판단]`.

### 3.5 (4) 테스트 설계 방향 (작성 가이드만)

   - 회귀: `meleeTargets()` 반환 타입이 `List`(또는 복사본) 이고, 순회 중 `enemies.remove` 해도 예외 없음.

2. **전투 시나리오(Flame/`flutter_test`)**

3. **사망 스트리밍**

## 4. 리스크 · 함정

- **커밋/배포 불일치**: 스냅샷 수정이 **미커밋**이면, 다른 클론·CI·릴리즈는 여전히 `sync*` hang. “고쳤다”고 착각하기 쉬움.
- **`_destructibles` 는 여전히 `sync*`** (`action_rpg_game.dart:634-639`). 스냅샷 헬퍼의 `...` 로 소비되므로 현재 경로 OK. 누군가 `meleeTargets` 를 다시 lazy 로 바꾸면 **블록 파괴 중 CME** 도 재개(실험: BLOCK SYNC* CME).
- **`onEnemyKilled` 안의 `gainXp`→레벨업 연출** 이 처치 콜스택에 붙어 있음 — 스냅샷 후 CME 는 막히지만, 한 스윙 다수 킬 시 비용·부수효과는 큼.
- **`Enemy` separation 라이브 순회** — 미래 기능이 순회 중 `enemies` 를 건드리면 재발.
- **사망 시 즉시 스트리밍** — 안전지대 채우기 UX 와 맞바꾸어 update 중 대형 변이; 장기적으로는 “pending spawn/despawn 큐 + update 끝에서 flush” 가 안전.
- **증상 혼동**: 프레임 스파이크 vs 예외 정지. 재현 시 콘솔/`FlutterError` 에 CME 가 있는지 구분해야 함.
- **캐시 워크스페이스** 에 게임 코드가 없음 — 분석을 플러그인 캐시에 한정하면 근거를 못 찾음.

## 6. 불확실 · 미확인

- **실기기/플레이 로그**에 실제 `ConcurrentModificationError` 스택이 남았는지 — 코드·재현 실험과는 정합하나 런타임 로그는 미확인.
- 워킹트리 스냅샷 수정 **이후에도** hang 이 남는다면, 원인은 CME 외(프레임 스파이크, 다른 예외, 플랫폼 오디오 등)일 수 있음 — **재현 빌드가 커밋인지 워킹트리인지** 가 갈림.
- Flame `update` 중 `world.add` 대량 호출의 **체감 프리즈 임계** — 측정 없음 `[추측: 가능하나 별 이슈]`.
- 멀티플레이 동기화는 아직 없음(`.cowork/cowork-prompt.md`) — 원격 엔티티 목록 동시 수정 hang 은 현 범위 밖.
- `onBlockDestroyed` 가 `_loadedBlocks` 청크 리스트를 순회 중 remove 하는 다른 lazy 경로가 더 있는지는 `_damageableTargets` 외 전수 미확인.
- 캐시 `.cowork/combat-hang-freeze/*` 타 AI 보고는 비어 있거나 미완성으로 교차검증 못 함.
