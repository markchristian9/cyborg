# cowork 시스템 프롬프트 — Cyborg (actionrpg)

> 🛑 이 파일은 `cowork` 이 claude·codex·grok·kimi **네 AI 에게 분석을 시킬 때마다 프롬프트 맨 앞에
> 반드시 주입** 하는 **이 프로젝트의 시스템 프롬프트** 다.
>
> ⚠️ 네 AI 는 읽기 전용이다. 이 문서에 "파일을 고쳐라" 같은 지시를 써도 물리적으로 실행되지 않는다
> (실제 수정은 종합(final-report.md)을 마친 오케스트레이터가 한다).

## Overview

**Cyborg** — Flutter + Flame 으로 만드는 2.5D 아이소메트릭 액션 RPG **MMORPG** 다.
세계관은 "AI 로봇이 점령한 세계를 인간 사이보그가 되찾는다".

핵심 전제:

- **단일 공유 월드.** 매치별 인스턴스도, 분리된 스테이지도 없다. 플레이어는 세션이 아니라 **월드에
  접속한다.** 여러 사용자가 같은 월드에서 동시에 사냥하고, 서로의 존재·이동·전투가 실시간으로 보인다.
  PK 가 허용된다.
- 백엔드는 **SpacetimeDB**(Rust 모듈, maincloud 의 `withcenter-cyborg`). 게임 서버 계층이 따로 없고
  DB 안에서 reducer·view 가 돈다.
- 현재 단계: 계정·캐릭터 선택 관문(`lib/auth/`)이 붙었고, 싱글 플레이 수준의 전투 루프
  (웨이브·레벨업·인벤토리·안전지대)가 돌아간다. **실시간 멀티플레이 동기화는 아직 없다.**
  방금 **레벨 리더보드**(전역 순위표)가 서버·클라이언트 양쪽에 추가되어 maincloud 에 배포됐다.

이번 분석에서 네 AI 에게 시키려는 것: **플레이어 HP 와 몬스터 피해량 체계를 다시 설계하는 것.**
사람이 요구한 목표 규격은 다음과 같다.

- 플레이어 **기본 HP 를 10,000** 으로 크게 키운다(현재 120).
- 플레이어에게 **방어력(defense)** 개념을 두고 **기본값은 0** 이다.
- **몬스터에 레벨을 부여**하고, 방어력 0 인 플레이어가 맞을 때 실제로 들어오는 피해가
  **그 몬스터의 레벨과 같은 수치**가 되게 한다 — 3레벨 몬스터는 3, 10레벨 몬스터는 10.
- HP 10,000 이 모두 소진되면 사망한다(사망 시 안전지대 즉시 리스폰은 이미 구현돼 있다).

⚠️ 전제 사실: 현재 코드에는 **몬스터 레벨이라는 개념 자체가 없고**(종류 4종 `EnemyKind` × 맵 중심
으로부터의 거리 기반 배율), **플레이어 방어력 스탯도 없다**(버프의 `damageTakenMultiplier` 뿐).
그러므로 이 요청은 상수 몇 개를 바꾸는 일이 아니라 **전투 수식의 재설계**다.

네 AI 는 다음을 함께 본다 — ① 이 규격이 성립하려면 어느 파일의 무엇을 어떻게 바꿔야 하는가,
② 그때 무엇이 깨지는가(플레이어 공격력·경험치 곡선·드롭·포션 회복량·HP 바와 데미지 텍스트 표시·
방화벽 지속 피해·기존 난이도 곡선), ③ 100배로 커진 HP 축에 맞춰 **함께 스케일되어야 하는 값이
어디에 흩어져 있는가**, ④ MMORPG 로서(나중에 서버 권위로 옮길 때) 이 설계가 걸림돌이 되는가.

## Persona

**액션 RPG 의 전투 수식과 성장 곡선을 설계해 온 시니어 게임플레이 엔지니어 겸 밸런스 디자이너.**
다음 두 관점을 동시에 갖는다.

1. **수치 설계** — HP·피해·방어·성장 곡선이 서로 어떤 함수로 엮여 있는지, 한 축을 100배로 키우면
   어떤 축이 함께 움직여야 체감(몇 대 맞으면 죽는가 / 몇 대 때리면 잡는가)이 유지되는지를 본다.
   회복량·드롭·경험치처럼 HP 를 기준으로 **암묵적으로** 스케일되어 있던 값을 빠짐없이 찾아낸다.
2. **구현 구조** — 그 수식을 이 코드베이스의 어디에 두어야 단일 진실 공급원이 되는지, 지금처럼
   강함을 정하는 값이 여러 곳(`EnemyStats.table` · `MonsterPopulation` · `WaveDirector` ·
   `LevelSystem`)에 흩어져 있을 때 무엇이 어긋나는지를 본다.

부수적으로 **클라이언트를 신뢰하지 않는 보안 관점**을 겸한다 — 전투가 전적으로 클라이언트에서
계산되는 현재 구조에서, 이 변경이 나중에 서버 권위로 옮길 때 걸림돌이 되는 지점을 짚는다.

## Instructions

1. **모든 주장에 `파일:줄` 근거를 붙인다.** 근거를 못 대는 추정은 `[추측]` 으로 명시한다.
2. **이 프로젝트의 서버 설계 원칙**(`spacetimedb/src/lib.rs` 머리말)을 어기는 권고는 하지 않는다:
   - 클라이언트를 신뢰하지 않는다. 소유자는 `ctx.sender()` 에서 도출하며 `account_id` 를 인자로 받는
     reducer 는 없다.
   - 비밀번호는 별도 표(`AccountSecret`)에 둔다.
   - **모든 테이블이 비공개다.** 클라이언트가 읽는 것은 view 뿐이다.
   - 시각은 `ctx.timestamp`, 난수는 `ctx.random()` 만 쓴다.
3. **용어를 정확히 구분한다.**
   - `level` — **플레이어** 캐릭터의 성장 단계. 상한 30(`LevelSystem.maxLevel`, 서버
     `leaderboard::MAX_LEVEL`). 리더보드 순위의 기준이기도 하므로 의미를 바꾸면 서버까지 영향이 간다.
   - **몬스터 레벨** — 이번에 새로 도입하려는 개념이다. 지금 코드에 **없다.** 기존의 `EnemyKind`
     (scout·sentry·heavy·commander) 나 `hpMultiplier`/`damageMultiplier` 를 몬스터 레벨과 혼동하지 말 것.
   - `xp` — **누적 총량이 아니라 "현재 레벨 안에서 다음 레벨까지 쌓은 진행도"** 다. 서버·클라이언트가
     같은 의미로 쓴다. 이 정의를 오해한 분석은 무효다.
   - **피해(damage)** — 요구 규격의 "3레벨 몬스터는 3의 데미지"는 **방어력 0 기준으로 플레이어 HP 에서
     실제로 깎이는 최종 수치**를 뜻한다. 공격력 원본값이 아니라 방어 적용 후의 결과값이다.
   - **방어력(defense)** — 이번에 새로 도입하려는 플레이어 스탯이며 기본값 0 이다. 기존
     `BuffSpec.damageTakenMultiplier`(포션 버프의 피해 감소 배율)와는 별개의 축이다.
4. **SpacetimeDB 2.7 의 제약을 전제로 판단한다.**
   - view 가 받는 핸들은 읽기 전용이라 `iter()` 가 없다. 여러 행을 훑는 길은 인덱스 범위 조회뿐이다.
   - **view 도 구독해야 행이 온다**(실측). 구독하지 않으면 reducer 는 성공하는데 캐시는 비어 있다.
   - Dart 코드 생성기는 view 반환 타입의 이름을 **테이블 목록에서만** 찾는다. 테이블이 아닌 타입을
     반환하는 view 는 `Type2` 같은 존재하지 않는 클래스를 참조하는 깨진 코드를 만든다.
   - auto_inc id 는 연속을 보장하지 않는다. 정렬 기준으로 삼을 때 이 점을 고려한다.
5. **"서버가 전투를 시뮬레이션하지 않는다"는 현재 한계를 사실로 인정하고 논한다.** 레벨은 클라이언트가
   신고한다. 그것을 없애라는 권고보다, 그 전제 위에서 무엇을 더 막을 수 있는지 / 어디까지가 수용
   가능한 위험인지를 구체적으로 짚는 편이 유용하다.
6. **MMORPG 전제를 잊지 않는다.** "혼자 플레이할 때는 문제없다" 는 판정은 이 프로젝트에서 의미가 없다.
   같은 월드에 수십~수천 명이 동시에 있고 각자 레벨업할 때 무슨 일이 생기는지로 판단한다.
7. 게임 화면(HUD·인벤토리·리더보드)은 전부 **Flame `PositionComponent`** 다(Flutter 위젯이 아니다).
   좌표·히트테스트·클리핑은 캔버스 기준이다. 위젯 전제의 권고는 맞지 않는다. HP 표시가 네 자리에서
   다섯 자리로 늘어나는 문제도 이 전제 위에서 논한다.
9. **기존 밸런스를 "지금이 옳다"고 전제하지 않는다.** 사람이 요구한 규격(HP 1만·피해 = 몬스터 레벨)이
   최우선이며, 그것과 충돌하는 기존 수치는 바뀌어야 할 쪽이다. 다만 그 규격을 그대로 따랐을 때
   플레이 체감이 무너지는 지점(예: 1만 HP 를 3씩 깎으면 3,333대를 맞아야 죽는다)이 있으면 **규격을
   지키면서** 그것을 메우는 방법을 제시한다 — 규격 자체를 임의로 바꾸는 권고는 채택하지 않는다.
8. 주석과 문서는 **한국어**로 쓴다. 코드 식별자는 영문 그대로.

## Tech stack

- **작업공간 경로**: `/Users/thruthesky/tmp/games/actionrpg`

  shared_preferences

- **생성 코드**: `lib/spacetime/generated/` — `dart run spacetimedb_sdk:generate --project-path

## 1. 결론 요약

**Cyborg 를 “서버가 판정하고 클라는 렌더·입력만” 구조로 가려면, 라리엔식 30Hz sim + SNAP 을 복제하는 것이 아니라, 이미 있는 SpacetimeDB reducer/구독 골격을 진실 공급원으로 키우고 클라이언트 로컬 전투 루프를 그 위에 얹는 것이 올바른 경로다.**

## 3. 상세 분석

### 3.1 질문 분해 — “서버 권위”가 이 코드베이스에서 뜻하는 것

| 축 | 지금 권위 | 목표 권위 | 현재 전달 경로 |
|---|---|---|---|
| 계정·세션·캐릭터 | 서버 | 서버 | reducer + view |
| 위치(자기/타인) | 클라 이동 + 서버 속도 검증 / 타인 구독 | 서버 확정 좌표 | `move_to` + `world_player` |
| 몬스터 존재·HP·킬 | **클라 로컬** (서버 표는 배포됐으나 미연동) | 서버 `monster` | `attack_monster` 미사용 |
| PC HP/MP/사망 | 클라 | 서버 `WorldPlayer`(+ 확장) | 로컬 `applyDamage` |
| 성장(XP/level) | **이중**: 로컬 전투→`report_progress` + 서버 `award_kill` | 서버 킬만 | `SpacetimeGameSync` |
| 회복·포션·버프·스킬 | 클라 | 서버 검증 후 상태 반영 | `buff.dart`·`inventory` 로컬 |
| 텔레포트 | 클라 즉시 이동 | 서버 `teleport_to` | 로컬 `teleportPlayerTo` |
| PK | 없음 | 서버 `attack_player` 류 | — |

### 3.2 라리엔 vs Cyborg 아키텍처 매핑

| 라리엔 (Go UDP Zone) | Cyborg (SpacetimeDB) 대응 | 이식 시 주의 |
|---|---|---|
| 30Hz `sim.Tick` | scheduled reducer (저주파) 또는 **이벤트 리듀서만** | 전 월드 30Hz 갱신은 SpacetimeDB 비용·구독 폭주에 비현실적 |
| INPUT dx/dy | `move_to` 또는 향후 `set_move_intent` | 지금 구조는 **좌표 보고+속도 가드**(절충안, `world.rs:132-139, 755-760`) |
| ATTACK 의도 | `attack_monster(id)` | 이미 “의도만 전송” 설계와 동일 |
| SNAP 15Hz 브로드캐스트 | **public 테이블 구독 diff** | SNAP 패킷 대신 row 업데이트; AOI 없으면 전 몬스터 행이 모든 클라에 감 |
| EVENT hit/death | 표 필드 변경 + (선택) 단기 이벤트 표 | 데미지 숫자는 클라 예측 연출 + 서버 HP 확정 |
| 클라 예측·reconcile | 로컬 예측 이동 + 서버 `world_player` 자신 행으로 보정 | 원격은 이미 `RemotePlayerEntity` 보간 (`remote_player.dart:18-20`) |
| Nakama 메타 + Zone 실시간 | SpacetimeDB 단일 모듈 | 메타/실시간 분리 없음 — 모든 판정이 같은 wasm 모듈 |

**핵심 판단:** 사용자는 “서버 권위 이동·이벤트·사망·HP/MP·스킬”을 원하지만, Cyborg 백엔드는 **틱 시뮬레이터가 아니라 트랜잭션 리듀서 엔진**이다. 권위 이전은 가능하고 방향이 맞지만, 구현 형태는 라리엔의 “매 틱 적분”이 아니라 **검증된 의도 → 상태 테이블 갱신 → 구독 반영 → 클라는 렌더/예측 연출** 이어야 한다.

### 3.3 현재 이중 세계 (가설 3의 구조)

```
[클라 Flame 루프]                    [SpacetimeDB]
Player.move / applyDamage            WorldPlayer (hp 있지만 안 깎임)
MonsterPopulation → Enemy            Monster (킬 판정 준비)
로컬 XP → report_progress            award_kill (attack_monster 시에만)
presence.move_to (좌표만)            move_to 속도 클램프
텔레포트 로컬                        teleport_to (미호출)
```

- **공유되는 것:** 다른 플레이어 좌표·이름·level·alive 표시(단, alive/hp 는 서버가 안 바꾸면 항상 true/입장값).
- **공유되지 않는 것:** 몬스터 생사, 내 HP, 킬, 실제 전투 결과. A 가 잡은 몹이 B 화면에 살아 있는 상태가 `GAME-DESIGN.md:704-708` 이 경고한 그대로다.

### 3.4 서버에 이미 있는 “완성도”와 빈 구멍

**있는 것 (재사용 우선순위 높음)**  
입장/퇴장, 좌표 검증 이동, 텔레포트 목적지·쿨다운, 몬스터 배치·HP·레벨, 근접 공격 한 방 판정, 선점 태그, 킬 시 XP·레벨 반영, 공개 표 구독 모델, disconnect 시 월드 퇴장(`lib.rs:207-213`).

**없는 것 / 깨진 것**  
1. 몬스터→플레이어 피해, 지속 피해(방화벽), 사망 리스폰 서버 판정.  
2. MP/energy, defense, 버프, 포션 사용, 스킬 코스트·쿨다운.  
3. `attack_player`(PK).  
4. 클라가 `monster` 구독·`attack_monster`·`teleport_to` 호출.  
5. HP 스케일 정합: 서버 max HP ~100+18×(lv-1) vs 클라 10000.  
6. 피해 수식: 서버 플레이어 공격력 레벨 선형 vs 클라 고정 melee 26 등.  
7. `monster_tick` 스케줄 행 미생성 → 리스폰 자동화 미작동 가능.  
8. AOI: 전 몬스터 public 구독 시 수천~1만 행 전체 푸시 위험(`MONSTER_CAPACITY` 상한 12000, `world.rs:108`).

### 3.5 권위 이전 시 권장 데이터·리듀서 모델 (설계 방향, 미구현)

**원칙 (기존 서버 원칙 준수)**  
- 소유자 = `ctx.sender()` 세션만.  
- 클라가 보내는 것 = **의도**(이동 목표/방향, 공격 대상 id, 스킬 id, 아이템 슬롯) 또는 **제한된 착지 보정 좌표**(텔레포트 slack 패턴 유지).  
- 보내는 것 금지 = 최종 damage, 최종 hp, 획득 xp, 드롭 결과, 난수 시드.

**상태 테이블 (제안 확장)**  

| 필드/표 | 용도 |
|---|---|
| `WorldPlayer` 확장 | `mp`, `max_mp`, `defense`, `energy`(필요 시), `invulnerable_until`, `next_skill_at` |
| `Monster` 유지 | 공유 몹; 필요 시 `ai_target`, `next_action_at`(저주파 AI) |
| `CombatEvent`(선택, 단기) | hit 연출용: attacker, target, amount, tick — 또는 HP diff 만으로 충분하면 생략 |
| 인벤/버프 표(추후) | 포션·버프 지속은 서버 타임스탬프 |

**리듀서 후보**  

| reducer | 판정 내용 | 클라 역할 |
|---|---|---|
| `move_to` (강화) | 속도·맵 경계·(가능하면) 안전/벽 — 지형은 시드 공유로 클라 일치 | 예측 이동, 서버 좌표 reconcile |
| `teleport_to` | 목적지·쿨다운·slack | 성공 시에만 연출 |
| `attack_monster` | 사거리·CD·피해·태그·킬·XP | 스윙 애니; HP는 구독 |
| `attack_player` | 안전지대 면역, 사거리, PK 규칙 | 동일 |
| `use_item` / `use_potion` | 소지 확인, 회복량, 버프 TTL | 마시 애니 |
| `cast_skill` | MP·CD·사거리·효과 | 이펙트 |
| `request_respawn` 또는 사망 시 자동 | 안전지대 좌표, HP full, 무적 윈도우 | 카메라 스냅 |
| scheduled `world_tick` / `monster_ai_tick` | 어그로 몹의 주기 피해 또는 AI 스텝(1~5Hz, 활성 몹만) | 피격 연출 |

**MP/HP 감소·회복**  
- 감소: 오직 서버 피해 경로(`monster_hit_player`, `attack_player`, hazard 틱 등).  
- 회복: `rest_tick`(안전지대+피격 후 warmup) 을 scheduled 또는 입장/이동 시 보정, `use_potion` 이산 이벤트.  
- 클라 `RestRecovery`·`applyDamage` 는 **예측 표시**로만 남기거나, 완전 권위 단계에선 제거.

**스킬**  
- 지금 코드베이스에 “서버 스킬 표”는 없고 근접/원거리/대시가 클라 로컬(`player.dart`).  
- 서버 권위로 가려면 스킬 정의를 Rust 상수로 두고 `cast_skill(skill_id, target_opt)` → 쿨다운·MP·효과를 서버 적용. 클라 전용 콤보 연출은 유지 가능하되 **히트 판정은 서버 한 번**.

### 3.6 클라 아키텍처 전환 (Flame 전제)

- UI/HUD 는 계속 Flame `PositionComponent` — 서버 row 를 읽어 바만 갱신.  
- `Enemy` 소스는 `MonsterPopulation` 시드 → **구독 `Monster` 행 + 활성 반경 스트리밍**(기존 46m/60m 패턴 유지, 출처만 서버).  
- 공격 입력: 로컬 `target.applyDamage` 제거 → `reducers.attackMonster(id)`; 낙관적 플래시 후 서버 HP 로 정합.  
- 자기 HP: 로컬 바 예측 가능하나 **사망·리스폰 트리거는 서버 `alive`/`hp`**.  
- `GameSync.reportLevel` / `report_progress`: 서버 킬 경로가 유일 출처가 되면 **제거 또는 no-op**.  
- 오프라인(`OfflineGameSync`/`OfflineWorldPresence`): 로컬 시뮬 유지 여부 정책 결정 필요 — MMORPG 본선과 분리.

### 3.7 SpacetimeDB 제약에 맞춘 “이동 권위” 현실안

완전 서버 적분 이동(입력만 받고 서버가 매 프레임 적분)은  
- 고주파 reducer 또는 고주파 scheduled tick,  
- 클라 예측·롤백,  
- 지형 walkable 의 서버 측 복제  
가 필요하다. 현재 모듈 주석(`world.rs:132-138`)과 설계 문서가 **의도적으로 속도 상한 절충**을 택했다.

권고 단계:  
1. **유지·강화**: 좌표 보고 + 속도 클램프 + (선택) 텔레포트/대시 전용 예외.  
2. **중기**: `intent`(방향·속도 플래그) + 서버가 마지막 확정 위치에서 적분( scheduled 5~10Hz 또는 move 호출 시 적분).  
3. **라리엔 수준 조작 내성**은 필요해질 때 2번으로 — 1단계에서 30Hz Zone 서버를 새로 세우지 말 것.

### 3.8 수치 SSOT 문제 (서버 권위 이전의 선행 조건)

권위 이전 전에 **한 축의 수치를 서버에 고정**해야 한다. 지금 어긋난 예:

| 축 | 클라 | 서버 |
|---|---|---|
| PC max HP | 10000 (`player.dart:45`) | 100+18×(lv-1) (`world.rs:142-145`) |
| 몹 공격 | level (`monster_codex:416`) | 몹→PC 경로 없음 |
| PC 공격 | melee 26 등 | `14+3×(lv-1)` |
| 몹 배치 | 클라 시드 개체군 | 레벨 1~200 군집 bootstrap |

서버가 판정해도 클라 연출 수치가 다르면 “맞았는데 안 죽음 / 죽었는데 서버는 살아 있음” 이 된다. **SSOT = Rust 상수(+ 필요 시 클라 표시용 미러 테스트)** 가 선행이다.

## 4. 리스크 · 함정

- **이중 진실 유지:** 로컬 킬 XP(`report_progress`)와 `award_kill` 이 동시에 쓰이면 조작·중복 성장. `leaderboard.rs:285-287` 가 이미 경고.
- **문서 표류:** `GAME-DESIGN.md:782-795` 는 presence/렌더 “미구현·안 씀” 이지만 `spacetime_world_presence`·`RemotePlayerEntity`·통합 테스트가 존재 — 계획 문서만 보면 작업을 중복하거나 회귀를 놓침.
- **전 몬스터 public 구독:** AOI 없이 `SELECT * FROM monster` 는 대규모 시 대역·메모리 폭주. 청크/레벨 대역 구독 또는 근접 필터 설계 필수.
- **`monster_tick` 미시드:** 리스폰 reducer 가 호출되지 않으면 서버 몹이 한 번 죽으면 영구 사망.
- **HP 100 vs 10000:** 서버 연동 직후 체감·HUD·사망 조건이 붕괴.
- **지형 미소유:** 서버는 walkable 을 모름(`teleport` slack 주석 `world.rs:149-155`). 벽 통과 이동은 속도 가드만으로는 안 막힘 — 완전 서버 이동 시 지형 데이터 이전 또는 클라 전용 제약 유지 범위 명시 필요.
- **scheduled AI 비용:** 수천 몹 매초 AI 갱신은 wasm 리듀서 타임아웃 위험 → **어그로된 몹만**, 또는 플레이어 근처 슬롯만.
- **재실행 멱등:** SpacetimeDB 직렬화 재실행 — 전역 카운터 금지, 상태 전부 표에 (`world.rs:29-31`).
- **PK·선점 상호작용:** 태그 TTL·안전지대 면역·사망 즉시 리스폰 정책이 클라와 어긋나면 분쟁 발생.
- **오프라인 모드:** 서버 필수화 시 `offline_main` 정책(로컬 시뮬 유지 vs 온라인 전용) 미정.
- **MMORPG 동시접속:** 초당 N 플레이어 × move(5Hz) + attack 는 트랜잭션 폭주 가능 — 이동 배치/간격 유지(`200ms`, presence 주석).

## 6. 불확실 · 미확인

- maincloud 에 배포된 모듈이 로컬 `world.rs` 와 바이트 단위로 동일한지(배포 시각·몬스터 실데이터 건수 240 vs 군집 bootstrap) — 원격 DB 실측 안 함.
- `monster_tick_timer` 행이 운영 DB 에 수동/이전 버전으로 존재하는지 — 코드상 insert 없음만 확인.
- SpacetimeDB 2.7 에서 대규모 public 표 구독 실측 대역·지연 — 문서/추정, 부하 테스트 없음.
- 지형 walkable 을 서버로 옮길지, 이동 치트 잔존을 수용할지 — **제품 결정** 필요.
- 오프라인 플레이를 MMORPG 본선과 계속 병행할지.
- 몬스터 AI 를 서버 틱으로 둘지, “플레이어 공격만 서버 / 몹 공격은 초기엔 서버 간이 사거리 도트”로 단순화할지 — 운영 비용 트레이드오프.
- 방어력·장비 성장 곡선이 서버에 언제 붙는지 — 클라 `defense=0` 고정 주석(`player.dart:77-78`)만 확인.
- 라리엔의 파티·거래·인벤 OCC 등 메타 시스템은 Cyborg 범위 밖 — 참고만 함.

---

**한 줄 요약:** 서버 권위 전환은 “새 게임 서버를 짓는 일”이 아니라, **이미 있는 `world.rs` 를 SSOT 로 키우고 클라 Flame 루프의 판정 코드를 의도 전송·렌더로 깎는 일**이며, SpacetimeDB 에 맞게 **이벤트 권위 + 선택적 저주파 틱** 으로 가야 한다.
