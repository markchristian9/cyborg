## 0. 탐색 로그 (ToT)

- **세운 가설**
  - **(1) 상수 패치설** — `Player` HP를 10000으로 올리고 `EnemyStats.damage`만 손보면 끝난다.
  - **(2) 몬스터 레벨 부재설** — cowork 프롬프트대로 레벨 개념이 없어 `EnemyKind`×거리 배율만 있고, 레벨을 새로 도입해야 한다.
  - **(3) 전투 수식 재설계 패키지설** — 레벨은 이미 있으나 피해 곡선이 레벨과 불일치하고, HP 100배 시 **무적 프레임·회복·성장·hazard**가 함께 안 움직이면 규격은 지켜도 플레이가 붕괴한다.
  - **(4) 플레이어 공격력도 100배 필수설** — 주는 피해까지 같이 키워야 한다.

- **검증**
  - 가설 1 → `player.dart:28-29` HP 120, `monster_codex.dart:341-342` `baseDamage = 6 + step*1.55`, `player.dart:361` 피격 무적 0.55초 → **부분만 지지, 전체 반증**(무적·포션·성장 미반영 시 TTK 붕괴).
  - 가설 2 → `enemy.dart:119-120` `level => species.level`, `monster_codex.dart:170-185, 227-257` 1~200종 도감, `monster_population.dart:178-196` `regionLevel` 배치 → **반증**. cowork-prompt·`GAME-DESIGN.md`의 “레벨 없음 / EnemyStats.table”은 **문서 구식**.
  - 가설 3 → 위 수치·경로 전부 확인 → **채택**.
  - 가설 4 → 요청 범위는 **받는 피해·HP·방어**. 플레이어→몬스터 축(`meleeDamage` 26 등)은 별 곡선. 필수 동반은 아니나 “난이도 체감” 부수 이슈로 남김 → **필수설은 기각, 영향 분석은 유지**.

## 1. 결론 요약

요청 규격(기본 HP 10000 · 방어 0 · 방어 0일 때 최종 피해 = 몬스터 레벨 · HP 0 사망)은 **가능하고, 몬스터 레벨 SSOT는 이미 `MonsterCodex`에 있다.**  
막혀 있는 것은 “레벨 부재”가 아니라 **`stats.damage` 곡선·`damageMultiplier`·피격 무적 0.55초·HP 스케일에 묶인 회복/성장**이다.  
HP만 키우고 피해만 `level`로 바꾸면, 저레벨 존에서는 i-frame 때문에 **사실상 불사**(Lv3 기준 최소 ~30분)가 된다. 규격을 유지한 채 살리려면 **무적·회복·`LevelGains.maxHp`·hazard를 같은 패키지로** 손봐야 한다.

## 3. 상세 분석

### 3.1 범위와 경계

| 축 | 권위 위치 | 이번 요청 |
|---|---|---|
| 플레이어 HP·피격 수식 | 클라이언트 `Player` | **핵심 변경** |
| 몬스터 레벨·기본 스탯 | 클라이언트 `MonsterCodex` | 레벨은 유지, **damage 정의 변경** |
| 난이도 배치 | `MonsterPopulation` / `WaveDirector` | multiplier 정리 필요 |
| 성장·회복 | `LevelSystem` / `PickupSpec` | HP 축 동반 스케일 |
| 서버 전투 | 없음 (진행도만) | 서버 배포 불필요; 이후 이전 시 수식 이식점만 확보 |
| 플레이어 `level` / 리더보드 | 서버 `report_progress` | **의미 유지** (몬스터 레벨과 혼동 금지) |

### 3.2 현재 피격 파이프라인

```
Enemy._resolveMeleeStrike / Projectile(owner=enemy)
  → amount = stats.damage * _damageScale
  → Player.applyDamage(amount)
       → (무적·대시·안전지대면 0)
       → taken = amount * damageTakenMultiplier
       → _hp -= taken; i-frame 0.55s
```

요구 규격의 “3레벨 몬스터 → 3”은 **이 파이프라인 끝의 `taken`(방어·버프 전/후 정의 필요)** 이다.  
권장 정의(규격 정합):

- `rawAttack = species.level` (double)
- `afterDefense = max(1, rawAttack - defense)`  (또는 사람이 고른 다른 감쇠; **defense=0이면 raw=level**)
- `taken = afterDefense * damageTakenMultiplier`  (fortify는 별축 유지)

`stats.damage`를 레벨로 바꾸거나, 적 공격 경로에서 `level.toDouble()`을 쓰거나 — **한곳 SSOT**가 중요. 지금은 Codex·시드 배율·웨이브 배율에 흩어짐.

### 3.3 현재 vs 규격 수치 체감

| 상황 | 현재 대략 피해 | 120 HP 생존 타수 | 규격 피해 | 10000 HP 생존 타수 |
|---|---|---|---|---|
| Lv3 drone | ~7.7 | ~15.5 | **3** | **3333** |
| Lv10 walker | ~22 | ~5.5 | **10** | **1000** |
| Lv100 | ~150 | 1타 전후 | **100** | **100** |

피격마다 0.55초 전면 무적이면, 규격 적용 시 **최소 사망 시간 ≈ (10000/level)×0.55초**  
→ Lv3: ~1833초(~30분), Lv10: ~550초. 다수 몹도 **한 번 맞으면 전원 면역**이라 밀도로 못 메운다.

### 3.4 반드시 같이 볼 스케일 항목

| 항목 | 현재 | HP 1만 시 | 방향 |
|---|---|---|---|
| 포션 heal | 45 / 110 | 0.45% / 1.1% | maxHp 비율 또는 ×~80 |
| 레벨업 maxHp | +18/+34 | 노이즈 수준 | 예: +400~+800대 또는 % |
| hazard | 5/0.5s | 무시 가능 | HP 축에 비례 (예: maxHp의 0.1%/틱 등) — **사람 값 확정 필요** |
| fortify 0.65× | 상대 배율 | 유지 가능 | UI 라벨 `DEF %`와 스탯 defense 혼동 주의 |
| `damageMultiplier` 편차 | ±5~15% | 규격 엄수 시 | 1.0 고정 또는 공격 원본이 아닌 다른 축으로 |
| 플레이어 공격→몹 HP | 26 vs Codex HP | 요청 밖 | 난이도 “잡는 속도”는 유지 가능; “맞는 속도”만 붕괴 |
| HUD/캐릭터 시트 | 3자리 전제 | `10000 / 10618` | 바 폭·폰트; DEF 행 추가 |

### 3.5 구현 구조 권고 (방향만)

1. **`Player`**: `baseMaxHp=10000`, `defense=0`, `applyDamage`에 방어 적용 후 버프 배율.
2. **`MonsterCodex._statsFor`**: `damage`를 **level 기준**으로 재정의. build 배율(0.85~1.35)을 유지하면 규격 위반 → **제거 또는 다른 축(경직·사거리)에만** 두기.
3. **시드/웨이브 `damageMultiplier`**: 규격 엄수면 제거·1.0 고정. HP 편차 배율은 유지 가능.
4. **피격 무적**: 규격 유지 시 **필수 동반 수정**. 후보 — (a) 시간 대폭 단축(0.05~0.15s), (b) 동일 소스만 쿨, (c) 무적 중에도 데미지 텍스트/누적 허용. 대시 무적·리스폰 2초는 별 정책.
5. **표시**: `hud.dart` / `character_screen.dart` HP 자릿수; COMBAT에 DEF; `inventory_ui`의 fortify `DEF +%` 문구를 **“피해 감소”** 등으로 분리 검토.
6. **문서/테스트**: `GAME-DESIGN.md` HP·적 표; `safe_zone_test`의 `EnemyStats.table` → Codex/`ofBuild` 기준으로 정리.
7. **서버**: 지금 단계 배포 불필요. 이후 서버 권위 시 같은 수식(`raw=monster_level`, `defense`)을 reducer로 옮길 자리만 클라이언트에 순수 함수로 모아 두면 이득. 클라이언트를 신뢰하지 않는 원칙은 유지.

### 3.6 MMORPG 관점

전투가 클라이언트 계산인 한, HP·방어 조작 치트 위험은 **기존과 동형**. 이번 변경이 서버 이전을 더 어렵게 하진 않음.  
공유 월드에서 플레이어마다 피격 무적·HP 풀이 커지면 **PK·다중 교전 위협이 급감** → “존재는 보이지만 전투 긴장 없음”이 됨. 무적 재설계 없이 라이브 밀도를 올려도 해결 안 됨.

## 4. 리스크 · 함정

- **피격 i-frame 0.55초**가 규격×HP1만과 결합하면 저·중레벨 구간 난이도 소멸 (최우선 함정).
- **`damageMultiplier`·build damage 배율**을 남기면 “레벨=피해” 규격이 수치 검증에서 깨짐.
- **포션/성장 미스케일** → 인벤 회복·레벨업 보상이 장식화.
- **fortify vs defense** 이중 방어축: 순서·UI 용어 혼동 시 밸런스·기획 소통 실패.
- **문서/테스트 구식**(`EnemyStats.table`, 웨이브 배율 0.16 vs 0.01) — 구현자가 잘못된 SSOT를 건드릴 위험.
- **사운드 `taken/40`**: 소피해에선 항상 최소 볼륨 — 기능 문제는 작음.
- **몬스터 HP·플레이어 공격**을 안 건드리면 “때리면 잘 죽고 맞아도 안 죽음” 비대칭 — 의도적일 수 있으나 액션 긴장 저하.
- 서버에 HP를 안 두므로 **치트 완화는 이번 범위 밖**; “설계 자리만” 확보 수준이 현실적.

## 6. 불확실 · 미확인

- 방어 공식의 구체형(`max(1, atk-def)` vs 비율 감쇠 등) — 규격은 **def=0 → 피해=level**만 고정; 성장 방어 곡선은 **사람 결정**.
- fortify와 defense 동시 적용 시 **최소 피해 1 보장 여부**.
- hazard·포션의 목표 체감(최대 HP 대비 몇 %가 “한 모금”) — 밸런스 수치 미정.
- 플레이어 공격력·몬스터 HP를 손볼지 — 요청 밖; 비대칭 난이도를 의도할지 미정.
