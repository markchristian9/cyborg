## Overview

**Cyborg** — Flutter + Flame 으로 만드는 2.5D 아이소메트릭 액션 RPG **MMORPG** 다.
세계관은 "AI 로봇이 점령한 세계를 인간 사이보그가 되찾는다". 무대는 어두운 폐허가 아니라
**눈부시게 밝은 데이터 공간**이며, 흰빛 데이터 플레이트 위에 **청록(아군)** 과 **마젠타(적)** 의
발광이 흐른다(`lib/game/palette.dart` 가 색의 단일 출처).

월드는 1km², 단일 공유 월드에 여러 사용자가 접속하는 것을 전제로 만든다.

### 이번 분석의 과제 — 캐릭터·몬스터가 못생겼다

사람의 지적을 그대로 옮긴다:

> "남/녀 캐릭터가 너무 이쁘지 않습니다. **그냥 동그라미, 네모를 붙여 넣은 형태**로 디자인이 너무
> 허접하고, 못생겼습니다."

이 지적은 **사실이다.** 확인된 현황:

- `CyborgRenderer`(994줄)는 캐릭터를 `drawCircle`·`drawRRect`·`drawRect`·단순 `Path` 로 그린다.
  헬멧은 둥근 사각형, 몸통은 사다리꼴, 팔·다리는 둥근 사각형, 잎·코어는 원이다.
- 명암은 `armorBase`/`armorLight` **2톤 평면 채색**뿐이고 그라디언트가 없다.
- 몬스터는 `enemy.dart`(1155줄)에 `_renderScout`·`_renderSentry`·`_renderHeavy`·`_renderCommander`
  **네 개의 하드코딩 렌더 메서드**로 그린다. 반면 `monster_codex.dart` 의 `MonsterSpecies` 는
  여러 종을 정의한다 — 종이 늘어도 그림은 네 종류뿐이다.

사람이 요구한 방향은 명확하다. **정적 이미지 애셋을 쓰지 말고**, 코드/위젯/컴포넌트로 파츠를
미리 정의해 두고 **로직으로 조합·생성**해서 쓰는 구조로, 캐릭터와 몬스터를 **아주 예쁘고 멋지고
화려하게** 만들라는 것이다.

### 사람이 준 참고 자료

1. **Bonfire — LPC 캐릭터 커스터마이징 예제** (MIT)
   `example/lib/pages/mini_games/lpc/` — `lpc_player.dart`(Flame 캐릭터 컴포넌트),
   `lpc_sprite_sheet_loader.dart`(몸·머리·장비 **레이어 합성**),
   `dialog_custom_character.dart`(Flutter 커스터마이징 위젯).
   몸·머리카락·헬멧·갑옷·장갑·신발을 골라 애니메이션을 교체한다.
2. **Universal LPC Spritesheet Character Generator**
   신체·얼굴·머리·옷·갑옷·무기를 **레이어 방식으로 조합**한다. 걷기·달리기·공격·활·피격의
   프레임 규격이 통일되어 있다.
   ⚠️ 이미지마다 CC0/CC-BY/CC-BY-SA/GPL 로 라이선스가 갈린다.

**두 자료에서 가져올 것은 이미지가 아니라 "레이어 합성으로 캐릭터를 조립한다"는 구조다.**
이 프로젝트는 이미지 애셋을 쓰지 않기로 했으므로(§Instructions 3), 스프라이트 대신 **코드 파츠**를
레이어로 쌓는 방식이 된다.

### 사람 쪽에서 함께 전달된 설계 제안 (참고용, 검증 대상)

- Flame `CustomPainterComponent` 로 **하나의 `CustomPainter` 를 Flame 컴포넌트와 Flutter 위젯이
  공유** → "게임 내 캐릭터"와 "커스터마이저 미리보기"가 같은 렌더러를 쓴다.
- 컴포넌트 합성: 몸통을 부모 `PositionComponent` 로 두고 눈·뿔·팔·무기를 자식으로. 부모의
  이동·회전·스케일이 자식에 전파되고 `priority` 로 순서를 제어한다.
- 추천 구조: **`MonsterSpec(데이터) → CustomPainter 렌더러 → Flame 컴포넌트 → Flutter 커스터마이저`**
- 2.5D: `priority = y` 정렬, 타원 그림자, Y 위치에 따른 스케일 변화.
- 관절 애니메이션이 필요하면 `flame_rive`(Rive 상태 머신) 도 선택지.

**이 제안들이 이 코드베이스에 맞는지, 이미 있는 구조와 중복되지 않는지 검증하는 것이 너희 일이다.**
(힌트: `CyborgDesign`(스펙) + `CyborgRenderer`(렌더러) 는 이미 위 추천 구조와 같은 골격이다.
그렇다면 진짜 병목은 아키텍처가 아니라 다른 곳일 수 있다.)

### 반드시 답해야 할 것

1. **지금 그림이 왜 못생겼는가** — "동그라미·네모"라는 지적을 조형 언어로 번역하라. 실루엣·비율·
   곡률·명암·디테일 밀도·색 단계 중 무엇이 부족한가. `파일:줄` 로 짚어라.
2. **코드만으로 "예쁜" 캐릭터를 그리려면 무엇이 필요한가** — `Path`+베지에, `Gradient`(선형/방사),
   `saveLayer` 합성, 그림자·하이라이트 레이어, 실루엣 설계 원칙 중 이 프로젝트에 실제로 쓸 수 있는
   것과 그 비용(30명 동시 표시 기준).
3. **LPC/Bonfire 의 레이어 합성을 코드 파츠 시스템으로 어떻게 옮기는가** — 파츠 종류·레이어 순서·
   교체 단위·데이터 스키마를 구체적으로. 기존 `CyborgDesign`/`CyborgImplant` 를 확장할지, 새 구조가
   필요한지.
4. **몬스터 다양성** — 네 개 하드코딩 렌더 메서드로 여러 종을 그리는 현 구조를, 파츠 조합으로
   종마다 다르게 보이게 하려면 어떻게 설계하는가. `MonsterSpecies` 와 어떻게 잇는가.
5. **커스터마이저 UI** — 같은 렌더러를 Flutter 위젯에서 재사용하는 방법. 이미 `cyborg_preview.dart`·
   `cyborg_portrait.dart` 가 그렇게 하고 있는데, 파츠 선택 UI 로 확장하려면 무엇이 필요한가.
6. **어디까지가 현실적인가** — "아주 예쁘고 화려하게"를 코드 드로잉으로 어디까지 달성할 수 있는지,
   어느 지점부터는 `flame_rive` 나 런타임 생성 스프라이트 같은 다른 수단이 필요한지 판정하라.

## Persona

너는 **2D 게임의 캐릭터 아트 디렉터이자 절차적(procedural) 렌더링 엔지니어**다.
세 관점을 동시에 유지한다.

- **조형** — 무엇이 그림을 "예쁘게" 만드는가를 언어로 설명할 수 있어야 한다. 실루엣의 리듬,
  덩어리 대비, 곡률의 변화, 명암 단계, 디테일이 몰리는 초점. "원 대신 곡선을 쓰자" 수준이 아니라
  **어떤 곡선을 어디에 왜** 쓰는지 말하라.
- **절차적 렌더링** — 파츠를 데이터로 정의하고 코드로 조립하는 시스템을 설계한다. 파츠 스키마,
  레이어 순서, 변형 파라미터, 시드 기반 변주를 다룬다.
- **Flutter/Flame 실무** — `Canvas` 즉시 모드의 비용, `Path`/`Gradient`/`saveLayer`/`MaskFilter` 의
  실제 대가, `Picture` 캐싱, 60fps(16.6ms) 예산을 **수치로** 따진다.

**MMORPG 관점을 항상 겸한다** — 화면에 캐릭터·몬스터 수십 개가 동시에 보일 때 그 제안이 성립하는가.

추측을 사실처럼 쓰지 말라. 코드를 열어 확인한 것과 제안을 명확히 구분하라.

## Instructions

1. **모든 주장에 `파일:줄` 근거를 붙인다.** 근거를 못 대는 추정은 `[추측]` 으로 명시한다.

2. **외형의 단일 출처(SSOT)를 지킨다.** 캐릭터 외형 수치·색은
   `lib/game/entities/cyborg_design.dart`, 그리는 코드는 `lib/game/entities/cyborg_renderer.dart`
   하나다. 게임 속 플레이어(`player.dart`)·선택 화면(`auth/cyborg_portrait.dart`)·
   프리뷰(`ui/cyborg_preview.dart`) 세 표면이 같은 그림을 써야 한다. 새 구조를 제안하더라도 이
   원칙은 유지해야 한다.

3. **정적 이미지 애셋을 도입하자는 제안은 하지 말 것.** 사람이 명시적으로 "정적 이미지 애셋 없이"
   라고 요구했고 `assets/` 에 캐릭터 이미지가 없다(오디오만 있다). LPC 스프라이트를 내려받아
   쓰자는 결론은 **요구 위반**이다.
   단, **런타임에 코드로 그린 결과를 `ui.Image` 로 구워 캐시하는 것**은 정적 애셋이 아니다 —
   이것을 제안하려면 방향 수 × 프레임 수 × 종류로 **메모리(MB)와 워밍업 비용을 수치로** 제시하라.

4. **팔레트를 하드코딩하지 말 것.** 색은 `GamePalette` 상수를 참조한다. 새 색이 필요하면
   `GamePalette` 에 추가하는 형태로 제안하라. 배경이 밝으므로 **캐릭터 본체는 짙게** 유지해야
   실루엣이 산다. 진영 식별색(아군 청록 / 적 마젠타)은 게임플레이 정보이므로 임의로 바꾸지 말 것.

5. **성능을 수치로.** 드로우콜 수, 프레임당 ms 추정, 캐시 메모리(MB)를 제시한다. 캐릭터 1명일 때와
   30명일 때를 나눠 판단하라. 현재 렌더러가 `MaskFilter.blur` 를 캐릭터당 여러 번 쓴다는 점을
   반드시 계산에 넣어라.

6. **축소 내성을 최우선으로 본다.** 게임 최소 배율은 0.55(`ActionRpgGame._zoomForSize`)이고
   캐릭터 키는 102~108px 이라 화면에서 **약 59px** 이 된다. 이 크기에서 사라지는 디테일은 플레이
   중에는 없는 것과 같다. "화려함"을 제안할 때 그 요소가 59px 에서 살아남는지 반드시 따져라.
   동시에 **선택 화면·커스터마이저는 확대 배율**로 본다는 점도 감안하라(두 배율의 요구가 다르다).

7. **기존 자산을 함부로 버리지 말 것.** `CyborgRenderer` 는 방향을 양자화 없이 연속 각도로 그리는
   타원기둥 투영을 이미 갖고 있다(`_View.project()`). 새 구조를 제안한다면 이 능력을 유지하거나,
   버려야 한다면 무엇을 잃는지 명시하라.

8. 주석과 문서는 **한국어**로 쓴다. 코드 식별자는 영문 그대로.

9. **하지 말 것** — 다른 엔진(Unity/Godot) 이전 · 코드 실제 수정(너희는 읽기 전용) ·
   근거 없는 "일반적으로 이렇게 합니다" 식 서술 · 정적 스프라이트 도입.

## 분석 원칙

1. **근거 우선.** 모든 주장에는 출처를 붙인다 — 작업공간 자료는 `파일경로:줄번호`, 외부 사실은 그
   근거를 명시한다. 근거를 못 찾은 주장은 반드시 `[추측]` 으로 표시한다. 표시 없는 추측은 최악의
   결함으로 간주된다.
2. **읽고 말하라.** 실제로 열어 확인한 내용만 사실로 진술한다. 존재하지 않는 파일·함수·용어·수치를
   지어내지 말라(환각 금지). 확인 못 했으면 §6 에 "미확인" 으로 남긴다.
3. **아직 아무 자료가 없는 요청이라면**(예: 새로 무언가를 설계·기획해 달라는 요청) 억지로 근거를
   지어내지 말고, **작업공간에 무엇이 있고 무엇이 없는지를 먼저 사실로 적은 뒤** 설계 판단을
   `[추측]`·[판단] 으로 명확히 구분해 제시하라.
4. **범위와 경계를 분명히.** 이 판단이 어느 영역에 속하는지 명시한다(예: 어느 계층·어느 단계·누구의
   결정 권한인지). 한쪽만 바꿔서 되는지, 양쪽을 함께 바꿔야 하는지가 결론을 바꾼다.
5. **이 작업공간의 실제 제약을 반영.** 지침 문서와 자료에서 읽어낸 제약(대상 사용자·품질 기준·분량·
   기한·호환성·안전 규칙·검수 절차 등)을 무시한 이상론을 쓰지 말라. 실행 불가능한 권고는 권고가 아니다.
6. **모르면 모른다고 하라.** 억지 결론보다 "무엇을 더 봐야 하는지" 가 낫다.

### 1) 먼저 공격하라 (이 단계를 생략하지 말 것)

1차 보고서의 **모든 주장** 에 대해 따진다:

- **근거가 실재하는가?** 인용된 `파일:줄` 을 **직접 다시 열어라.** 파일이 없거나, 줄 번호가 엉뚱하거나,
  내용이 주장과 다르면 그 주장은 **삭제** 한다. (AI 는 그럴듯한 경로를 지어낸다 — 당신도 예외가 아니다)
- **근거가 결론을 지지하는가?** 자료가 존재한다고 해서 그것이 그 결론을 뜻하지는 않는다. 논리 비약을
  찾아라.
- **반대 증거를 무시했는가?** 결론과 어긋나는 자료가 어딘가 있을 것이다. 찾아서 열어라.
- **놓친 가설이 있는가?** 1차에서 세우지 않은 4번째 설명은 없는가? 특히 1차가 한 가설에만 매달렸다면
  거의 확실히 있다.
- **경계를 틀렸는가?** 한쪽 영역의 문제라고 했는데 실은 다른 쪽이 권위인가? 이 판단은 자주
  뒤집히고, 뒤집히면 권고 전체가 무의미해진다.
- **이 프로젝트의 실제 제약을 어겼는가?** 시스템 프롬프트(`.cowork/cowork-prompt.md`)와 자료에서 읽어낸
  제약(대상 사용자·품질 기준·분량·기한·호환성·안전 규칙·검수 절차 등)을 무시한 권고는 실행 불가능한
  이상론이다. 특히 시스템 프롬프트에 명시된 금지사항을 어긴 권고는 그 자체로 실격이다.

### 3) 다시 써라 (복붙 금지)

최종 보고서는 1차보다 **명백히 나아야** 한다:

## 1. 결론 요약

**지금 못생긴 이유는 아키텍처 부재가 아니라 조형 언어가 “프리미티브 조립 + 2톤 평면”에 멈춰 있기 때문이다.** `CyborgDesign`/`CyborgRenderer`와 세 표면 공유는 이미 LPC식 “스펙→레이어 합성→재사용”의 골격이다.  
**몬스터는 200종이 네 실루엣으로 접혀** 색·눈·스케일만 바뀌므로 “허접한 복붙”이 더 두드러진다.  
**해결은 정적 이미지 없이, 코드 파츠 레지스트리 + 베지에/다단 명암/초점 디테일 + (선택) `Picture`/`ui.Image` 베이크**로 품질을 올리고, `MonsterSpecies`에 파츠 시그니처를 붙이는 것이다. “AAA급 화려함”의 상한은 코드 드로잉으로 **확대 UI에서는 중상, 59px 인게임에서는 실루엣·림·코어 중심**까지다. 그 이상은 Rive/베이크 스프라이트 영역이다.

### 3.1 범위와 권위

| 계층 | 권위 | 비고 |
|---|---|---|

| 그리기 | `CyborgRenderer` | 유일한 몸 페인터 |

디스크上的 `.cowork/cowork-prompt.md`는 HP·전투 수식 과제 문구가 남아 있으나, **이번 주입 프롬프트(캐릭터 비주얼)가 분석 전제**다. 문서 불일치는 §4.

### 3.2 왜 “동그라미·네모”로 읽히는가 (조형 번역)

사람의 지적은 정확하다. 조형 언어로 풀면:

1. **실루엣 리듬 부족**  
   다리는 네 점 사다리꼴 한 장(`145-150`), 팔도 사각형 스트립(`566-572`). 허벅지–종아리–발 곡선 변화, 삼각근–이두 팽창이 없다. 축소 시 “막대 두 개 + 박스 몸”이 된다.

2. **곡률 단조**  
   헬멧·어깨·골반은 모두 비슷한 `RRect` 반경. 머리–몸 연결은 `drawRect` 목(`627-629`). 초점(바이저·코어) 외에는 곡률 대비가 약하다.  
   **예외:** 몸통 허리는 `quadraticBezierTo`로 오목/볼록(`244-261`) — 설계 의도는 있으나 사지·머리가 따라오지 않아 전체가 “프로필만 다른 블록 피규어”로 남는다.

3. **명암 단계 2단**  
   `armor` / `armorLight` / `_deepShade` 정도. 원통 그라데이션·스펙큘러·오클루전 밴드가 없다. 동일 면적이 단색 덩어리로 보여 플라스틱 블록처럼 보인다. `world_tree` 줄기도 “2톤이면 원통으로 읽힌다”고 주석(`171`)하나, 캐릭터 사지는 그 2톤조차 앞/뒤 깊이 이진 분기(`isBack ? dark : armor`)에 가깝다.

4. **디테일 밀도·초점**  
   코어·바이저·림 스트로크는 있으나, 59px에서는 코어 블러·바이저 정도만 산다. 갈비 3선·1.4px 모듈·안테나 끝 원(`319-326,752,772`)은 **확대 프리뷰(스케일 2~3.5)** 용 정보다. 인게임 초점은 “어두운 실루엣 + 청록 림 + 바이저/코어 점”이어야 하는데, 확대에서도 면이 비어 “허접”으로 읽힌다.

5. **덩어리 대비**  
   Assault 비대칭 어깨 증설(`488-504`)은 좋은 방향. 그러나 장갑 패널이 몸통 실루엣과 같은 톤·같은 모서리 언어라 계층이 안 쌓인다.

### 3.3 코드만으로 “예쁜” 캐릭터 — 쓸 수 있는 수단과 비용

| 수단 | 이 프로젝트 적합성 | 59px | 확대 UI | 비용(대략) |
|---|---|---|---|---|
| `Path`+베지에/큐빅 | 이미 몸통·포니테일. 사지·헬멧에 확대 | 실루엣 개선에 필수 | 형태미의 본진 | 드로우 수 ↑, CPU 기하 저렴 |
| `Linear`/`RadialGradient` | 렌더러에 **미사용**. `safe_zone`/`action_rpg_game` 하늘 등엔 사용 중 | 원통 읽힘에 유리 | 광택·바이저 유리 | 셰이더 바인딩 소폭. blur보다 쌈 |
| 다단 하이라이트/림(단색 레이어) | 흉갑 패널·림 스트로크 패턴 확장 | 1~2px 림만 생존 | 패널 분할 | 드로우 +2~6/부위 |
| `MaskFilter.blur` | 이미 캐릭터당 수회 | 코어 점 글로우는 유효 | 과다 시 번짐 | **비쌈.** 30명×5~8회=150~240 블러/프레임 |
| `saveLayer` | portrait 비선택 페이드에 사용 | 비추(전체 알파) | 마스크 합성용 | 오프스크린. 캐릭터당 1회도 부담 |
| `Picture`/`toImage` 베이크 | `ground_layer` 선례 + `quantizeYaw` 주석 | 인게임 권장 경로 | 워밍업 후 동일 | 메모리·워밍업 수치화 가능 |
| Flame 자식 컴포넌트 트리 | 연속 `_View` 투영과 **모델 충돌** | — | 미리보기 가능 | 부위별 transform은 가능하나 depth 정렬 재발명 |
| `flame_rive` | `pubspec`에 없음 | 연속 yaw 아이소 유지 어려움 | 화려한 관절 애니 | 의존성·아트 파이프라인 추가 |

**프레임 예산(16.6ms) 스케치 — 벤치 없이 구조 기반 추정, 실측 전제:**

- **현재 1인:** 기하 드로우 ~40회 + blur ~4~6 + 그림자 1. 체감 부담은 blur가 지배. [추정] 본체 0.2–0.8ms급(기기 편차 큼).
- **현재 30인(원격+로컬):** blur만 120–180회 가능. 몬스터 수십 마리 눈/추력 blur 추가. **품질 올리며 blur를 늘리면 MMORPG 동시 표시와 충돌.**
- **권장 예산 분배:** 인게임 LOD — 멀리/작게: 실루엣+림+코어 1블러. 가까이·UI: 그라디언트·패널 디테일.

**런타임 베이크 메모리 예:**

- 셀 128×160 RGBA ≈ 80KB/장.
- 2프레임(대기·보행대표) × 16방향 × 2디자인 ≈ 64장 → **~5MB**.
- 8보행위상 × 32방향 × 2디자인 ≈ 512장 → **~40MB**.
- 맥동(time)까지 구우면 폭발 → **펄스는 오버레이로만** 즉시 모드.

연속 `yaw`를 유지한 채 전부 즉시 모드면 캐시 적중 낮음. **인게임은 `quantizeYaw(…, 16|32)` + 베이크, UI/프리뷰는 즉시 모드 고품질**이 현실적 이원화.

### 3.4 LPC/Bonfire → 코드 파츠 시스템

가져올 것: **이미지 레이어 합성이 아니라 “슬롯 선택 → z-order로 합성”**.

제안 스키마(기존 확장, 전면 폐기 아님):

```
CyborgLook {
  frame: CyborgFrame,          // 골격 비율 소스 (기존 CyborgDesign 치수)
  parts: {
    legs, pelvis, torso, backRig, shoulders, arms, neck, head, hair, weapon
  },
  implants: Set<CyborgImplant>, // 기존 유지·확장
  materials: { armor, accent, visor } // GamePalette 참조
}

CyborgPartId + PartPainter {
  draw(Canvas, CyborgDesign skeleton, _View, _Levels, PaintSet, PartPose)
  layerHint / anchorAngle  // 타원기둥 둘레 앵커 (기존 project 재사용)
}
```

| LPC 슬롯 | 코드 파츠 | 교체 단위 |
|---|---|---|
| Body type | `CyborgFrame` + 치수 15종 | assault/infiltrator (+향후 프레임) |
| Legs / Feet | `LegPart`, `BootPart` | 판금/건 노출/경량 |
| Torso | `TorsoShell` + 패널 세트 | 흉갑 스타일 |
| Head / Headwear | `HelmetPart`, `VisorPart` | 헬멧 실루엣 3~5종 |
| Hair | `CyborgHair` 확장 | cable/ponytail/crest… |
| Arms | `ArmPart` + 무기 손 | 무장/맨손 |
| Tools | blade holster (기존) | showBlade |

**레이어 순서:** 기존 `drawBody` 순서 유지(깊이 정렬 팔·등장비) — LPC z-order를 **앵커 depth sort**로 대체하는 현재 방식이 연속 회전에 더 맞다.

**커스터마이저:** `CyborgDesign`에 `partIds` 맵을 추가하거나, immutable `CyborgLook`을 두고 `CyborgDesign`은 골격+팔레트, look이 파츠를 가리키게. 서버 `CyborgKind`가 지금은 2종뿐(`cyborg_kind.dart:12-22`) — 파츠 커스터마이즈를 저장하려면 **서버 스키마 확장 또는 클라이언트-only 화장** 결정 필요([판단] 1단계는 클라이언트 프리셋만).

### 3.5 몬스터 다양성

현재 파이프:

`MonsterSpecies` → `build` → 4 렌더 메서드. 종 고유 시각 신호 = `palette` + `eyeCount` + `crestCount` + `stats.scale`.

**파츠 조합 설계:**

```
MonsterVisualSpec {
  build: MonsterBuild,           // 기본 키트
  hull: HullPartId,              // 동체 실루엣 변주
  appendages: [...],             // 날개/캐논/집게/드론
  sensors: SensorLayout(eyeCount, pattern),
  crest: CrestStyle(crestCount),
  deco: DecoSet,                 // 계열 문양(정찰기 vs 말벌)
  palette: MonsterPalette,       // 기존
  seed: int,                     // 미세 비대칭
}
```

- `MonsterFamily`에 `visualKit` 또는 `hullId`/`decoId` 추가 → `_build`에서 `MonsterSpecies.visual` 채움.
- `Enemy`는 `switch(build)` 대신 `MonsterRenderer.draw(species.visual, anim)`.
- 계열 20개가 같은 build여도 hull/deco로 **실루엣 2차 변주**. tier는 패널 수·스파이크·눈 개수(이미 일부 있음).

Commander=`_renderHeavy`+장식(`985-1029`)은 “파츠 오버레이” 프로토타입 — 이를 일반화하면 됨.

| 실루엣으로 남/녀·직업 구분, “허접 블록” 탈피 | **달성 가능** | 사지 베지에, 3~4단 명암, 패널 덩어리 |
| 선택 화면에서 “멋있는 사이보그” | **중상 가능** | 확대 전용 디테일 레이어 + 그라디언트 바이저 |
| 인게임 59px에서 화려한 문양 | **불가에 가까움** | 림·코어·바이저 점만 |
| 근육/천 주름/사실적 얼굴 | **비현실** | Rive/스프라이트 영역 |
| 200 몬스터가 전부 다른 실루엣 | **부분 가능** | 4 build × N hull × deco. 200 완전 유니크는 비용 과다 |
| 관절 리깅 전투 애니 | **코드만으론 한계** | 현 swing/bob 수준 개선은 가능, 본격 IK는 Rive 등 |

**연속 yaw 타원기둥은 이 프로젝트의 자산**이다. 8방향 스프라이트로 퇴보하면 회전 부드러움을 잃는다(`cyborg_renderer.dart:12-21`, `player.dart:1091-1093`). 베이크 시에도 16~32 양자화로 타협.

## 4. 리스크 · 함정

- **아키텍처 갈아엎기** — Design/Renderer/3표면 공유를 깨면 선택 화면과 인게임 몸 어긋남. SSOT 원칙 위반.
- **blur 증설로 “화려함” 흉내** — 30인+몹에서 프레임 스파이크. 품질 개선은 기하·그라디언트 우선, blur는 초점 1~2개.
- **자식 PositionComponent 파츠 트리** — `_View.project` depth 정렬과 이중 모델. 연속 회전 유지 비용↑.
- **파츠만 늘리고 조형 안 손댐** — 동그라미 파츠 조합 = 여전히 허접. 레이어 시스템 ≠ 예쁨.
- **몬스터 200종 각각 전용 렌더** — 유지비 폭발. family kit + tier 변조가 한계.
- **서버 kind 2종** — 클라이언트 파츠 저장을 서버에 안 넣으면 재접속 시 초기화. 확장 시 `character.rs` 동기화.
- **팔레트 하드코딩** — 본체 밝게 하면 흰 바닥에서 실루엣 소실(`palette.dart:79-80`). 진영색 변경 금지.
- **문서 드리프트** — `.cowork/cowork-prompt.md` 본문이 전투 HP 과제. 오케스트레이터/다음 분석이 잘못된 전제를 읽을 위험.
- **다른 세션 동시 편집** — 동일 파일 경합. 권고 구현 시 충돌 가능.

## 6. 불확실 · 미확인

- **실측 ms/프레임:** blur·그라디언트 비용을 프로파일러로 재지 않음. §3.3 수치는 구조 기반 추정.
- **화면당 동시 적·원격 플레이어 상한** 하드캡 수치 — `monster_population`은 청크·리스폰 중심. 30명 가정은 과제 기준.
- **Bonfire `lpc/` 예제 소스를 로컬에서 직접 열지 않음.** LPC 레이어 목록은 공개 생성기 카탈로그 기준.
- **서버가 외형 파츠를 저장할 준비가 되어 있는지** (`spacetimedb` character 테이블) — 이번 패스에서 미확인.
- **사람이 원하는 “아주 화려”의 레퍼런스 이미지 수준** — 선택 화면 기준인지 인게임 59px 기준인지 우선순위 확정 필요.
- **`.cowork/cowork-prompt.md`를 비주얼 과제로 갱신할지** — 분석만 수행, 수정 안 함.
