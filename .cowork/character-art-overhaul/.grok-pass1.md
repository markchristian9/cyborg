## 1. 결론 요약

**지금 못생긴 이유는 아키텍처 부재가 아니라 조형 언어가 “프리미티브 조립 + 2톤 평면”에 멈춰 있기 때문이다.** `CyborgDesign`/`CyborgRenderer`와 세 표면 공유는 이미 LPC식 “스펙→레이어 합성→재사용”의 골격이다.  
**몬스터는 200종이 네 실루엣으로 접혀** 색·눈·스케일만 바뀌므로 “허접한 복붙”이 더 두드러진다.  
**해결은 정적 이미지 없이, 코드 파츠 레지스트리 + 베지에/다단 명암/초점 디테일 + (선택) `Picture`/`ui.Image` 베이크**로 품질을 올리고, `MonsterSpecies`에 파츠 시그니처를 붙이는 것이다. “AAA급 화려함”의 상한은 코드 드로잉으로 **확대 UI에서는 중상, 59px 인게임에서는 실루엣·림·코어 중심**까지다. 그 이상은 Rive/베이크 스프라이트 영역이다.

## 3. 상세 분석

### 3.1 범위와 권위

| 계층 | 권위 | 비고 |
|---|---|---|
| 외형 수치·색 | `CyborgDesign` + `GamePalette` | SSOT. 새 색은 팔레트 경유 |
| 그리기 | `CyborgRenderer` | 유일한 몸 페인터 |
| 소비 표면 | `player` / `remote_player` / portrait / preview | 같은 `drawBody` |
| 몬스터 데이터 | `MonsterSpecies`/`MonsterFamily` | 전투·이름·팔레트 |
| 몬스터 그림 | `Enemy._render*` | **데이터와 1:1이 아님** |
| 서버 kind | `CyborgKind` ↔ `male_cyborg`/`female_cyborg` | 외형 수치는 갖지 않음 |

디스크上的 `.cowork/cowork-prompt.md`는 HP·전투 수식 과제 문구가 남아 있으나, **이번 주입 프롬프트(캐릭터 비주얼)가 분석 전제**다. 문서 불일치는 §4.

### 3.2 왜 “동그라미·네모”로 읽히는가 (조형 번역)

사람의 지적은 정확하다. 조형 언어로 풀면:

1. **실루엣 리듬 부족**  
   다리는 네 점 사다리꼴 한 장(`145-150`), 팔도 사각형 스트립(`566-572`). 허벅지–종아리–발 곡선 변화, 삼각근–이두 팽창이 없다. 축소 시 “막대 두 개 + 박스 몸”이 된다.

2. **곡률 단조**  
   헬멧·어깨·골반은 모두 비슷한 `RRect` 반경. 머리–몸 연결은 `drawRect` 목(`627-629`). 초점(바이저·코어) 외에는 곡률 대비가 약하다.  
   **예외:** 몸통 허리는 `quadraticBezierTo`로 오목/볼록(`244-261`) — 설계 의도는 있으나 사지·머리가 따라오지 않아 전체가 “프로필만 다른 블록 피규어”로 남는다.

3. **명암 단계 2단**  
   `armor` / `armorLight` / `_deepShade` 정도. 원통 그라데이션·스펙큘러·오클루전 밴드가 없다. 동일 면적이 단색 덩어리로 보여 플라스틱 블록처럼 보인다. `world_tree` 줄기도 “2톤이면 원통으로 읽힌다”고 주석(`171`)하나, 캐릭터 사지는 그 2톤조차 앞/뒤 깊이 이진 분기(`isBack ? dark : armor`)에 가깝다.

4. **디테일 밀도·초점**  
   코어·바이저·림 스트로크는 있으나, 59px에서는 코어 블러·바이저 정도만 산다. 갈비 3선·1.4px 모듈·안테나 끝 원(`319-326,752,772`)은 **확대 프리뷰(스케일 2~3.5)** 용 정보다. 인게임 초점은 “어두운 실루엣 + 청록 림 + 바이저/코어 점”이어야 하는데, 확대에서도 면이 비어 “허접”으로 읽힌다.

5. **덩어리 대비**  
   Assault 비대칭 어깨 증설(`488-504`)은 좋은 방향. 그러나 장갑 패널이 몸통 실루엣과 같은 톤·같은 모서리 언어라 계층이 안 쌓인다.

### 3.3 코드만으로 “예쁜” 캐릭터 — 쓸 수 있는 수단과 비용

| 수단 | 이 프로젝트 적합성 | 59px | 확대 UI | 비용(대략) |
|---|---|---|---|---|
| `Path`+베지에/큐빅 | 이미 몸통·포니테일. 사지·헬멧에 확대 | 실루엣 개선에 필수 | 형태미의 본진 | 드로우 수 ↑, CPU 기하 저렴 |
| `Linear`/`RadialGradient` | 렌더러에 **미사용**. `safe_zone`/`action_rpg_game` 하늘 등엔 사용 중 | 원통 읽힘에 유리 | 광택·바이저 유리 | 셰이더 바인딩 소폭. blur보다 쌈 |
| 다단 하이라이트/림(단색 레이어) | 흉갑 패널·림 스트로크 패턴 확장 | 1~2px 림만 생존 | 패널 분할 | 드로우 +2~6/부위 |
| `MaskFilter.blur` | 이미 캐릭터당 수회 | 코어 점 글로우는 유효 | 과다 시 번짐 | **비쌈.** 30명×5~8회=150~240 블러/프레임 |
| `saveLayer` | portrait 비선택 페이드에 사용 | 비추(전체 알파) | 마스크 합성용 | 오프스크린. 캐릭터당 1회도 부담 |
| `Picture`/`toImage` 베이크 | `ground_layer` 선례 + `quantizeYaw` 주석 | 인게임 권장 경로 | 워밍업 후 동일 | 메모리·워밍업 수치화 가능 |
| Flame 자식 컴포넌트 트리 | 연속 `_View` 투영과 **모델 충돌** | — | 미리보기 가능 | 부위별 transform은 가능하나 depth 정렬 재발명 |
| `flame_rive` | `pubspec`에 없음 | 연속 yaw 아이소 유지 어려움 | 화려한 관절 애니 | 의존성·아트 파이프라인 추가 |

**프레임 예산(16.6ms) 스케치 — 벤치 없이 구조 기반 추정, 실측 전제:**

- **현재 1인:** 기하 드로우 ~40회 + blur ~4~6 + 그림자 1. 체감 부담은 blur가 지배. [추정] 본체 0.2–0.8ms급(기기 편차 큼).
- **현재 30인(원격+로컬):** blur만 120–180회 가능. 몬스터 수십 마리 눈/추력 blur 추가. **품질 올리며 blur를 늘리면 MMORPG 동시 표시와 충돌.**
- **권장 예산 분배:** 인게임 LOD — 멀리/작게: 실루엣+림+코어 1블러. 가까이·UI: 그라디언트·패널 디테일.

**런타임 베이크 메모리 예:**

- 셀 128×160 RGBA ≈ 80KB/장.
- 2프레임(대기·보행대표) × 16방향 × 2디자인 ≈ 64장 → **~5MB**.
- 8보행위상 × 32방향 × 2디자인 ≈ 512장 → **~40MB**.
- 맥동(time)까지 구우면 폭발 → **펄스는 오버레이로만** 즉시 모드.

연속 `yaw`를 유지한 채 전부 즉시 모드면 캐시 적중 낮음. **인게임은 `quantizeYaw(…, 16|32)` + 베이크, UI/프리뷰는 즉시 모드 고품질**이 현실적 이원화.

### 3.4 LPC/Bonfire → 코드 파츠 시스템

가져올 것: **이미지 레이어 합성이 아니라 “슬롯 선택 → z-order로 합성”**.

제안 스키마(기존 확장, 전면 폐기 아님):

```
CyborgLook {
  frame: CyborgFrame,          // 골격 비율 소스 (기존 CyborgDesign 치수)
  parts: {
    legs, pelvis, torso, backRig, shoulders, arms, neck, head, hair, weapon
  },
  implants: Set<CyborgImplant>, // 기존 유지·확장
  materials: { armor, accent, visor } // GamePalette 참조
}

CyborgPartId + PartPainter {
  draw(Canvas, CyborgDesign skeleton, _View, _Levels, PaintSet, PartPose)
  layerHint / anchorAngle  // 타원기둥 둘레 앵커 (기존 project 재사용)
}
```

| LPC 슬롯 | 코드 파츠 | 교체 단위 |
|---|---|---|
| Body type | `CyborgFrame` + 치수 15종 | assault/infiltrator (+향후 프레임) |
| Legs / Feet | `LegPart`, `BootPart` | 판금/건 노출/경량 |
| Torso | `TorsoShell` + 패널 세트 | 흉갑 스타일 |
| Head / Headwear | `HelmetPart`, `VisorPart` | 헬멧 실루엣 3~5종 |
| Hair | `CyborgHair` 확장 | cable/ponytail/crest… |
| Arms | `ArmPart` + 무기 손 | 무장/맨손 |
| Tools | blade holster (기존) | showBlade |

**레이어 순서:** 기존 `drawBody` 순서 유지(깊이 정렬 팔·등장비) — LPC z-order를 **앵커 depth sort**로 대체하는 현재 방식이 연속 회전에 더 맞다.

**커스터마이저:** `CyborgDesign`에 `partIds` 맵을 추가하거나, immutable `CyborgLook`을 두고 `CyborgDesign`은 골격+팔레트, look이 파츠를 가리키게. 서버 `CyborgKind`가 지금은 2종뿐(`cyborg_kind.dart:12-22`) — 파츠 커스터마이즈를 저장하려면 **서버 스키마 확장 또는 클라이언트-only 화장** 결정 필요([판단] 1단계는 클라이언트 프리셋만).

### 3.5 몬스터 다양성

현재 파이프:

`MonsterSpecies` → `build` → 4 렌더 메서드. 종 고유 시각 신호 = `palette` + `eyeCount` + `crestCount` + `stats.scale`.

**파츠 조합 설계:**

```
MonsterVisualSpec {
  build: MonsterBuild,           // 기본 키트
  hull: HullPartId,              // 동체 실루엣 변주
  appendages: [...],             // 날개/캐논/집게/드론
  sensors: SensorLayout(eyeCount, pattern),
  crest: CrestStyle(crestCount),
  deco: DecoSet,                 // 계열 문양(정찰기 vs 말벌)
  palette: MonsterPalette,       // 기존
  seed: int,                     // 미세 비대칭
}
```

- `MonsterFamily`에 `visualKit` 또는 `hullId`/`decoId` 추가 → `_build`에서 `MonsterSpecies.visual` 채움.
- `Enemy`는 `switch(build)` 대신 `MonsterRenderer.draw(species.visual, anim)`.
- 계열 20개가 같은 build여도 hull/deco로 **실루엣 2차 변주**. tier는 패널 수·스파이크·눈 개수(이미 일부 있음).

Commander=`_renderHeavy`+장식(`985-1029`)은 “파츠 오버레이” 프로토타입 — 이를 일반화하면 됨.

### 3.6 커스터마이저 UI

이미:

- `CyborgPreviewPainter` / `CyborgPortrait` = Flutter `CustomPaint` + 동일 렌더러.
- `preview_main.dart` = 디자인 전용 진입점.
- 배율 1.0~3.5, 보행/뒷모습 토글(`cyborg_preview.dart:374-409`).

부족한 것:

- 파츠 선택 상태 모델(`selectedHelmet` 등).
- 파츠 카탈로그 UI(칩/리스트) — 현재 임플란트는 **읽기 전용 라벨**(`232-266`).
- `CharacterScreen`은 스탯 패널만, 렌더러 없음 → 인게임 커스터마이저와 무관.

`CustomPainterComponent` 공유는 **필수가 아님**. 상태 없는 `CyborgRenderer.drawBody`가 이미 Flame/Flutter를 잇는다. 이득은 미미, 리팩터 비용만 큼.

### 3.7 현실적 상한

| 목표 | 코드 드로잉 | 조건 |
|---|---|---|
| 실루엣으로 남/녀·직업 구분, “허접 블록” 탈피 | **달성 가능** | 사지 베지에, 3~4단 명암, 패널 덩어리 |
| 선택 화면에서 “멋있는 사이보그” | **중상 가능** | 확대 전용 디테일 레이어 + 그라디언트 바이저 |
| 인게임 59px에서 화려한 문양 | **불가에 가까움** | 림·코어·바이저 점만 |
| 근육/천 주름/사실적 얼굴 | **비현실** | Rive/스프라이트 영역 |
| 200 몬스터가 전부 다른 실루엣 | **부분 가능** | 4 build × N hull × deco. 200 완전 유니크는 비용 과다 |
| 관절 리깅 전투 애니 | **코드만으론 한계** | 현 swing/bob 수준 개선은 가능, 본격 IK는 Rive 등 |

**연속 yaw 타원기둥은 이 프로젝트의 자산**이다. 8방향 스프라이트로 퇴보하면 회전 부드러움을 잃는다(`cyborg_renderer.dart:12-21`, `player.dart:1091-1093`). 베이크 시에도 16~32 양자화로 타협.

## 4. 리스크 · 함정

- **아키텍처 갈아엎기** — Design/Renderer/3표면 공유를 깨면 선택 화면과 인게임 몸 어긋남. SSOT 원칙 위반.
- **blur 증설로 “화려함” 흉내** — 30인+몹에서 프레임 스파이크. 품질 개선은 기하·그라디언트 우선, blur는 초점 1~2개.
- **자식 PositionComponent 파츠 트리** — `_View.project` depth 정렬과 이중 모델. 연속 회전 유지 비용↑.
- **파츠만 늘리고 조형 안 손댐** — 동그라미 파츠 조합 = 여전히 허접. 레이어 시스템 ≠ 예쁨.
- **몬스터 200종 각각 전용 렌더** — 유지비 폭발. family kit + tier 변조가 한계.
- **서버 kind 2종** — 클라이언트 파츠 저장을 서버에 안 넣으면 재접속 시 초기화. 확장 시 `character.rs` 동기화.
- **팔레트 하드코딩** — 본체 밝게 하면 흰 바닥에서 실루엣 소실(`palette.dart:79-80`). 진영색 변경 금지.
- **문서 드리프트** — `.cowork/cowork-prompt.md` 본문이 전투 HP 과제. 오케스트레이터/다음 분석이 잘못된 전제를 읽을 위험.
- **다른 세션 동시 편집** — 동일 파일 경합. 권고 구현 시 충돌 가능.

## 6. 불확실 · 미확인

- **실측 ms/프레임:** blur·그라디언트 비용을 프로파일러로 재지 않음. §3.3 수치는 구조 기반 추정.
- **화면당 동시 적·원격 플레이어 상한** 하드캡 수치 — `monster_population`은 청크·리스폰 중심. 30명 가정은 과제 기준.
- **Bonfire `lpc/` 예제 소스를 로컬에서 직접 열지 않음.** LPC 레이어 목록은 공개 생성기 카탈로그 기준.
- **서버가 외형 파츠를 저장할 준비가 되어 있는지** (`spacetimedb` character 테이블) — 이번 패스에서 미확인.
- **사람이 원하는 “아주 화려”의 레퍼런스 이미지 수준** — 선택 화면 기준인지 인게임 59px 기준인지 우선순위 확정 필요.
- **`.cowork/cowork-prompt.md`를 비주얼 과제로 갱신할지** — 분석만 수행, 수정 안 함.
