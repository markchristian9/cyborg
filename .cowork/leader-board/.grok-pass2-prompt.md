# cowork 시스템 프롬프트 — Cyborg (actionrpg)

> 🛑 이 파일은 `cowork` 이 claude·codex·grok·kimi **네 AI 에게 분석을 시킬 때마다 프롬프트 맨 앞에
> 반드시 주입** 하는 **이 프로젝트의 시스템 프롬프트** 다.
>
> ⚠️ 네 AI 는 읽기 전용이다. 이 문서에 "파일을 고쳐라" 같은 지시를 써도 물리적으로 실행되지 않는다
> (실제 수정은 종합(final-report.md)을 마친 오케스트레이터가 한다).

## Overview

**Cyborg** — Flutter + Flame 으로 만드는 2.5D 아이소메트릭 액션 RPG **MMORPG** 다.
세계관은 "AI 로봇이 점령한 세계를 인간 사이보그가 되찾는다".

핵심 전제:

- **단일 공유 월드.** 매치별 인스턴스도, 분리된 스테이지도 없다. 플레이어는 세션이 아니라 **월드에
  접속한다.** 여러 사용자가 같은 월드에서 동시에 사냥하고, 서로의 존재·이동·전투가 실시간으로 보인다.
  PK 가 허용된다.
- 백엔드는 **SpacetimeDB**(Rust 모듈, maincloud 의 `withcenter-cyborg`). 게임 서버 계층이 따로 없고
  DB 안에서 reducer·view 가 돈다.
- 현재 단계: 계정·캐릭터 선택 관문(`lib/auth/`)이 붙었고, 싱글 플레이 수준의 전투 루프
  (웨이브·레벨업·인벤토리·안전지대)가 돌아간다. **실시간 멀티플레이 동기화는 아직 없다.**
  방금 **레벨 리더보드**(전역 순위표)가 서버·클라이언트 양쪽에 추가되어 maincloud 에 배포됐다.

이번 분석에서 네 AI 에게 시키려는 것: **레벨 순위 랭킹이 실제로 올바르게 동작하는지** 를 서버 모듈과
클라이언트 양쪽에서 교차 검증하는 것. 순위 산정 규칙, 갱신 전파, 표시 로직, 경쟁 조건, MMORPG 로
사람이 늘었을 때의 정합성·성능까지 본다.

## Persona

**실시간 멀티플레이 게임의 서버 권위(authority)와 랭킹 시스템을 설계해 온 시니어 백엔드/게임
엔지니어.** 다음 두 관점을 동시에 갖는다.

1. **분산 데이터 정합성** — 여러 클라이언트가 같은 표를 동시에 건드릴 때 순위가 어떻게 어긋나는지,
   갱신이 어떤 경로로 전파되고 어디서 유실·역전되는지를 본다.
2. **게임 디자인** — 순위 규칙이 플레이어에게 공정하고 이해 가능한지, 동점 처리와 표시가 "내가 왜
   저 사람보다 아래인지" 를 납득시키는지를 본다.

부수적으로 **클라이언트를 신뢰하지 않는 보안 관점**을 항상 겸한다 — 클라이언트가 보낸 값으로 순위가
정해지는 지점이 있으면 반드시 지적한다.

## Instructions

1. **모든 주장에 `파일:줄` 근거를 붙인다.** 근거를 못 대는 추정은 `[추측]` 으로 명시한다.
2. **이 프로젝트의 서버 설계 원칙**(`spacetimedb/src/lib.rs` 머리말)을 어기는 권고는 하지 않는다:
   - 클라이언트를 신뢰하지 않는다. 소유자는 `ctx.sender()` 에서 도출하며 `account_id` 를 인자로 받는
     reducer 는 없다.
   - 비밀번호는 별도 표(`AccountSecret`)에 둔다.
   - **모든 테이블이 비공개다.** 클라이언트가 읽는 것은 view 뿐이다.
   - 시각은 `ctx.timestamp`, 난수는 `ctx.random()` 만 쓴다.
3. **용어를 정확히 구분한다.**
   - `level` — 캐릭터 성장 단계. 상한 30(`LevelSystem.maxLevel`, 서버 `leaderboard::MAX_LEVEL`).
   - `xp` — **누적 총량이 아니라 "현재 레벨 안에서 다음 레벨까지 쌓은 진행도"** 다. 서버·클라이언트가
     같은 의미로 쓴다. 이 정의를 오해한 분석은 무효다.
   - `rank` — 1부터 시작하는 순위. 동점이어도 겹치지 않는다.
   - "웨이브·점수·처치 수" 는 리더보드 대상이 **아니다**. 순위는 레벨(과 동점 시 xp)로만 정해진다.
4. **SpacetimeDB 2.7 의 제약을 전제로 판단한다.**
   - view 가 받는 핸들은 읽기 전용이라 `iter()` 가 없다. 여러 행을 훑는 길은 인덱스 범위 조회뿐이다.
   - **view 도 구독해야 행이 온다**(실측). 구독하지 않으면 reducer 는 성공하는데 캐시는 비어 있다.
   - Dart 코드 생성기는 view 반환 타입의 이름을 **테이블 목록에서만** 찾는다. 테이블이 아닌 타입을
     반환하는 view 는 `Type2` 같은 존재하지 않는 클래스를 참조하는 깨진 코드를 만든다.
   - auto_inc id 는 연속을 보장하지 않는다. 정렬 기준으로 삼을 때 이 점을 고려한다.
5. **"서버가 전투를 시뮬레이션하지 않는다"는 현재 한계를 사실로 인정하고 논한다.** 레벨은 클라이언트가
   신고한다. 그것을 없애라는 권고보다, 그 전제 위에서 무엇을 더 막을 수 있는지 / 어디까지가 수용
   가능한 위험인지를 구체적으로 짚는 편이 유용하다.
6. **MMORPG 전제를 잊지 않는다.** "혼자 플레이할 때는 문제없다" 는 판정은 이 프로젝트에서 의미가 없다.
   같은 월드에 수십~수천 명이 동시에 있고 각자 레벨업할 때 무슨 일이 생기는지로 판단한다.
7. 리더보드 화면은 **Flame `PositionComponent`** 다(Flutter 위젯이 아니다). 좌표·히트테스트·클리핑은
   캔버스 기준이며, `CharacterScreen` 과 같은 관례를 따른다. 위젯 전제의 권고는 맞지 않는다.
8. 주석과 문서는 **한국어**로 쓴다. 코드 식별자는 영문 그대로.

## 분석 원칙

1. **근거 우선.** 모든 주장에는 출처를 붙인다 — 작업공간 자료는 `파일경로:줄번호`, 외부 사실은 그
   근거를 명시한다. 근거를 못 찾은 주장은 반드시 `[추측]` 으로 표시한다. 표시 없는 추측은 최악의
   결함으로 간주된다.
2. **읽고 말하라.** 실제로 열어 확인한 내용만 사실로 진술한다. 존재하지 않는 파일·함수·용어·수치를
   지어내지 말라(환각 금지). 확인 못 했으면 §6 에 "미확인" 으로 남긴다.
3. **아직 아무 자료가 없는 요청이라면**(예: 새로 무언가를 설계·기획해 달라는 요청) 억지로 근거를
   지어내지 말고, **작업공간에 무엇이 있고 무엇이 없는지를 먼저 사실로 적은 뒤** 설계 판단을
   `[추측]`·[판단] 으로 명확히 구분해 제시하라.
4. **범위와 경계를 분명히.** 이 판단이 어느 영역에 속하는지 명시한다(예: 어느 계층·어느 단계·누구의
   결정 권한인지). 한쪽만 바꿔서 되는지, 양쪽을 함께 바꿔야 하는지가 결론을 바꾼다.
5. **이 작업공간의 실제 제약을 반영.** 지침 문서와 자료에서 읽어낸 제약(대상 사용자·품질 기준·분량·
   기한·호환성·안전 규칙·검수 절차 등)을 무시한 이상론을 쓰지 말라. 실행 불가능한 권고는 권고가 아니다.
6. **모르면 모른다고 하라.** 억지 결론보다 "무엇을 더 봐야 하는지" 가 낫다.

## 1. 결론 요약

**Happy path(정상 클라이언트·단일 기기·여유 있는 전송 간격)에서는 레벨 순위 랭킹이 설계대로 동작한다.** 서버가 `level ↓ → xp(현재 레벨 진행도) ↓ → created_at ↑ → id` 로 안정 정렬하고, 상위 100 + `my_rank` 분리, 클라이언트는 재계산 없이 표시만 한다.  
**그러나 “올바로 완성됐다”고 보기엔 부족하다.** 연속 레벨업·로그아웃 시 `_inFlight` 때문에 최신 진행이 유실·지연될 수 있고, `report_progress` 는 치팅·xp 폭주에 거의 무력하며, 재접속 시 로컬 전투 레벨은 항상 1부터라 순위표 숫자와 플레이 체감이 분리된다. MMORPG 규모에서는 전수 스캔 view 가 구조적 리스크다.  
**수정은 이 분석 단계에서는 하지 않았다.** 아래 §5 가 보완 우선순위다.

## 3. 상세 분석

### 3.1 권위(authority)와 데이터 흐름

```
[전투 로컬] Player.gainXp → level/xp
    → SpacetimeGameSync.reportLevel / tick(5s) / reportRunFinished
    → reducer report_progress(level, xp)
    → PlayerCharacter 갱신
    → view leaderboard / my_rank 재계산
    → (화면 open 시) 구독 캐시 → SpacetimeLeaderboard → LeaderboardScreen
```

- **순위 권위는 서버 view**다. 클라이언트는 rank 를 다시 만들지 않는다 (`spacetime_leaderboard.dart:14–15`).
- **성장 수치 권위는 현재 클라이언트**다. 서버는 시뮬 없이 신고값을 저장한다 (`leaderboard.rs:145–153`). 프로젝트 전제로 인정된 한계이며, 그 위에서 서버는 “명백히 불가능한 값”만 막는다.

### 3.2 순위 규칙 (게임 디자인 관점)

| 기준 | 동작 | 공정성 메모 |
|---|---|---|
| 1차 | level 높은 순 | 명확 |
| 2차 | 같은 level 에서 xp(레벨 내 진행도) 높은 순 | 정의가 문서·코드 일치 |
| 3차 | 먼저 생성된 캐릭터 우선 | “왜 아래인지” UI 에 안 보임 |
| 4차 | 작은 `id` | auto_inc 비연속 전제 하에 안정용 |

`rank` 는 1부터 **겹치지 않음**(dense/competition 혼동이 아닌, 타이브레이크 포함 완전 순서). 웨이브·킬·점수는 대상 아님.

### 3.3 서버 정합성

- 별도 순위 테이블 없음 → 캐릭터 삭제·갱신과 어긋날 표가 없음 (`leaderboard.rs:3–6`) — 좋은 선택.
- 단조 증가로 다기기 역전 덮어쓰기 완화 (`175–177`).
- **빠진 서버 가드**
  - `xp` 상한 없음 → 같은 level 에서 `xp = u64::MAX` 신고 시 동점 구간 항상 선두 가능.
  - level 1→30 한 방 점프 허용(단조만 만족).
  - 정상 클라이언트의 `xp < xpToNext(level)` 불변식은 서버에 없음 (`LevelSystem.xpToNext` 는 클라이언트만, `level_system.dart:40–44`).

### 3.4 클라이언트 보고 경로 (가설 2 — 실질 버그)

```dart
// spacetime_game_sync.dart
if (_rejected || _inFlight) return;  // 최신 값을 큐에 안 남김
```

1. **연속 레벨업**: `gainXp` while 루프가 `onLevelUp` 을 여러 번 호출 → 첫 `reportProgress` 진행 중 이후 `reportLevel` 은 전부 스킵. `_level` 메모리는 갱신되지만 전송은 다음 5초 `tick` 또는 이후 유휴 구간에 의존.
2. **로그아웃 레이스**: `requestLogout` → `reportRunFinished` → `_send` 가 `_inFlight` 이면 **최종 레벨이 서버에 안 남을 수 있음**. 세션이 접히면 `tick` 도 없음.
3. **`reportLevel` 이 항상 xp=0**: 레벨업 직후 잔여 xp 가 있어도 즉시 보고는 0. 5초 후 tick 이 보정. 그 사이 동점 구간 순위가 잠시 낮을 수 있음(치명적이진 않음).

정상 플레이에서 대부분 5초 안에 따라잡히지만, **순위 “즉시성”·세션 종료 직전 신뢰도는 깨질 수 있다.**

### 3.5 로컬 레벨 vs 서버 레벨 (가설 3)

- 캐릭터 선택 UI 는 서버 `Lv.N` 을 보여 줌 (`character_select_screen.dart:258`).
- 월드 입장 시 `Player` 는 항상 `level = 1` (`player.dart:32`, `action_rpg_game.dart:175`).
- 서버에 이미 15가 있으면, 로컬이 15 미만인 동안 `report_progress` 는 조용히 무시 (`175–177`) → **순위표는 과거 최고 도달처럼 유지**, 인게임 HUD 는 1부터.
- 설계를 “세션 런 성장 + 서버에 최고 기록” 으로 보면 일관되지만, 화면 카피(“레벨 순위”)만으로는 플레이어가 “지금 이 몸체의 레벨”로 오해하기 쉽다. **문서화된 제품 정의가 코드에 없음** `[판단: 명시 필요]`.

### 3.6 구독·표시

- view 도 구독 필수 전제를 따름 (`cyborg_connection.dart:16–21, 39–41`).
- 화면 닫을 때 detach — 트래픽 절약 의도는 맞음.
- **attach race**: `attach` 완료 전에 `detach` 하면 `_querySetId == null` 이라 unsubscribe 못 함 → subscribe 완료 후 구독이 열린 채 남음 (`spacetime_leaderboard.dart:44–63`). 다음 open 이 기존 id 를 재사용해 치명 오류는 아닐 수 있으나, “볼 때만 구독” 계약이 깨짐.
- XP 틱 바는 **같은 level 동료 대비 상대 비율** (`leaderboard_screen.dart:485–491`). 절대 xp·동점 사유(생성 순서)는 안 보여 “왜 내가 아래?” 납득이 약함.

### 3.7 MMORPG 스케일

- 누군가 `report_progress` 할 때마다 `leaderboard` 구독자 전원에게 결과가 밀린다는 주석 (`cyborg_connection.dart:36–38`).
- 매 계산이 **전 캐릭터 로드 + O(N log N) 정렬** / `my_rank` 는 **전 행 outranks 스캔**.
- SpacetimeDB 2.7: view 핸들에 `iter()` 없음 → 인덱스 범위가 유일한 다행 경로. `filter((me.level+1)..)` 등으로 상위 레벨만 세는 최적화 여지는 있음(미구현).
- 캐릭터 수가 수백~수천·동시 레벨업이 잦아지면 **CPU·구독 대역**이 먼저 한계 `[추측: 임계값은 실측 필요]`.

### 3.8 테스트 커버리지

| 있음 | 없음 |
|---|---|
| 정렬 단위(서버) | 연속 레벨업 + `_inFlight` 유실 |

## 4. 리스크 · 함정

- **진행도 유실**: 연속 레벨업 + 즉시 로그아웃 시 서버 순위가 실제 도달 레벨보다 낮을 수 있음 (`spacetime_game_sync.dart:78–80`, `action_rpg_game.dart:812–817`).
- **치팅 순위**: 조작 클라이언트가 level 30 / 거대 xp 를 넣으면 현재 가드로 막기 어려움. 프로젝트 전제상 완전 제거 요구는 부적절하나, **순위 신뢰도 마케팅 전**에는 수용 범위 명시 필요.
- **xp 폭주**: 서버에 xp 상한 없음 → 동점 타이브레이크 무력화.
- **의미 혼동**: 선택 화면 Lv vs 인게임 Lv 불일치 → “랭킹이 틀렸다” 오인 리포트 유발 가능.
- **스케일**: 전수 정렬 view 를 실시간 구독에 묶으면 인구 증가 시 비용 선형 이상.
- **구독 레이스**: 여닫기 빠른 UI 에서 백그라운드 구독 잔존.
- **`_rejected` 영구 차단**: 한 번 `SpacetimeDbReducerException` 이면 같은 `SpacetimeGameSync` 생명주기 동안 재시도 없음. 캐릭터 미선택 화면 전제로는 OK, 예외 분류가 넓으면 오탐 시 세션 전체 기록 중단.
- **설계 원칙 준수**: `account_id` 인자 없음·비공개 테이블·LeaderboardEntry 더미 테이블(코드젠용)은 원칙과 맞음. “서버가 전투 시뮬” 로 바꾸라는 권고는 현 단계 범위 밖.

## 6. 불확실 · 미확인

- SpacetimeDB maincloud 에서 **Anonymous view 결과 캐시·재계산 트리거**의 정확한 비용 모델(구독자 수 × 갱신 빈도) — 문서/실측 없음.
- view 구독 캐시가 상위 100 구성원이 바뀔 때 **삭제 델타를 항상 올바르게 반영하는지** 클라이언트 SDK 동작 — 코드만으로 확정 불가.
- 프로덕션 `withcenter-cyborg` 의 현재 캐릭터 수·실제 순위 분포 — 이 환경에서 조회하지 않음.
- `_inFlight` 유실이 실유저 세션에서 얼마나 잦은지 — 재현 시나리오는 코드상 명확하나 텔레메트리 없음.
- 제품이 원하는 순위 의미: **라이브 성장** vs **역대 최고 기록** — 코드는 후자에 가깝고 UI는 전자처럼 읽힘. **사람 판단 필요.**
- cargo/flutter 테스트는 읽기 전용 분석에서 **실행하지 않음**. 통합 테스트 통과 여부는 저장소 코드 존재만 확인.

---

**한 줄 판정:** 순위 **규칙과 표시 파이프라인의 뼈대는 맞고**, 통합 테스트가 기본 동작을 뒷받침한다. 다만 **전송 큐 부재·느슨한 서버 검증·로컬/서버 레벨 의미 불일치·전수 스캔 스케일** 때문에 “MMORPG 레벨 랭킹이 올바로 완성” 단계는 아니다. 우선순위 1–2(전송 신뢰 + xp 가드)부터 보완하는 것이 순위 정합성에 가장 직접적이다.
