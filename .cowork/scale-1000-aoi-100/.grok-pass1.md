요청하신 목표(동접 1,000 / AOI 100) 분석을 위해 기준 문서와 SpacetimeDB 서버·클라이언트 자료를 먼저 읽고, 계산에 필요한 수치를 수집합니다.## 0. 탐색 로그 (ToT)

- **세운 가설**
  1. **(구조·구독 층)** 현재 상한 “동접 수십 명”은 `SELECT * FROM world_player` / `monster` 전역 구독의 \(5N^2\)·\(33N^2\) fan-out 때문이며, AOI 100으로 구독을 상수화하면 네트워크 병목은 제거 가능하다.
  2. **(락·쓰기 층)** 전역 쓰기 직렬화 아래 동접 1,000 × 5Hz = 5,000 TPS의 `move_to` 자체는 단순 reducer라 이론상 가능하나, `monster_ai` 틱이 락을 오래 잡으면 실질적으로 붕괴한다.
  3. **(스키마·구현 층)** AOI 구독이 문서상 권고돼 있어도 `WorldPlayer`에 `chunk`/인덱스가 없고 클라이언트는 전역 구독만 하므로, **지금 코드만으로는 목표 불가**이며 스키마·구독·AI 루프를 함께 바꿔야 한다.
  4. **(타협 층)** SpacetimeDB 단일 DB·수평 확장 부재·좁은 구독 SQL 때문에 “한 지점에 1,000명이 서로 전부 보이는” 상태는 끝까지 불가하고, **AOI 상한 100 + 의도/LOD** 가 설계 타협의 핵심이다.

## 1. 결론 요약

**지금 구조로는 동접 1,000 / AOI 100은 불가능하다.** 실질 상한 “수십 명” 판정은 자릿수가 맞다(전역 구독 \(5N^2\) + AI \(O(\text{근처 몹}\times N)\)).  
**조건부로 목표는 설계 가능하다**: (1) 청크 기반 AOI 구독, (2) `WorldPlayer`/`Monster` 세로 분할 + 좌표 테이블, (3) AI를 청크 버킷으로 재작성, (4) 좌표 보고 5Hz→1~2Hz 또는 의도 전송, (5) 화면 표시 상한 ≈100.  
**AOI 100이 서로 보이는 최악 집결**에서 플레이어 좌표만 초당 **약 5×10⁵ 행 · 수십~90MB/s(행 크기·프로토콜 오버헤드 포함)** 이며, 전역 구독 대비 **약 10배** 줄지만 여전히 최적화 없이는 비싸다.  
**SpacetimeDB 한계로 타협이 필요한 지점**: 단일 DB·쓰기 전역 직렬화·구독 SQL 산술/프로젝션 불가·모듈 상주 공간 인덱스 불가. “한 좌표에 1,000명이 전원 상호 가시”는 이 스택에서 끝까지 포기해야 한다.

## 3. 상세 분석

### 3.1 질문 1 — AOI 100 상태의 초당 행·바이트

**기호**  
- \(N=1000\): 동접  
- \(A=100\): 한 플레이어 AOI 안의 **다른** 플레이어 수(목표)  
- \(R=5\): 초당 좌표 보고(현재 200ms, 이동 중·`_minStep` 이상일 때)  
- \(S_{wp}\): `world_player` 행 BSATN 크기  

**행 크기 \(S_{wp}\) (계산)** — `world_player.dart:98-119` 필드 합:

| 필드 | 대략 바이트 |
|---|---:|
| Identity | 32 |
| character_id u64 | 8 |
| name/kind 문자열 | 이름 가변 + `male_cyborg`≈15 → **~25–40** |
| level, grid_x/y, hp×2, alive | 4+8+8+1 ≈ 21 |
| Timestamp ×7 | 56 |
| mp, max_mp, defense, deaths | 16 |
| **합계** | **약 160–200B** |

문서 추정치 **180B**(`GAME-SERVER.md:175`)는 자릿수로 타당. 이하 \(S_{wp}=180\)B.  
프로토콜 프레임(테이블/op 헤더)은 미측정 → **페이로드 하한**으로 취급(+10–30% 가능) → §6.

**서버 쓰기 수(구독과 무관)**  
\[
U = N \times R = 1000 \times 5 = 5{,}000\ \text{updates/s}
\]
(전원이 매 주기 이동하는 최악. 정지·`_minStep` 필터 시 실측은 이보다 작음.)

**A. 현재 구조(전역 구독)**  
\[
\text{egress rows/s} = U \times N = 5N^2 = 5 \times 10^6
\]
\[
\text{egress bytes/s} \approx 5\times10^6 \times 180 = 9\times10^8 \approx 900\ \text{MB/s}
\]
→ Maincloud·클라이언트 모두 비현실. **문서 표와 일치**(`GAME-SERVER.md:186-190`).

**B. 목표: AOI=A=100 상호 가시(대칭 AOI, 전원 이동)**  
각 갱신은 대략 \(A\)명의 구독자에게 fan-out(같은 클러스터 안).

\[
\text{egress rows/s} = U \times A = 5{,}000 \times 100 = 5\times10^5
\]
\[
\text{egress bytes/s} \approx 5\times10^5 \times 180 = 9\times10^7 \approx 90\ \text{MB/s}
\]

**클라이언트 1명 수신(플레이어만)**  
\[
A \times R \times S_{wp} = 100 \times 5 \times 180 = 90{,}000\ \text{B/s} \approx 90\ \text{KB/s}
\]
→ 클라이언트 단독으로는 감당 가능 구간.

**서버 총 egress 90MB/s**는 전역 대비 1/10이지만, **한 인스턴스 상시 비용·대역으로 여전히 무겁다.** 세로 분할·Hz 인하 전제 없이는 “가능” 판정 불가.

**몬스터 추가(같은 AOI 가정)**  
문서 보수 가정: 근처 움직이는 몹 10기/인, AI 3.33Hz, 전역 구독 시 \(≈33N^2\)(`GAME-SERVER.md:200-205`).  
AOI 후 fan-out을 구독자 \(N\)이 아니라 **해당 청크를 구독 중인 인원**으로 바꾸면, 집결 A=100 클러스터에서:

- 가정: 클러스터당 활성 몹 이동 \(M_{\text{move}}≈30\)기/틱(측정 필요), 틱 3.33Hz, 구독자 100  
- 클러스터 egress ≈ \(30 \times 3.33 \times 100 × S_m\), \(S_m≈90\)B → 약 **0.9MB/s/클러스터**  
- 클러스터 10개면 ~9MB/s. **전역 구독 대비 자릿수 개선**, 다만 몹 전역 구독 유지 시 문서의 30MB/s@N=100 수준이 다시 나타남.

**감당 판정**

| 구간 | 플레이어 egress | 판정 |
|---|---|---|
| 현재 전역, N=1000 | ~900MB/s | **불가** |
| AOI 100 + 5Hz + 180B 행 | ~90MB/s 총 | **경계·비권장**(비용·헤드룸 부족) |
| AOI 100 + 2Hz + pos≈50B | \(1000×2×100×50=10\)MB/s | **단일 인스턴스 현실 목표 구간** |
| 클라이언트 수신(위 조건) | 수십 KB/s | **가능** |

### 3.2 질문 2 — 구독 SQL 제약 안 AOI 구현

**제약(확인)**  
- `SELECT *`만 → 컬럼 일부 수신 불가 → **세로 분할이 유일한 대역 해법**  
- 산술/`x BETWEEN` 형태 좌표 범위 필터 부적합  
- JOIN ≤2 + 양측 인덱스  
- 인덱스 없는 필터는 전표 스캔·구독 비용 폭증

**현재 코드 갭**  
- 플레이어: chunk **없음** → `WHERE chunk = …` 구독 불가  
- 몬스터: chunk는 **home 기준**(`world.rs:414-418`) → 추격 중 실제 위치와 어긋날 수 있으나 leash 26타일 < 청크 32라 AI용으로는 타협됨. **구독 AOI용으로는 “현재 위치 청크” 컬럼이 더 정확**할 수 있음(이동 시 인덱스 갱신 비용 트레이드오프).

**권장 구현: ① 클라이언트 나열 청크 구독** (`GAME-SERVER.md:300-310`과 동일, 코드 반영 필요)

```sql
SELECT * FROM world_player_pos WHERE chunk = c0 OR chunk = c1 OR ... -- 최대 9개
SELECT * FROM monster_pos WHERE chunk = ...
```

- **AI 청크 32** vs **구독 청크 64~128 분리** 권고(`GAME-SERVER.md:310`):  
  - 구독 청크 \(C_s=64\): 9칸 ≈ 192×192 타일  
  - 구독 청크 \(C_s=128\): 9칸 ≈ 384×384  
  - AOI “다른 플레이어 100”은 **밀도 상한/표시 상한**으로 강제하는 편이 안전(공간만으로는 보스 집결 시 1000명 진입 가능).

**재구독 비용**

| 구독 청크 | 보행 3.6타일/s 직선 시 경계 교차 주기 | 비고 |
|---|---:|---|
| 32 | \(32/3.6≈8.9\)s | 재구독 잦음 |
| 64 | ≈17.8s | 균형 |
| 128 | ≈35.6s | 스냅샷 큼 |

재구독 1회 비용 ≈ **새로 들어오는 청크의 스냅샷 행 수 × 행 크기** (겹친 청크는 zero-copy, 공식 문서 “subscribe before unsubscribe”).  
예: 새 청크 1개에 플레이어 20 + 몹 40, pos 50B → 초기 전송 ~3KB + 적용 지연 1 RTT.  
**32타일 청크만 쓰면** 대각 이동·경계 진동 시 재구독이 수 초마다 겹칠 수 있음 → **구독용 64~128 + 히스테리시스(경계 안쪽에서만 전환)** 필요.

**RLS vs View**

| 방식 | AOI 적합성 | 근거 |
|---|---|---|
| 청크 OR 나열 | **주력** | 인덱스, 공유 region, 서버 per-user 계산 최소 |
| View (`AnonymousView`) | **부적합** | 파라미터 없는 공유 결과; “내 주변” 불가(`GAME-SERVER.md:320-324`) |
| View (`ViewContext` 사용자별) | 가능하나 N배 계산 | 1,000명=1,000번 |
| RLS `:sender` | 보안 보조만 | experimental, 조인 갱신 이슈(#2810), per-user |

### 3.3 질문 3 — 전역 락 아래 5,000 TPS `move_to`

**사실**  
- 단일 writer 락(공식/이슈 #2836).  
- `move_to` 자체는 가벼움: identity PK + 거리 + 1 row update(`world.rs:1044-1085`).  
- 벤치 ~3×10⁵ TPS는 **단순 트랜잭션** 참고치; fan-out·AI와 동시 측정 아님.

**예산 스케치(추정, 측정 전)**  
- AI 주기 300ms. AI가 \(T_{ai}\) ms 락 점유.  
- 남은 시간 비율 \(1 - T_{ai}/300\) 동안만 다른 reducer 처리.  
- 5,000 `move_to`/s → 300ms 창에 평균 1,500건.  
- AI=50ms면 250ms/1500 ≈ **0.17ms/건** 예산. 단순 update면 가능할 수 있음.  
- AI=150ms면 150ms/1500=0.1ms + 큐잉 지연 폭증.  
- **현재 AI는 N과 함께 폭주**(`world.rs:1479-1487`) → N=1000에서 \(T_{ai}\)가 예산 초과할 가능성이 큼 → **5,000 TPS “ alone 가능 / with AI 불가”** 가 정확한 표현.

**보고 주기를 얼마로**  
| R (Hz) | N=1000 시 move TPS | 비고 |
|---:|---:|---|
| 5 (현재) | 5,000 | 최악 전제 |
| 2 | 2,000 | 보간으로 화면 유지 가능(`remote_player.dart:18-20`이 0.2s 전제) |
| 1 | 1,000 | 의도 전송 없을 때 하한 후보 |
| 의도(출발+속도+t0) | 경로 변경 시만 | 직선 구간 TPS ≪ 1 |

권고: **AOI·AI 수정 후** 기본 2Hz, 근접 전투만 5Hz(서버가 거리를 알면 LOD 쓰기 가능). 측정 전 단정 금지.

**입력 배칭**  
- **다수 플레이어 → 한 reducer**: 클라이언트가 보내는 모델에서는 **불가**(sender 바인딩).  
- **한 플레이어 경로 압축**(waypoints[] 한 호출): 가능, TPS↓.  
- **서버 스케줄 리듀서에서 여러 행 update**: 몬스터 AI·일괄 이동에 해당; 플레이어 입력 큐를 표에 넣으면 insert TPS는 그대로.  
- 공식 Performance “Batch Operations”는 **한 reducer 안 다중 행**이지, 다중 클라이언트 호출 병합이 아님.

### 3.4 질문 4 — `monster_ai` 자료구조

**현재** (`world.rs:1428-1487`)  
1. 전체 생존 플레이어 Vec — \(O(N)\)  
2. 플레이어당 9청크 `by_chunk` — 근처 몹 집합  
3. 각 근처 몹 × **전체** 플레이어 최근접 — \(O(M_{\text{near}} \times N)\)

문서 수치: N=1000, \(M_{\text{near}}→7500\)이면 틱당 7.5M 거리, 초당 ~2.5×10⁷(`GAME-SERVER.md:222-226`).

**SpacetimeDB 제약**: 모듈 전역 메모리 공간 인덱스 유지 불가 → **매 틱 테이블에서 재구축**.

**권장 구조(틱 로컬만)**  
```text
by_chunk: HashMap<u32, Vec<&WorldPlayer>>   // O(N) 1회 구축
활성 청크 = 사람 있는 청크 ∪ 이웃
각 활성 청크의 몹(by_chunk 인덱스)에 대해
  후보 플레이어 = 자기+이웃 청크의 Vec만 순회
```

**비용(재구축 포함)**  
- 맵 구축: \(O(N)\) 참조 삽입. N=1000이면 무시 가능(μs~0.1ms 급 예상).  
- 거리 계산: \(O(M_{\text{active}} \times P_{\text{local}})\).  
  - 산개: \(P_{\text{local}}≈1\sim5\), \(M_{\text{active}}\) 수백 → 틱당 수천 회.  
  - AOI 목표 집결: \(P_{\text{local}}≈100\), \(M_{\text{active}}≈100\sim300\) → 틱당 1~3×10⁴ 회 ≪ 7.5×10⁶.  
  - **전원이 한 9청크에 1000명**: 여전히 \(M_{\text{local}}×1000\). 표시 AOI 100과 별개로 AI는 전원 반응 → **핫스팟 상한/비활성 AI 계층** 필요.

**추가**  
- 무인 청크 스킵(`GAME-SERVER.md:268`)  
- 이동 없는 몹 `update` 금지(구독 스팸)  
- 거리 LOD: 근접 3.33Hz / 원거리 1Hz / 무인 0

### 3.5 질문 5 — 기법별 절감량(수치 비교)

기준: **AOI 100 + N=1000 + 전원 5Hz 이동**의 플레이어 좌표 egress  
\(B_0 = 5\times10^5 \times 180 = 90\) MB/s.

| 기법 | 가정 | 대략 결과 | \(B_0\) 대비 |
|---|---|---|---:|
| **AOI 구독**(전역→A=100) | fan-out N→A | 500만→50만 행/s | **÷10** (전역 900MB 대비 ÷10; 이미 AOI면 1×) |
| **세로 분할** | 좌표행 ~50B (id+xy+chunk+ts) | 90→**25** MB/s | **÷3.6** |
| **f32→i16 격자** | xy 8B→4B, 행~46B | ~23 MB/s | 추가 **~10%** (분할 후) |
| **의도 전송** | 방향 유지 시 0.2~1Hz 갱신 | 5Hz→0.5Hz면 **÷10** | 경로 재계산 잦으면 이득↓ |
| **LOD 5Hz/1Hz** | 가까운 20명 5Hz, 먼 80명 1Hz | 유효 \(R_{avg}=(20×5+80×1)/100=1.8\)Hz | **÷2.8** vs 5Hz |
| **보고 2Hz 전역** | R=2 | 행 수 ÷2.5 | **÷2.5** |
| **조합** AOI+분할+2Hz | 1000×2×100×50 | **10 MB/s** | **÷9** vs AOI-only 90MB |
| **조합** +LOD+의도 | 실효 R~1, 일부 의도 | **수 MB/s** | 목표 운용 구간 |

**주의**: LOD를 **구독 SQL만**으로 주파수 분리 불가. 서버가 먼 플레이어 행을 덜 `update`하거나 별도 `world_player_pos_lod` 테이블을 써야 함. 클라이언트 드롭은 서버 egress를 줄이지 않음.

### 3.6 질문 6 — 우선순위 변경 목록과 “끝내 불가” 지점

| 순위 | 변경 | 예상 효과(배수) | 조건 |
|---:|---|---|---|
| 1 | 전역 구독 제거 + 청크 AOI 구독 + `WorldPlayer.chunk`(+index) | egress **÷N/A ≈ ÷10@N=1000,A=100** | 필수. 없으면 나머지 무의미 |
| 2 | 테이블 세로 분할 (Pos / Meta / Vitals) | 행 크기 **÷3~4** | 구독 `SELECT *` 제약 대응 |
| 3 | `monster_ai` 청크 버킷 + 무인 스킵 + no-op update 제거 | AI CPU **÷10~100**(분포 의존) | 전역 락 예산 회복의 핵심 |
| 4 | 좌표 보고 5Hz→2Hz(또는 의도) | TPS·egress **÷2.5~10** | 보간 유지(`remote_player`) |
| 5 | 구독 청크 64~128 + 히스테리시스 | 재구독 빈도 **÷2~4** | AI 청크와 분리 검토 |
| 6 | 표시 상한 100 + 원거리 LOD 쓰기 | 집결 최악 **상한 고정** | 기획 합의 |
| 7 | CombatEvent 분리(삽입 후 지연 삭제) | 연출 대역 통제 | 같은 트랜잭션 insert+delete 함정(`GAME-SERVER.md:280`) |

**SpacetimeDB로 끝내 타협해야 하는 지점**  
1. **단일 DB·무수평 확장** — 월드 샤딩은 직접 구현, 플랫폼 미제공.  
2. **쓰기 전역 직렬화** — 존 병렬 틱으로 처리량 N배 불가.  
3. **구독으로 “내 주변 반경 R” 한 줄 표현 불가** — 청크 이산화 필수.  
4. **행 부분 프로젝션 불가** — 세로 분할 강제.  
5. **상주 spatial hash/navmesh 메모리 불가** — 매 틱 재구축 또는 테이블 인덱스.  
6. **AOI 999(전원 상호 가시 1,000)** — 네트워크·락 동시 불가; **AOI 100이 기획 상한**이어야 함.  
7. **검증 없는 “1,000 가능” 단정 불가** — 봇 부하 테스트 필수(`GAME-SERVER.md:341-350`).

**목표 달성 정의(명시)**  
- 동접 1,000 **산개 또는 다수 지역** + **지역당 가시 ≤100** + 위 1~4 적용 + AI \(T_{ai}<50\)ms p95 + 총 egress 수 MB/s대 → **설계상 도달 가능 구간**.  
- 동접 1,000이 **한 점 집결·전원 5Hz·전체 행 구독** → **불가**.

## 4. 리스크 · 함정

- **문서 vs 코드**: `GAME-SERVER.md`는 AOI·세로 분할·AI 수정을 권고하지만, 코드는 여전히 전역 구독·chunk 없는 `WorldPlayer`·O(N) 타겟 루프. 문서만 읽고 “이미 설계됨”으로 오해하기 쉬움.  
- **재구독 깜빡임**: unsubscribe 먼저 하면 화면 공백. 반드시 신규 subscribe 후 해제(공식 권고).  
- **home-chunk 몬스터**: 추격 중 실제 그리드와 구독 청크 불일치 가능(roam 26 < 32라 완화되나 구독 청크를 키우면 상대적 오차 감소).  
- **변화 없는 update**: 전체 행 재전송 + 전 구독자 fan-out. regen은 이미 회피(`world.rs:1615-1616`); move/AI도 동일 원칙 필요.  
- **이벤트 insert+delete 동일 트랜잭션**: 클라이언트 미전달(`GAME-SERVER.md:280`).  
- **Maincloud egress 과금**: 90MB/s급은 기술 문제이자 비용 문제(`GAME-SERVER.md:192`).  
- **측정 부재**: 행 크기 180B, AI ms, 실 TPS는 전부 추정; 자릿수는 안정, 계수는 ±2배 가능.  
- **보안**: 청크 구독만 하면 치트 클라이언트가 전역 SQL을 걸 수 있음 → 나중에 private+RLS/뷰로 봉인 검토.  
- **“문서 업데이트” 요청**: 본 분석은 읽기 전용; 파일 수정은 하지 않음(§5에 반영 위치만).

## 6. 불확실 · 미확인

- **실측 없는 값**: BSATN+WebSocket 프레임 포함 실제 바이트/행; `move_to` p50/p99 ms; `monster_ai` 벽시계 ms @ N=10/100/1000.  
- **Identity 인코딩 길이** 및 bool 패딩 — 행 크기 ±20B.  
- **Maincloud 플랜별 egress·CPU 한도** — 공개 요금 페이지 수준만 참조, 계약 한도 미확인.  
- **동접 1,000이 산개일 때의 평균 AOI 인원** — 목표 100은 최악 집결 스펙인지 평균인지 기획 확인 필요.  
- **플레이어 실제 이동 비율**(정지·`_minStep`) — 5Hz 전제 최악 대비 실트래픽 배수.  
- **구독 쿼리당 OR 청크 개수 상한** — 문서에 하드 캡 명시 못 봄; 9~25개 실용성 실험 필요.  
- **RLS 안정화 시점** — experimental 상태 지속 여부.  
- **BitCraft 부하 프로파일**과의 유사성 — 사례는 존재하나 우리 7,500몹·5Hz 좌표와 동일하지 않음.

**결정적 실험(가설 1 vs 2 가르개)**  
1. N=100 전역 구독 egress 측정 → \(5N^2×S\) 검증.  
2. 동일 N에서 AI 틱 시간만 프로브 → 락 점유.  
3. 청크 구독 프로토타입 후 N=200에서 총 egress가 N이 아니라 A에 비례하는지 확인.
