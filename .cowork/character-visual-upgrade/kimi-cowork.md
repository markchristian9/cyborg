## 1. 결론 요약

  - **"256 방향" 요구는 기술적으로 충족됐다.** `yaw` 가 연속 실수라 양자화가 없으며(`player.dart:833` → `cyborg_renderer.dart:57`), `quantizeYaw()` 는 정의만 있고 호출처가 없다(`iso.dart:118`). 다만 사람 눈이 이 크기에서 구분하는 한계는 대략 32~64 방향이라, "부드럽게 돈다"는 목적은 이미 달성됐고 256이라는 숫자 자체는 의미가 없다.
  - **회전이 실제로 무너지는 지점이 두 군데 있다.** 포니테일이 항상 화면 왼쪽으로만 휘어 좌측면 뷰에서 얼굴을 덮고(`cyborg_renderer.dart:720-734`), 헬멧 안테나는 깊이 검사 없이 항상 그려져 뒤통수 방향에서 관통한다(`cyborg_renderer.dart:690-700`).
  - **클릭 이동은 단거리(화면 내)에서 정상 동작하며 입력 우선순위도 올바르다.** 그러나 경로 탐색이 없어 벽 너머 클릭은 0.35초 만에 포기되고, 적을 탭하면 공격이 아니라 적 안으로 걸어 들어가며, 탭 처리자가 없는 HUD 패널 위의 탭은 월드로 새어 나간다.

## 3. 상세 분석

  ### 3.1 "256 방향" 판정 — 충족, 그리고 상한은 사람의 눈

  `yaw` 는 `facing()` 그리드 벡터에서 `atan2` 로 구한 연속 실수다(`iso.dart:108`). 양자화가 없으므로 256방향을 "지원"하는 게 아니라 **개념적으로 무한 방향**이며, 회전 중 계단 현상은 생길 수 없다. 이 부분의 1차 구현 주장은 사실이다.

  다만 체감 상한을 수치로 따져 보면: 남성형 가슴 반폭 `a = 11.5px`, 깊이 반폭 `b = a × 0.62 ≈ 7.1px`(`cyborg_renderer.dart:33, 817-821`). 투영 폭의 최대 변화율은 약 4.2px/rad(45° 부근)라, 폭 변화만으로는 1px 임계 기준 180°당 15~20단계다. 여기에 바이저·코어·사지의 x 이동(수 px 범위)이 합쳐져도 **110px 높이에서 32~64방향, 59px(최소 줌)에서는 16~32방향**이 구분 한계다 [수치 추정 — 코드의 치수에서 계산, 실측 아님]. 즉 연속 회전은 이미 지각 한계를 넘어섰고, 남은 문제는 "방향 수"가 아니라 "각 방향에서 그림이 망가지지 않는가"다.

  ### 3.2 회전이 무너지는 구체 지점

  - **포니테일(여성형)** — 고정점은 뒤통수(둘레각 π)로 올바르게 회전하지만, 휘는 방향 벡터가 `p.x - spread*1.4` 로 화면 왼쪽에 하드코딩돼 있다(`cyborg_renderer.dart:722-728`). 우측면(`yaw ≈ +π/2`)에서는 자연스럽지만 좌측면(`yaw ≈ -π/2`)에서는 고정점이 머리 오른쪽인데 머리채가 왼쪽으로 휘어 **헬멧을 가로질러 얼굴 쪽으로 넘어간다.** `visible` 값의 부호로 휘는 방향을 반전시키면 되는 구조다.
  - **안테나** — 깊이 검사 없이 항상 최상위에 그려진다(`cyborg_renderer.dart:690-700`). 대뇌피질 모듈은 `depth > -headR * 0.3` 조건이 있는데(`:673`) 안테나만 없다. 좌 관자놀이가 원측으로 넘어가는 yaw 구간(대략 후면 ±45°)에서 헬멧 뒤를 관통해 보인다.
  - **측면 뷰의 사지 겹침** — 팔·다리의 둘레각이 ±π/2 고정이라 `yaw = ±π/2`에서 양쪽의 화면 x 가 모두 0으로 수렴해 완전히 겹친다(`:122-128, 483-485`). 깊이 정렬로 앞쪽만 보이므로 측면 대기 자세는 다리 1개·팔 1개짜리 기둥이 된다. 타원기둥 근사의 구조적 한계이며, 측면에서 둘레각을 살짝 벌려 주는 보정(예: ±π/2 ± 0.15)으로 완화 가능하다.
  - **광원이 몸에 붙어 회전** — 흉갑 하이라이트가 몸통 둘레각 -0.6 rad 에 고정(`:245`)이라 캐릭터가 돌면 빛도 같이 돈다. 월드 광원은 고정(좌상단)이어야 하므로, 후면으로 돌 때 하이라이트가 사라지는 현재 동작은 결과적으로는 자연스럽지만, 측면 전이 중 광원이 몸을 따라 미끄러지는 어색함이 있다 [판단].
  - **적과의 불일치** — 플레이어만 연속 회전하고 적은 2값 반전(`enemy.dart:412`)이라, 같은 화면에서 회전 품질 격차가 눈에 띈다.

  ### 3.3 비주얼 — "화려함"의 분포가 치우쳐 있다

  발광 장치 자체는 풍부하다: 3겹 코어+방열 링(`:306-341`), 몸통·헬멧 림 라이트, 바이저 주사선, 부츠 밑창, 척추 레일, `time` 맥동(`:70`). 그러나:

  - **음영이 없다.** 장갑이 `armorBase`/`armorLight` 2톤 평면 채색이라 입체감을 전부 발광에 의존한다. 다리(`:139-145`)와 팔(`:514-520`)은 단색 채우기 하나뿐이라 밝은 배경 위에서 "짙은 판때기"로 읽힌다. 32~64px 에서 살아남는 개선은 글로우 추가가 아니라 **부위당 2톤 명암(빛 면/그늘 면 분할)과 실루엣 마디(무릎·발목·팔꿈치의 폭 변화)** 다 — 지금 다리는 골반→발목이 직선 테이퍼라 관절이 없다.
  - **식별성 부재(MMORPG 관점).** 두 프레임의 색이 완전히 같아(`cyborg_design.dart:159-163 ≡ 199-203`) 30인이 모이면 실루엣 2종 × 같은 색의 복제품이 된다. 진영색 통일 의도(주석 `:196-198`)는 유효하므로, accent 는 유지하되 플레이어별 **보조 색조(바이저 색상 틴트나 림 라이트 색 편차)나 이름표 색**으로 개체를 구분하는 축이 필요하다.
  - **맥동이 정체 상태에서 유일한 생명감** — 대기 모션이 호흡 bob 1.2px(`player.dart:821`)뿐이라, 화려함의 시간 축이 빈약하다 [판단].
  - 최소 줌(0.55)에서 림 라이트 1.4px → 0.77px 로 서브픽셀이 되어 소멸한다. 축소 내성을 원하면 림 라이트는 줌과 무관하게 최소 1px 실효 폭이 필요하다.

  ### 3.4 클릭 이동 — 설계는 올바르고, 경계 조건이 남았다

  - **우선순위는 정확하다.** 키보드+조이스틱이 `_applyInput` 으로 합성되고(`action_rpg_game.dart:391-409`), `moveInput` 이 있으면 클릭 목표를 버린다(`player.dart:260-263`). 뷰포트 UI 가 먼저 탭을 가져가는 구조(`click_move.dart:14-21`)도 맞다.
  - **직선 이동의 유효 범위**: 탭은 뷰포트 안에서만 발생하므로 목표 거리는 기껏해야 화면 폭(줌 1 기준 세로 760px ≈ 대각 10~15타일). 이 거리에서는 경로 탐색 없이도 대부분 도달한다. 문제는 **벽 너머를 찍는 경우** — `nearestWalkable` 이 최대 24타일 떨어진 곳으로 보정해(`level_map.dart:200`) 캐릭터가 벽 반대편의 엉뚱한 지점을 향해 걷다가 0.35초 후 멈춘다. 1km 월드 자체는 미니맵 클릭이 없으므로 직접적인 문제는 아니다.
  - **적을 탭하면 적 안으로 걸어 들어간다.** 적은 탭 처리자가 아니므로 탭이 그대로 바닥으로 뚫린다. 근접 접근으로는 쓸 만하지만 공격은 안 나가고, 원거리 적에게는 자살 돌진이 된다. PK 가 열리면 "플레이어를 탭 = 그 플레이어에게 걸어감" 이라 더 위험하다.
  - **HUD 누수**: `Hud` 를 포함한 표시 전용 뷰포트 컴포넌트는 `TapCallbacks` 가 아니라서(Grep 확인), 그 위의 탭이 `ClickMoveLayer` 까지 내려간다. 체력바·버프바 영역을 터치하면 캐릭터가 움직인다. 메뉴·스크림은 처리자가 있어 막힌다(`world_menu.dart:447`).
  - **드래그 미지원**: `onTapDown` 만 처리해 손가락을 누른 채 움직여도 목표가 갱신되지 않는다. PK 추격처럼 목표를 연속 수정해야 하는 상황에서 반복 탭을 강요한다.
  - 세부 결함 하나: 도착 감속 구간(0.6타일 이내)에서 속도가 `arrive` 비례로 떨어지는데, 끼임 판정 임계가 `effectiveMoveSpeed * dt * 0.25`(`player.dart:291`)라 목표 0.15타일 부근에서 정상 도착 직전에도 "끼임"으로 오인될 여지가 있다. 실제로는 0.18타일에서 먼저 멈추므로(`:305`) 발동 여백이 종이 한 장이다.

  ### 3.5 성능 — 1인은 여유, 30인은 블러가 문제다

  캐릭터 1인당 캔버스 오퍼레이션 약 45~50회(섹션별 그리기 호출 합산), 그중 `MaskFilter.blur` 가 5~6회다. 블러는 Impeller/Skia 에서 오프스크린 패스를 유발하는 가장 비싼 연산이다 [추측 — 정확한 ms 는 실기기 프로파일 필요].

  - 1인: 50 ops + 블러 5회 → 프레임 예산(16.6ms) 안에 충분.
  - 30인: 약 1,500 ops + **블러 150회 이상/프레임**. 여기에 버프 오라 블러(`player.dart:771`), 대시 잔상 `saveLayer`(`:793`), 블레이드 스윙 블러 ×2(`:858, 878`)가 얹힌다. 중급 모바일에서 프레임 예산 초과가 거의 확실하다 [추측].
  - `quantizeYaw()` 가 준비돼 있지만(`iso.dart:118`) 미사용이라 캐시 경로가 없다. 런타임 `Picture`/`Image` 캐시를 쓴다면 메모리 추정: 캐릭터 1장 ≈ 120×130px, devicePixelRatio 3 기준 래스터 약 360×390×4B ≈ **0.55MB/장**. 32방향 × 2프레임 × 보행 4상 = 256장 ≈ **140MB** — 전면 캐시는 비현실적. 16방향 × 2프레임 × 정지 1상 = 32장 ≈ **18MB** 정도가 상한이고, 보행은 몸통 캐시 + 사지 라이브 합성이 현실적이다. 워밍업은 32장 × 약 1~2ms [추측] ≈ 수십 ms 로 스폰 시 한 프레임 히치 가능.

  

## 4. 리스크 · 함정

  - **포니테일 좌우 비대칭은 스냅샷으로 못 잡는다.** 현재 스냅샷이 0°~315° 정방향만 뽑아(`cyborg_render_snapshot_test.dart:79-86`) 음수 yaw(좌측면) 결함을 놓칠 수 있다 — 사실 이 셋이면 ±가 섞이지만, 사람이 8장을 눈으로 훑어야 발견된다.
  - **블러 제거/캐시 도입 시 그림이 달라진다.** `MaskFilter.blur` 를 그래디언트 원으로 바꾸면 발광 질감이 변하므로, 팔레트·디자인 SSOT(`cyborg_design.dart`) 와 스냅샷 비교 없이 바꾸면 "화려함"이 후퇴할 수 있다.
  - **`nearestWalkable` 보정은 침묵 실패다.** 클릭 지점이 보정돼도 사용자에게 알리지 않아(표식이 보정된 위치에 찍힐 뿐, `action_rpg_game.dart:692-694`) "왜 거기로 가지"라는 혼란이 생긴다.
  - **PK 가 열리는 순간 클릭 이동의 약점이 전투 약점이 된다.** 도주 중 탭 실수 = 적진으로 돌진, 적 탭 = 돌진. "공격 의도 탭"과 "이동 의도 탭"의 구분이 지금 설계에는 없다.
  - **30인 시나리오는 아직 검증 불가.** 원격 플레이어 클래스 자체가 없으므로(멀티 동기화 미구현), 렌더러의 다인 비용은 추정일 뿐 실측이 불가능하다. 지금 블러를 손보지 않으면 동기화가 들어오는 시점에 성능 공사와 동기화 공사가 겹친다.
  - **외형 SSOT 는 현재 깨진 곳이 없다.** 건드릴 때 `cyborg_portrait.dart`·`cyborg_preview.dart`·`player.dart` 세 표면이 동시에 바뀌어야 한다는 제약만 유지하면 된다.

## 6. 불확실 · 미확인

  - **블러의 실제 프레임 비용(ms)은 미실측** — 30인 시나리오는 원격 플레이어가 없어 재현 불가. 실기기 프로파일(Impeller 타임라인)이 필요하다.
  - **사람 눈의 방향 구분 한계(32~64)는 코드 치수에서의 계산값**이지 실험값이 아니다. 스냅샷을 5.625°(64방향) 간격으로 뽑아 육안 확인하면 확정 가능하다.
  - `Hud` 내부 구성(패널 크기·배치)은 읽지 않았다 — 탭 누수가 실제로 불편한지는 HUD 면적에 따라 달라진다.
  - `GAME-DESIGN.md` 전체와 `CLAUDE.md` 의 세부 지침은 헤더만 확인했다. 비주얼 방향성에 대한 추가 합의(예: 남/여 색 분리 의사)가 문서 후반에 있을 수 있다.
  - 포니테일 좌측면 덮침은 코드상 명백하나, 실제 렌더에서 얼마나 눈에 띄는지는 스냅샷 육안 확인이 필요하다(분석 중 파일이 다른 세션에 의해 변경될 수 있음 — 인용은 읽은 시점 기준).
