## 1. 결론 요약

1차 구현은 **요구 3종의 골격은 들어갔지만 “완료”로 보기 어렵다.**  
**방향**: 각도는 연속 실수라 256을 수치상 넘지만, 몸통 폭·부위 depth 투영 위주의 2D 근사라 정면↔측면↔후면 전이에서 팔·머리·포니테일·무기가 판때기처럼 읽힌다. 사람이 원한 “촘촘히 부드럽게 돈다”는 **절반만** 달성.  
**클릭 이동**: 직선+슬라이딩+막힘 포기+표식/안내선까지 구현됐고 WASD/조이스틱보다 우선순위가 낮다(수동 입력이 이김). 다만 **적/PC 탭=이동**, 경로 탐색 없음, 1km 원거리 우회 불가.  
**비주얼**: VULCAN/WRAITH 골격·임플란트 차이와 림/코어 발광은 있으나, 색이 동일하고 관절 마디·소형(줌 다운) 실루엣이 약해 “더 예쁘고 화려” 요구의 **1차 기반** 수준.  
**치명 불일치**: 선택 화면은 남/여를 그리지만 인게임 `_spawnPlayer`는 항상 기본 `assault` — 여성 출격이 몸통에 반영되지 않는다.

## 3. 상세 분석

### 3.1 범위

| 요구 | 상태 | 경계 |
|---|---|---|
| 남/여 더 멋있게 | 1차 디테일 레이어 존재, “화려/예쁨”은 미달 | 아트 방향 + `CyborgDesign`/`CyborgRenderer` |
| 클릭 이동 | 구현됨, 경로탐색·타겟 탭 없음 | `click_move` + `Player` 이동 + 게임 API |
| 256방향 | **각도 입력 충족 / 시각 충실 부분 충족** | 렌더 근사 모델; 캐시 양자화는 미도입 |

멀티플레이 동기화 없음(프로젝트 전제). 그래도 렌더 비용은 **화면 30명** 기준으로 평가.

### 3.2 방향 — “256” 판정

**사실(코드)**  
- 입력: `facing` 벡터 → `facingYaw` → `drawBody(yaw:)` 실수. 양자화 단계 없음.  
- 기하: 부위를 타원 둘레 매개각 `t`에 두고 `R_yaw`로 투영. 팔·다리·어깨는 depth 정렬 후 그림.  
- `quantizeYaw`는 “캐시하려면 이산화” 주석만 있고 **현재 파이프에서 미사용**.

**목적 대비 해석**  
사람이 원한 것은 숫자 256이 아니라 **회전 시 계단 없는 부드러움**이다.

| 층 | 연속성 | 판정 |
|---|---|---|
| 각도 샘플링 | 무한(실수) | 256 이상 **충족** |
| 몸통 실루엣 폭 | `halfWidth`가 yaw에 연속 변화 | 측면 얇아짐 **동작** |
| 부위 가시성 | `depth>0` 게이트(바이저·코어·등팩) | 앞/뒤 전환 **동작** |
| 부위 **형태** | 헬멧/팔/다리가 자체 3D 메시가 아님 | 전이 구간에서 **판때기감** |

**사람 눈이 구분하는 방향 수** (스프라이트 경험칙, 본 저장소 실측 아님 → `[추측]`):  
8=명백한 계단, 16=대부분 허용, 32~64=연속 착시, 256은 아틀라스 캐시 밀도용.  
**즉시 모드 연속 드로잉**이면 각도 밀도 문제는 이미 해결; 남는 문제는 **근사 모델의 형태 충실도**.

**회전이 어색해지는 구체 부위**

1. **머리/헬멧** — RRect가 항상 원점 중심, 폭만 `headWidthScale`로 변함. 측면에서도 “정면 헬멧 도형”. 바이저만 `project(0)`으로 x 이동.  
2. **팔** — 비무기 팔은 세로 RRect; yaw에 따른 어깨 관절 각도 없음. 무기 팔은 `lean ∝ sin(yaw)` 정도.  
3. **다리** — 보폭이 주로 화면 y, 측면일 때만 x로 흘림. 무릎 관절 없음 → 옆걸음이 종이인형.  
4. **포니테일** — 뒤통수 투영은 있으나 곡선이 항상 `p.x - spread` 쪽으로 치우침(`703-734`). 좌/우 측면 대칭 깨짐.  
5. **등 블레이드** — `depth<=0`이면 통째 생략; 측면 전이에서 툭 사라짐.  
6. **안테나** — 항상 왼쪽 앵커(`-π/2`); 후면에서도 같은 규칙.

**가설 1만으로 “끝”이라고 하면 틀림. 가설 2를 함께 써야 정확하다.**

### 3.3 비주얼 — “화려하다”고 할 수 있는가

**이미 있는 강점(코드 확인)**  
- 밝은 배경 전제에 맞춘 짙은 장갑 + accent 림(`palette` + `_deepShade`).  
- 코어 3겹+링, 바이저 블러+주사선, 부츠 발광, `time` 맥동(인게임).  
- 남/여 **골격·임플란트·헤어** 차등(어깨/허리/포니테일 vs 동력팩·흉골).

**부족(화려함을 장식이 아닌 읽힘으로 번역)**  

| 문제 | 32~64px에서 | 근거 |
|---|---|---|
| 남/여 색 동일 | 원거리 식별은 실루엣만 | `cyborg_design` accent 동일(의도 주석 있음) |
| 관절 마디 약함 | 팔·다리가 막대로 붕괴 | 단일 path/RRect |
| 무기 실루엣 빈약 | 홀스터 3px 막대 | `_drawHolsteredBlade` |
| 포니테일/케이블이 작은 스케일에서 노이즈 | 1.2px 스트로크 | 스트로크 두께 고정 |
| 프리뷰/초상이 `time` 미전달 | 코어 pulse 정지 | portrait `drawBody`에 time 없음 |

발광을 더 얹는 것은 blur 비용을 키울 뿐, **어깨-허리-골반 대비 강화·무릎/손 하이라이트 1px·측면 실루엣 프로파일**이 소형 스케일에서 이득이 크다.

줌 0.55에서 본체 높이 ≈ \(108 × 0.55 ≈ 59\)px → “32~64px 생존”이 실전 조건.

### 3.4 클릭 이동

**동작 흐름**  
탭(월드 최하층) → `movePlayerToWorldPoint` → `nearestWalkable`(반경 24) → `moveTo` → 매 프레임 `_steerToTarget` 직선 속도 → 충돌 슬라이딩 → 진행 없으면 0.35s 후 포기.  
수동 입력 시 목표 즉시 취소. 조이스틱/액션 버튼은 **viewport**라 월드 탭보다 먼저 소비(설계 의도 주석과 일치).

**실전 깨짐 지점**

| 상황 | 결과 |
|---|---|
| 벽 너머 목적지 | 미끄러지다 stuck → 포기. 우회 경로 없음 |
| 1km 원거리 탭 | 속도 3.6타일/s → 이론상 수분 직진; 장애물 밀집 시 중도 포기 |
| 적/파괴물 탭 | `TapCallbacks` 없음 → **그 좌표로 걸어감**(공격 타겟팅 없음) |
| PK(다른 PC) | 동기화 전제이지만, 탭=이동이면 “클릭 공격” UX와 충돌 `[설계 공백]` |
| 긴 `MovePathHint` | 거리/14 점선 루프; 수 km급 화면 거리는 드묾(카메라 추종) |
| UI 시트 열림 | 시트들이 `event.handled` — 겹침은 대체로 안전 |

1km 월드에서 **로컬 내비(시야 안 포인트 앤 클릭)** 로는 통한다. **장거리 오토패스**로는 통하지 않는다.

### 3.5 성능 (수치 추정 — 프로파일 실측 아님)

한 캐릭터 `drawBody` 대략:

- 도형 호출: ~40~55회(임플란트 분기 포함; `drawPath/Circle/RRect/Line` 기준 계수).
- `MaskFilter.blur`: 정면 assault ≈ **부츠2 + 코어2 + 바이저1 = 5**, + 그림자 1 → **~6**; infiltrator 등 레일 시 +1.
- `clipPath`/`clipRRect`: 흉갑 하이라이트·바이저 주사선(정면).
- `saveLayer`: 본체엔 거의 없음(대시 고스트·비선택 초상에서 사용).

| 규모 | blur 횟수/프레임 | 거친 예산 `[추측]` |
|---|---|---|
| 1명 | ~6 | 0.3~1.5 ms (데스크톱), 모바일 상위 |
| 30명 | ~180 + 도형 1200+ | blur만으로 수~십수 ms 가능 → **60fps 위험** |
| 적 140 활성 상한과 합치면 | 적 자체 blur도 다수 | 캐릭터 고급화와 충돌 |

`Picture`/`Image` 캐시 제안 시 메모리(대략, 70×120 RGBA ≈ 33.6 KB/장):

| 구성 | 장수 | 메모리 |
|---|---|---|
| 32방향 × 4보행 × 2프레임 | 256 | ~8.6 MB |
| 64 × 4 × 2 | 512 | ~17 MB |
| 256 × 8 × 2 | 4096 | ~138 MB (+워밍업 CPU) |

**권장 캐시 밀도는 32~64방향.** 256 아틀라스는 이 프로젝트 규모에서 과하다. 연속 드로잉을 유지하되 **LOD: 근접만 full blur, 원거리는 평탄 색+림 1획**이 30명 예산에 맞다.

### 3.6 SSOT / 문서

- 렌더 SSOT(`CyborgDesign` + `CyborgRenderer`)는 선택·프리뷰·Player 그리기 경로에서 **코드상 통일**.
- **데이터 파이프**는 끊김: `PlayerCharacter.kind` → `CyborgKind.design`이 `Player(...)`에 안 들어감. 문서 `GAME-DESIGN.md:123-126` “어긋날 수 없다”와 **실제 불일치**.
- `GAME-DESIGN.md:4.3`은 구 8방향 모델 서술; 클릭 이동도 조작표에 없음.

## 4. 리스크 · 함정

- **선택 여성 → 인게임 남성 몸**: 사용자가 “비주얼 개선이 안 됐다”고 느끼는 1순위 원인 가능.
- **blur 중첩 추가 = 30인 프레임 붕괴**: “화려함”을 glow로만 해결하면 MMORPG 전제와 충돌.
- **직선 클릭 이동 UX 기대 불일치**: Diablo식 오토패스를 기대하면 벽에서 멈춤이 버그로 보임.
- **탭 의미 단일화**: 모든 월드 탭=이동이라 향후 클릭 전투·루팅과 충돌.
- **문서/테스트 드리프트**: GAME-DESIGN 구모델; 스냅샷은 8방위뿐이라 45° 중간 각도 회귀 감지 약함.
- **적 2방향 vs 플레이어 연속**: 같은 화면에 이질감; 다만 플레이어 개선 범위 밖일 수 있음.
- **SSOT 깨기 유혹**: `player`에 다시 `_renderBody`를 넣으면 1차 통일이 후퇴.

## 6. 불확실 · 미확인

- **실기기 프레임 타임**: blur/ms는 추정. `flutter run`+DevTools Timeline 실측 없음(읽기 전용·실행 금지 분석).
- **Flame 탭 히트 테스트 세부**: 월드 위 `IsoEntity`가 size 없이 이벤트를 가로채는지 런타임 미확인. 코드상 `TapCallbacks`는 UI·ClickMoveLayer 위주.
- **온라인 캐릭터 kind 필드 실값**: 서버 `player_character.kind`와 클라이언트 연동은 생성 경로만 확인; 실제 DB 샘플 미확인.
- **사람 눈 방향 구분 한계**: 문헌/실측 없이 `[추측]`; 이 프로젝트 스냅샷으로 블라인드 비교하면 판정 가능.
- **PK·다른 플레이어 엔티티**: 실시간 멀티 미구현이라 탭-PK 상호작용은 설계 공백.
- **다른 세션의 동시 편집**: 분석 중 파일이 바뀌었을 수 있음 — 인용은 본 턴에서 읽은 내용 기준.

**살아남은 이중 결론(억지 단일화 안 함)**  
- (A) 각도 파이프는 이미 “256+ 연속”이다.  
- (B) 시각 모델은 아직 “연속 각을 먹는 8~16감 빌보드”에 가깝다.  
결정적 증거: 동일 `yaw` 미세 변화 PNG 시퀀스에서 팔/머리 윤곽이 부드럽게 변형되는가 vs 폭·가시성 플래그만 바뀌는가 — 스냅샷 확장으로 가르면 된다.
