# cowork 시스템 프롬프트 — Cyborg (actionrpg)

> 🛑 이 파일은 `cowork` 이 claude·codex·grok·kimi **네 AI 에게 분석을 시킬 때마다 프롬프트 맨 앞에
> 반드시 주입** 하는 **이 프로젝트의 시스템 프롬프트** 다.
>
> ⚠️ 네 AI 는 읽기 전용이다. 이 문서에 "파일을 고쳐라" 같은 지시를 써도 물리적으로 실행되지 않는다
> (실제 수정은 종합(final-report.md)을 마친 오케스트레이터가 한다).

## Overview

**Cyborg** — Flutter + Flame 으로 만드는 2.5D 아이소메트릭 액션 RPG **MMORPG** 다.
세계관은 "AI 로봇이 점령한 세계를 인간 사이보그가 되찾는다".

핵심 전제:

- **단일 공유 월드.** 매치별 인스턴스도, 분리된 스테이지도 없다. 플레이어는 세션이 아니라 **월드에
  접속한다.** 여러 사용자가 같은 월드에서 동시에 사냥하고, 서로의 존재·이동·전투가 실시간으로 보인다.
  PK 가 허용된다.
- 백엔드는 **SpacetimeDB**(Rust 모듈, maincloud 의 `withcenter-cyborg`). 게임 서버 계층이 따로 없고
  DB 안에서 reducer·view 가 돈다.
- 현재 단계: 계정·캐릭터 선택 관문(`lib/auth/`)이 붙었고, 싱글 플레이 수준의 전투 루프
  (웨이브·레벨업·인벤토리·안전지대)가 돌아간다. **실시간 멀티플레이 동기화는 아직 없다.**
  방금 **레벨 리더보드**(전역 순위표)가 서버·클라이언트 양쪽에 추가되어 maincloud 에 배포됐다.

이번 분석에서 네 AI 에게 시키려는 것: **플레이어 HP 와 몬스터 피해량 체계를 다시 설계하는 것.**
사람이 요구한 목표 규격은 다음과 같다.

- 플레이어 **기본 HP 를 10,000** 으로 크게 키운다(현재 120).
- 플레이어에게 **방어력(defense)** 개념을 두고 **기본값은 0** 이다.
- **몬스터에 레벨을 부여**하고, 방어력 0 인 플레이어가 맞을 때 실제로 들어오는 피해가
  **그 몬스터의 레벨과 같은 수치**가 되게 한다 — 3레벨 몬스터는 3, 10레벨 몬스터는 10.
- HP 10,000 이 모두 소진되면 사망한다(사망 시 안전지대 즉시 리스폰은 이미 구현돼 있다).

⚠️ 전제 사실: 현재 코드에는 **몬스터 레벨이라는 개념 자체가 없고**(종류 4종 `EnemyKind` × 맵 중심
으로부터의 거리 기반 배율), **플레이어 방어력 스탯도 없다**(버프의 `damageTakenMultiplier` 뿐).
그러므로 이 요청은 상수 몇 개를 바꾸는 일이 아니라 **전투 수식의 재설계**다.

네 AI 는 다음을 함께 본다 — ① 이 규격이 성립하려면 어느 파일의 무엇을 어떻게 바꿔야 하는가,
② 그때 무엇이 깨지는가(플레이어 공격력·경험치 곡선·드롭·포션 회복량·HP 바와 데미지 텍스트 표시·
방화벽 지속 피해·기존 난이도 곡선), ③ 100배로 커진 HP 축에 맞춰 **함께 스케일되어야 하는 값이
어디에 흩어져 있는가**, ④ MMORPG 로서(나중에 서버 권위로 옮길 때) 이 설계가 걸림돌이 되는가.

## Persona

**액션 RPG 의 전투 수식과 성장 곡선을 설계해 온 시니어 게임플레이 엔지니어 겸 밸런스 디자이너.**
다음 두 관점을 동시에 갖는다.

1. **수치 설계** — HP·피해·방어·성장 곡선이 서로 어떤 함수로 엮여 있는지, 한 축을 100배로 키우면
   어떤 축이 함께 움직여야 체감(몇 대 맞으면 죽는가 / 몇 대 때리면 잡는가)이 유지되는지를 본다.
   회복량·드롭·경험치처럼 HP 를 기준으로 **암묵적으로** 스케일되어 있던 값을 빠짐없이 찾아낸다.
2. **구현 구조** — 그 수식을 이 코드베이스의 어디에 두어야 단일 진실 공급원이 되는지, 지금처럼
   강함을 정하는 값이 여러 곳(`EnemyStats.table` · `MonsterPopulation` · `WaveDirector` ·
   `LevelSystem`)에 흩어져 있을 때 무엇이 어긋나는지를 본다.

부수적으로 **클라이언트를 신뢰하지 않는 보안 관점**을 겸한다 — 전투가 전적으로 클라이언트에서
계산되는 현재 구조에서, 이 변경이 나중에 서버 권위로 옮길 때 걸림돌이 되는 지점을 짚는다.

## Instructions

1. **모든 주장에 `파일:줄` 근거를 붙인다.** 근거를 못 대는 추정은 `[추측]` 으로 명시한다.
2. **이 프로젝트의 서버 설계 원칙**(`spacetimedb/src/lib.rs` 머리말)을 어기는 권고는 하지 않는다:
   - 클라이언트를 신뢰하지 않는다. 소유자는 `ctx.sender()` 에서 도출하며 `account_id` 를 인자로 받는
     reducer 는 없다.
   - 비밀번호는 별도 표(`AccountSecret`)에 둔다.
   - **모든 테이블이 비공개다.** 클라이언트가 읽는 것은 view 뿐이다.
   - 시각은 `ctx.timestamp`, 난수는 `ctx.random()` 만 쓴다.
3. **용어를 정확히 구분한다.**
   - `level` — **플레이어** 캐릭터의 성장 단계. 상한 30(`LevelSystem.maxLevel`, 서버
     `leaderboard::MAX_LEVEL`). 리더보드 순위의 기준이기도 하므로 의미를 바꾸면 서버까지 영향이 간다.
   - **몬스터 레벨** — 이번에 새로 도입하려는 개념이다. 지금 코드에 **없다.** 기존의 `EnemyKind`
     (scout·sentry·heavy·commander) 나 `hpMultiplier`/`damageMultiplier` 를 몬스터 레벨과 혼동하지 말 것.
   - `xp` — **누적 총량이 아니라 "현재 레벨 안에서 다음 레벨까지 쌓은 진행도"** 다. 서버·클라이언트가
     같은 의미로 쓴다. 이 정의를 오해한 분석은 무효다.
   - **피해(damage)** — 요구 규격의 "3레벨 몬스터는 3의 데미지"는 **방어력 0 기준으로 플레이어 HP 에서
     실제로 깎이는 최종 수치**를 뜻한다. 공격력 원본값이 아니라 방어 적용 후의 결과값이다.
   - **방어력(defense)** — 이번에 새로 도입하려는 플레이어 스탯이며 기본값 0 이다. 기존
     `BuffSpec.damageTakenMultiplier`(포션 버프의 피해 감소 배율)와는 별개의 축이다.
4. **SpacetimeDB 2.7 의 제약을 전제로 판단한다.**
   - view 가 받는 핸들은 읽기 전용이라 `iter()` 가 없다. 여러 행을 훑는 길은 인덱스 범위 조회뿐이다.
   - **view 도 구독해야 행이 온다**(실측). 구독하지 않으면 reducer 는 성공하는데 캐시는 비어 있다.
   - Dart 코드 생성기는 view 반환 타입의 이름을 **테이블 목록에서만** 찾는다. 테이블이 아닌 타입을
     반환하는 view 는 `Type2` 같은 존재하지 않는 클래스를 참조하는 깨진 코드를 만든다.
   - auto_inc id 는 연속을 보장하지 않는다. 정렬 기준으로 삼을 때 이 점을 고려한다.
5. **"서버가 전투를 시뮬레이션하지 않는다"는 현재 한계를 사실로 인정하고 논한다.** 레벨은 클라이언트가
   신고한다. 그것을 없애라는 권고보다, 그 전제 위에서 무엇을 더 막을 수 있는지 / 어디까지가 수용
   가능한 위험인지를 구체적으로 짚는 편이 유용하다.
6. **MMORPG 전제를 잊지 않는다.** "혼자 플레이할 때는 문제없다" 는 판정은 이 프로젝트에서 의미가 없다.
   같은 월드에 수십~수천 명이 동시에 있고 각자 레벨업할 때 무슨 일이 생기는지로 판단한다.
7. 게임 화면(HUD·인벤토리·리더보드)은 전부 **Flame `PositionComponent`** 다(Flutter 위젯이 아니다).
   좌표·히트테스트·클리핑은 캔버스 기준이다. 위젯 전제의 권고는 맞지 않는다. HP 표시가 네 자리에서
   다섯 자리로 늘어나는 문제도 이 전제 위에서 논한다.
9. **기존 밸런스를 "지금이 옳다"고 전제하지 않는다.** 사람이 요구한 규격(HP 1만·피해 = 몬스터 레벨)이
   최우선이며, 그것과 충돌하는 기존 수치는 바뀌어야 할 쪽이다. 다만 그 규격을 그대로 따랐을 때
   플레이 체감이 무너지는 지점(예: 1만 HP 를 3씩 깎으면 3,333대를 맞아야 죽는다)이 있으면 **규격을
   지키면서** 그것을 메우는 방법을 제시한다 — 규격 자체를 임의로 바꾸는 권고는 채택하지 않는다.
8. 주석과 문서는 **한국어**로 쓴다. 코드 식별자는 영문 그대로.

- **생성 코드**: `lib/spacetime/generated/` — `dart run spacetimedb_sdk:generate --project-path

1. **근거 우선.** 모든 주장에는 출처를 붙인다 — 작업공간 자료는 `파일경로:줄번호`, 외부 사실은 그

   지어내지 말고, **작업공간에 무엇이 있고 무엇이 없는지를 먼저 사실로 적은 뒤** 설계 판단을
   `[추측]`·[판단] 으로 명확히 구분해 제시하라.
4. **범위와 경계를 분명히.** 이 판단이 어느 영역에 속하는지 명시한다(예: 어느 계층·어느 단계·누구의
   결정 권한인지). 한쪽만 바꿔서 되는지, 양쪽을 함께 바꿔야 하는지가 결론을 바꾼다.
5. **이 작업공간의 실제 제약을 반영.** 지침 문서와 자료에서 읽어낸 제약(대상 사용자·품질 기준·분량·
   기한·호환성·안전 규칙·검수 절차 등)을 무시한 이상론을 쓰지 말라. 실행 불가능한 권고는 권고가 아니다.
6. **모르면 모른다고 하라.** 억지 결론보다 "무엇을 더 봐야 하는지" 가 낫다.

3) '파티 리더 추종(follow) & 자동 사냥' 설계 — 클라이언트에서 할지 서버 reducer 로 할지 판정하라. 라리엔은 서버 autopilot 앵커를 매 tick 갱신하지만 actionrpg 는 서버가 tick 시뮬레이션을 돌리지 않는다(monster_tick 은 5초 리스폰 전용). actionrpg 의 AutoHuntController(lib/game/systems/auto_hunt.dart)에는 이미 moveAnchor(157줄)·enable/disable·pursuitTimeout·blocklist 가 있다. 이것을 어떻게 재사용해 '리더 추종'을 구현할지, 추종 거리(leash)·재추적·장애물(경로탐색 없음)·리더 텔레포트(world.rs teleport_to)·리더 사망·리더 접속종료·follower 사망 처리를 구체적으로 설계하라. 기존 수동 자동사냥과 추종 사냥의 우선순위 충돌(앵커 소유권)을 어떻게 푸는지 반드시 답하라.
4) CLAUDE.md:33-34 'Hunting is solo, not party based. There is no party, no shared damage credit and no party loot rule.' 와 GAME-DESIGN.md:781 '솔로 사냥(파티 없음) — 설계상 파티 개념 자체가 없음' 이 이번 요청과 정면 충돌한다. world.rs 의 선점 태그(tagged_by, TAG_TTL_MICROS) 기반 킬 크레딧과 경험치 지급(award_kill)을 파티 공유로 바꿔야 하는가, 아니면 그대로 두고 '함께 다니되 경험치는 각자'로 갈 것인가? PK 허용 및 '남이 선점한 몹을 뺏으려면 그 사람을 쓰러뜨려라'는 기존 설계 철학과의 정합성을 따져 판정하고, 문서를 어떻게 갱신할지 구체적 문구까지 제안하라.
5) 구현 순서(우선순위)와 각 단계 검증 방법. CLAUDE.md 의 'Always test with DTD. 키보드/클릭 주입 금지, main()/initState() 에 테스트 코드 주입, 스크린샷·로그로 검증' 제약을 반드시 지키는 검증안이어야 한다. 다른 팀의 WorldPresence 구현이 아직 없는 동안 우리 기능을 어떻게 단위 테스트할지(가짜 WorldPresence 주입 등)도 답하라.

## 3. 상세 분석

### 3.1 범위·경계

| 영역 | 권위 | 담당 팀 |
|---|---|---|
| 월드 입장·좌표·원격 PC 렌더 | 서버 `world_player` + 클라 `WorldPresence` | **다른 팀** (이미 `SpacetimeWorldPresence`·`RemotePlayerEntity` 존재) |
| 파티 멤버십·초대 | SpacetimeDB 표/reducer | **우리 팀 (신규)** |
| 추종 시 이동·사냥 실행 | 클라 `AutoHuntController` + 로컬/서버 전투 경로 | **우리 팀** (presence는 읽기만) |
| 킬/EXP/loot | 기존 `tagged_by` + `award_kill` | **변경하지 않음** (의도적) |

“먼저 월드 연결부터”는 **이미 진행·부분 완료**이므로 반복 권고하지 않는다. 단 cowork-prompt/GAME-DESIGN의 “클라가 월드 미사용” 서술은 **코드와 어긋난다**(`spacetime_world_presence.dart`, `action_rpg_game.dart:533-536`).

### 3.2 SpacetimeDB 파티 스키마 (권고 설계)

기존 원칙: 계정 계층 비공개, 월드 공개 예외는 “서로 봐야 하는 사실”만(`world.rs:33-39`). 파티 멤버십은 **소셜 상태**이므로 기본은 **비공개 표 + view**. 다만 같은 파티원이 서로를 식별하려면 view가 멤버 행을 돌려줘야 한다. Dart 생성기는 view 반환 타입을 **테이블 이름에서만** 찾는다(`GAME-DESIGN.md:680-683` 리더보드 패턴) → view 전용 “가짜 표” 또는 **기존 테이블 타입을 그대로 반환**.

**표 (모두 private, `public` 없음)**

1. `party`
   - `id: u64` PK auto_inc  
   - `leader_character_id: u64` (btree)  
   - `created_at: Timestamp`  
   - (선택) `member_count: u32` — view/iter 제약 완화용 캐시  
   - **account_id 열 금지** (공개 경로 유출 방지 철학과 동일)

2. `party_member`
   - `character_id: u64` PK (**한 캐릭터 = 최대 1 파티**)  
   - `party_id: u64` btree  
   - `joined_at: Timestamp`  
   - (선택) `is_leader: bool` — `party.leader`와 이중이 되면 promote 시 둘 다 갱신; 단일 SSOT는 `party.leader_character_id` 권장

3. `party_invite` (만료·stale 차단 = 라리엔 `leadSeq` 역할)
   - `id: u64` PK auto_inc (**invite_seq**)  
   - `party_id`, `from_character_id`, `to_character_id` (to에 btree)  
   - `created_at`  
   - 수락 시 `id` 대조 → stale/다른 파티 초대 차단

4. (2단계) `hunt_lead_session` — party leader와 **분리**
   - `party_id` unique (파티당 1 세션)  
   - `leader_character_id`, `seq: u64`, `leash_meters` 또는 tiles, `started_at`  
   - follower 목록은 `hunt_follow` 표(`character_id` PK, `session_seq`, `party_id`) 또는 member 행 플래그

**Reducer (인자로 account_id/남의 identity 금지; 전부 `require_session` + selected character + 가능하면 `require_world_player`)**

| reducer | 검증 요약 |
|---|---|
| `create_party` | 월드 입장·무소속 → party 생성, 자신을 leader member로 insert |
| `invite_to_party(target_character_id)` | 호출자가 멤버(또는 leader-only 정책), 대상이 월드에 있고 무소속, 인원 상한, invite 행 생성 |
| `accept_invite(invite_id)` | `to` = 내 캐릭터, invite 유효·미만료, 아직 무소속 → member insert, invite 삭제 |
| `decline_invite(invite_id)` | 동일 소유 검증 후 삭제 |
| `leave_party` | 멤버 삭제; leader면 promote 자동 또는 disband 정책 명시 |
| `disband_party` | leader only, 멤버·초대·hunt session 일괄 삭제 |
| `promote(target_character_id)` | leader only, 대상 같은 파티 |
| `kick(target_character_id)` | leader only, 자신 제외 |
| `start_hunt_lead` / `accept_hunt_lead(seq)` / `stop_hunt_lead` / `set_hunt_leash` | 라리엔 §10.5 동등; **이동 시뮬레이션 없음**, 상태 플래그만 |

**구독**

```text
-- 월드 입장 후 (다른 팀 kWorldSubscriptions와 병합 시 충돌 주의 → 별도 query set 권장)
SELECT * FROM my_party
SELECT * FROM my_party_members
SELECT * FROM my_party_invites   -- to = me
SELECT * FROM my_hunt_lead       -- 본인 관점 leading|following|idle
```

view는 `ctx.sender()` → session → character_id → party_member 조인. **iter 없는 view**이므로 party_id btree 인덱스 필수.

**disconnect** (`lib.rs:208-213`): `world_player` 삭제만 함. 파티 멤버 행은 남을 수 있음 →  
- 최소: 멤버 유지(재접속 후 파티 유지)  
- 추종: 리더가 `world_player`에 없으면 클라가 follow 중단 + (선택) `stop_hunt_lead`를 리더 측 on_disconnect 훅에서 서버가 종료  

권고: **`on_disconnect`에 hunt_lead 세션 종료 + (선택) 초대 만료 청소**를 명시적으로 추가. 파티 멤버십은 로그아웃/`leave_party`까지 유지할지 제품 결정.

### 3.3 라리엔 이식 판정

| 라리엔 요소 | 판정 | 이유 |
|---|---|---|
| party leader vs hunt lead 분리 | **가져옴** | §10.5; 멤버십 권한과 사냥 지휘 혼동 방지 |
| 초대/수락/거절/추방/위임 흐름 | **가져옴** (reducer로 재모델링) | 사용자 흐름 동일 |
| `leadSeq` / invite id | **가져옴** | SpacetimeDB도 구독 지연·중복 클릭 → stale accept 가능 |
| 기존 autopilot leash 재사용 철학 | **가져옴** | `AutoHuntController`가 동일 역할 |
| 리더 사망 시 세션 유지·재집결 | **가져옴(클라)** | actionrpg도 안전지대 즉시 리스폰(`action_rpg_game.dart:1401-1412` 근처 설계) |
| PMEMB 청크 / `PartyMemberAccumulator` | **버림** | 구독 행 동기화; UDP MTU 없음 |
| PINV 1초×3 재전송 | **버림** | 신뢰 채널 + 표 지속; 대신 invite TTL(예: 20s) + UI 만료 |
| Nakama createParty / UUID 로컬 발급 | **버림** | party id는 서버 auto_inc |
| Zone 30Hz `updatePartyFollowAnchors` | **버림** | 서버 tick 없음; 클라 프레임에서 `moveAnchor` |
| EXP 균등 분배 / 드롭 라운드로빈 | **버림** | Cyborg 솔로·태그·PK 철학과 정면 충돌 |
| 최대 32명 / shard | **축소** | 초기 4~8 권장; shard 개념 없음(단일 월드) |

### 3.4 추종 & 자동 사냥 (클라)

**실행 위치: 클라이언트.** 서버는 “누가 누구를 따르기로 했는지”만 권위.

```
    leaderGrid = that.grid
    if !autoHunt.enabled: autoHunt.enable(leaderGrid)
    else: autoHunt.moveAnchor(leaderGrid)   // auto_hunt.dart:157-162
  elif leader 없음(월드 이탈) 또는 !alive 정책:
    // 접속종료: follow 해제 권고
    // 사망: 라리엔처럼 세션 유지 시 마지막 anchor 유지 → 부활 후 others에 다시 나타나면 재추적
  candidates / attack / move 실행은 기존 _updateAutoHunt 그대로
```

**leash:** `radiusMeters`를 hunt lead의 leash로 설정(기존 1~10m clamp, `auto_hunt.dart:64-71`). 리더 HUD 슬라이더는 서버 `set_hunt_leash` + 구독 반영 후 `autoHunt.radiusMeters = …`.

**경로탐색 없음:** 기존 `pursuitTimeout` 4s / `blockDuration` 3s 재사용(`auto_hunt.dart:84-93`) — 벽 뒤 몬스터 무한 추격 방지.

**텔레포트:** 리더가 `teleport_to`(`world.rs:744+`)하면 `RemotePlayerEntity`는 distance>12면 스냅(`remote_player.dart:77-80`). follower 앵커도 다음 presence에서 점프 → `moveAnchor`로 자연 재추적. follower 본인 텔레포트는 follow 유지 시 리더 쪽으로 다시 걸어감.

**앵커 소유권 (필수 정책)**

| 모드 | 땅 클릭 / 반경 버튼 | auto hunt 토글 |
|---|---|---|
| 수동 자동사냥 | `moveAnchor(클릭)` (`action_rpg_game.dart:992-995`) | 토글 on/off |
| **추종 사냥** | 클릭 이동·`moveAnchor` **무시** 또는 “추종 중” 배너 | 토글 off = **추종 중단**(서버 `stop` + disable) |
| 수동 조작(조이스틱) | 기존 `suspended` (`auto_hunt.dart:170-171`, `action_rpg_game.dart:647-656`) — 추종 중에도 “손 떼면 재개” 가능. 장기 수동 시 follow 유지 여부는 제품 선택(권고: 유지) |

단일 컨트롤러에 `enum AnchorOwner { manual, partyFollow }`를 두어 **follow가 manual을 선점**하고, follow 종료 시에만 manual re-enable.

**사망:** `onPlayerDied`가 지금 auto hunt를 끈다(`action_rpg_game.dart:1409-1412`). 추종 모드에서는 **끄지 말고 suspended**, 리스폰 후 재개 — 라리엔 follower 사망 정책과 정합. 리더 사망은 presence `alive=false` 동안 anchor 갱신 스킵.

### 3.5 문서·보상 철학 충돌

**판정: 파티 공유 데미지/EXP/loot로 바꾸지 말 것.**

이유:
1. 서버 킬 철학이 PK와 한 세트(`world.rs:16-17`): 선점 몹 뺏으려면 사람부터.
2. 파티 EXP 분배는 “같이 때리면 보상 공유” → 태그 무력화·막타 분쟁 재도입.
3. MMORPG 수천 명 동시 접속 시 파티 eligible 반경·락 복잡도가 Zone tick 모델에 의존(라리엔 `party.md` §6) — SpacetimeDB reducer-only 구조에 비용 큼.
4. 요청 기능의 핵심은 **이동 동선 공유(추종)** 이지 보상 공유가 아님.

**문서 개정 제안 문구**

`CLAUDE.md` Multiplayer:

```markdown
- Party membership and leader-follow (auto-hunt leash) are allowed for co-travel.
- Hunting credit remains solo: first-tag owns the kill, no shared damage credit,
  no party XP split, no party loot rule. Each player earns only what they tag.
- PK remains allowed; contesting a tagged monster still means fighting its owner.
```

`GAME-DESIGN.md:781` 행:

```markdown
| 파티 (동행·추종) | ✅ 멤버십·hunt lead 추종. 보상은 솔로(선점 태그) |
| 솔로 킬 크레딧 | ✅ 파티여도 EXP/loot 비공유 |
```

## 4. 리스크 · 함정

- **문서 vs 코드 불일치:** GAME-DESIGN/구 cowork 서술은 “클라 월드 미연결”인데 `SpacetimeWorldPresence`·원격 동기화가 이미 있음. 분석·구현 시 **코드 우선**.
- **`award_kill` 파티화는 되돌리기 어렵고 PK 경제를 붕괴**시킴 — 1차 범위에서 금지.
- **view/iter/생성기 제약:** 잘못된 view 반환 타입 → `Type2` 깨진 생성 코드(`GAME-DESIGN.md:680-683`).
- **공개 표 남용:** party를 public으로 두면 전 서버 파티 그래프 노출; 비공개+view가 원칙에 맞음.
- **파일 충돌:** `action_rpg_game.dart`는 양팀 핫스팟 — 파티 블록을 파일 하단 신규 섹션으로 격리하거나 믹스인/별 컴포넌트로 빼기.
- **추종 중 사망 시 현행 `autoHunt.disable()`**가 추종을 끊어 라리엔과 불일치 — 반드시 분기.
- **리더 이탈:** `on_disconnect`가 `world_player`만 지움 → 멤버십 고아/추종 좀비; hunt session 정리 규칙 필요.
- **클라이언트 전투 권위 잔존:** 로컬 `MonsterPopulation`과 서버 `monster` 이중 구조(`GAME-DESIGN.md:796-800`). 추종은 “리더 주변으로 이동”만 보장; **같은 몹을 본다는 보장은 다른 팀 몬스터 바인딩 완료 후**.
- **치팅:** 추종 이동·공격이 클라면 가짜 좌표 가능 — 기존과 동일 위험 수준; 멤버십 위조만 서버로 차단하면 1차 수용 가능(`cowork-prompt` 원칙 5).

## 6. 불확실 · 미확인

- 파티 **최대 인원**·초대 권한(leader only vs 전원): 제품 미지정 → 초기 **leader only 초대, max 4~8** 가정 `[추측]`.
- 리더 disconnect 시 **파티 해산 vs 멤버십 유지**: 미결정. 재접속 UX 필요.
- hunt lead를 **1차 파티 MVP에 포함할지**, 멤버십+UI만 먼저 갈지 — 요청은 둘 다이나 공수상 분리 가능.
- 서버 `attack_monster`와 클라 로컬 `Enemy` 전투가 언제 단일화되는지(타팀) — 추종 중 “같이 때리기” 체감에 영향.
- SpacetimeDB view가 **다수 party_member 행을 인덱스로만** 모을 때 조인 패턴의 실제 매크로 제약 — 구현 시 `cargo`로 확인 필요(읽기 전용 분석에서 컴파일 미실행).
- `party` 표를 public으로 두면 미니맵 “파티원 색”이 쉬워지나 원칙 위반 → 비공개 view vs 최소 공개 필드는 구현 시 한 번 더 검토.
- 라리엔 `test/party_*.dart` 전 파일·`sim/party.go` 라인 단위 동등성은 일부 문서 기준; Go 서버 소스는 이번 패스에서 전부 미개봉 — 세부 레이스 조건은 `[미확인]`.
