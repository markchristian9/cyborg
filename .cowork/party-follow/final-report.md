## 1. 결론

**해피패스는 이어져 있지만 "올바로 동작한다"고 말할 수 없다.** 초대→수락→추종→서버 몬스터 자동 공격의 코드 사슬은 실제로 끊김 없이 연결돼 있고, 다른 세션이 방금 넣은 `tryMelee(target:)` 대상 지정도 추종 경로에 자동으로 얹힌다. 그러나 시나리오를 끝까지 밀면 **결함 9개**가 나온다.

**가장 치명적인 것**: `invitePlayerToParty` 의 유일한 호출부가 "근처 요원" 목록인데, 그 목록은 파티가 **없을 때만** 그려진다(`party_panel.dart:126-128`). 즉 **2인이 되는 순간 3명째를 초대할 방법이 사라진다.** 서버는 12명을 허용하고 정원 초과 문구까지 준비해 뒀는데 그 코드에 닿을 길이 없다.

**두 번째**: AOI 가 파티 이후에 들어오면서 추종이 깨졌다. 리더가 74타일 청크 경계를 넘으면 `presence.others` 에서 사라지고 컨트롤러가 **그 프레임에 즉시** `lost` 로 끊는다. 유예가 0이라, 설계된 포기 거리 120타일은 **도달할 수 없는 죽은 상수**다.

**'파티 이끌기'는 여전히 미구현이다**(hunt_lead 문자열 0건). 2차 설계는 타당하나 AOI 우회 방법은 **반증됐다** — 서버 view 를 새로 만들 필요 없이 `world_player` 를 리더 `character_id` 로 추가 구독하면 된다. **서버 배포 없이 해결된다.**

## 3. 합의 — 검증 통과

- **추종하며 자동 공격은 실제로 성립한다.** 확인: `enemies` 의 유일한 소스가 서버 `monster` 표이고(`action_rpg_game.dart:1262`), 근접 타격이 `Enemy.serverId` → `presence.attack` → `attack_monster` reducer 로 간다. 추종은 별도 공격 코드 없이 **자동 사냥의 앵커만 옮기므로**, 다른 세션이 넣은 `tryMelee(target: decision.target)`(`action_rpg_game.dart:808`)의 이점(스윙당 요청 1건)이 추종 중에도 그대로 따라온다. 클라 접근 거리(1.5타일)가 서버 판정(2.2타일)보다 좁아 사거리 거절도 없다.

- **서버 뒤처리에는 빈틈이 없다.** 확인: `party.rs` 의 `remove_member` 가 탈퇴·추방을 한 곳에 모아 following 해제·파티장 승계·1명 이하 자동 해체를 모두 처리하고, `disband_party` 는 행을 통째로 지운다. 문제는 서버가 아니라 **클라의 뒷정리와 UI 진입점**이다.

- **추방은 사장 코드다.** 확인: `spacetime_party.dart` 에 `kick()` 구현이 있고 서버 reducer 도 있는데 `lib/` 전체에서 호출하는 곳이 **0건**이다.

- **`changes` 결함은 지금 무영향이다.** 확인: `party.changes` 를 듣는 리스너가 코드베이스에 하나도 없고 파티 UI 는 매 프레임 폴링으로 돈다. 인터페이스 정합성 문제일 뿐 이끌기의 전제조건이 아니다 — 2차에서 "반드시 함께 반영"이라 적었던 것을 **우선순위 하향으로 정정한다.**

## 4. 이견 — 자료로 판정

### 쟁점 A: AOI 밖 리더 좌표를 어떻게 받는가

- claude·codex: 서버에 `my_follow_target` view 를 새로 만들어 대상의 좌표·생사만 내보낸다.
- grok·kimi: **`world_player` 를 `character_id` 등식으로 추가 구독하면 된다. view 불필요.**

- **판정: grok·kimi 가 맞다.** 확인:
  - `world.rs:275-276` — `world_player` 는 `public` 표다. 즉 구독 대상이며, view 를 거칠 이유가 없다.
  - `character_id` 는 `#[unique]` 라 인덱스가 있다.
  - 구독 SQL 은 등식 나열만 허용하는데(`cyborg_connection.dart` 주석), `character_id = <리더>` 는 정확히 등식이다.
  - 구독은 이미 **동적으로 재구독**된다 — `spacetime_world_presence.dart` 의 `_maybeResubscribe()` 가 플레이어가 청크를 옮길 때마다 구독을 갈아 끼운다. 리더 id 하나를 그 쿼리에 얹는 것은 기존 메커니즘의 연장이다.
  - **결정적 이점: 서버 배포가 필요 없다.** view 안은 `Party` 열 추가와 함께 배포·바인딩 재생성을 요구하는데, 직접 구독은 클라만 고치면 된다. 이 저장소는 여러 세션이 `generated/` 를 공유해 재생성이 최대 위험으로 기록돼 있다(1차 §5).
- **부수 효과**: 이 방법은 이끌기 전용이 아니라 **모든 추종**(현재의 파티장 고정 추종 포함)을 함께 고친다. claude 가 "AOI 우회 view 를 이끌기 전용으로 만들면 안 된다"고 경고한 바로 그 지점을, 구독 방식이 자연히 만족한다.

### 쟁점 B: `giveUpDistanceTiles = 120` 의 지위

- claude: **죽은 상수다.** AOI 창이 74타일이라 120에 닿기 전에 `lost` 가 먼저 난다.
- 나머지: 무언급(2차에서 codex 는 제거를, grok 은 유지를 주장했었다).
- **판정: claude 가 맞다. 그러나 상수를 지우면 안 된다.**
  - 확인: 청크가 74타일이고 3×3 구독이므로 중심에서 경계까지 최소 74타일. 120타일 리더는 이미 구독 밖이라 `presence.others` 에 없고, 컨트롤러 ①분기가 먼저 `lost` 를 낸다. 지금은 확실히 죽은 코드다.
  - **하지만 §4-A 를 적용하면 되살아난다.** 리더를 직접 구독하면 AOI 밖에서도 좌표가 오므로, 그때 "너무 멀어서 포기"를 판정하는 것이 바로 이 상수다. 2차에서 "follower 가 죽어 안전지대에서 되살아났을 때 무방비 장거리 횡단을 막는 장치"라고 판정한 그 역할을 그제야 실제로 수행한다.
  - 즉 **A 를 고치면 B 는 저절로 유효해진다.** 순서가 중요하다.

## 5. 고유 통찰 — 검증됨

- ⭐ **claude·kimi: 파티 중 추가 초대 불가.** 확인: `party_panel.dart:126-128` 의 `if (party.inParty) return _memberRows(party); return _nearbyRows();` 와 `invitePlayerToParty` 호출부 1곳(`party_panel.dart:425`). **사실상 2인 파티가 상한**이며, 이번 요청의 "파티 초대가 올바로 동작하는가"에 대한 답이 여기 있다.

- ⭐ **claude: `accept_invite` 의 만료 정리가 무효다.** `party.rs` 가 만료 초대를 `delete` 한 뒤 `Err` 를 반환하는데, `Err` 는 트랜잭션을 롤백하므로 그 삭제가 되돌려진다. 만료 행은 `invite_to_party` 가 같은 대상에게 다시 초대할 때까지 남는다. (단 claude 자신이 §6 에서 "SpacetimeDB 표준 동작에 기댄 판단, 실측 기록 없음"이라 밝혔다 — **구현 전 확인이 필요한 항목**으로 남긴다.)

- ⭐ **claude: 내가 부활할 때 진전 기록이 초기화되지 않는다.** `party_follow.dart` 의 `_bestDistance` 리셋은 **리더**가 죽었을 때만 일어난다. 내가 죽어 안전지대로 튕기면 리더 옆에서 재던 작은 값이 남아 `distance < _bestDistance - 0.5` 가 계속 거짓이고, 8초 뒤 "닿을 수 없다"로 끊긴다. 2차 보완에서 "부활 시 오판"을 고쳤다고 적었는데 **그것은 리더 부활만이었다.**

- ⭐ **kimi: 파티장이 접속을 끊으면 얼어붙는다.** 해산도 위임도 리더 전용이라 남은 사람은 아무것도 못 한다. 각자 나가면 풀리지만 그 사실을 알려 주는 안내가 없다.

- **codex: target view 에 `lead_seq`·`deaths` 를 넣어야 한다** — §4-A 로 view 자체를 채택하지 않으므로 무효화되지만, "부활을 감지할 신호가 필요하다"는 지적은 유효하다. `world_player.deaths` 가 이미 구독으로 오므로 그것으로 §5 의 부활 문제를 감지할 수 있다.

## 6. 반증 — 근거가 틀린 주장

- **claude·codex**: "AOI 우회는 서버 view 로" — ❌ `world_player` 가 `public` 이고 `character_id` 가 `unique` 인덱스라 **직접 구독으로 된다**(§4-A). 서버 배포라는 큰 비용을 치를 이유가 없다. 두 AI 모두 `world.rs:275-276` 의 `public` 선언을 근거에 넣고도 그 함의를 놓쳤다.

- **2차 종합(내 것)**: "`changes` 에 `my_party` 를 반드시 함께 반영해야 한다" — ⚠️ **과장이었다.** 네 AI 중 kimi·claude 가 "소비자가 없어 무영향"이라 지적했고 확인 결과 `party.changes` 리스너가 0건이다. 고치는 것은 옳지만 **전제조건이 아니다.**

- **2차 종합(내 것)**: "부활 시 진전 기록 오염을 고쳤다" — ❌ 고친 것은 **리더 부활**뿐이고 **내 부활**은 그대로 남아 있다(§5). 같은 이름의 결함을 반쪽만 고쳐 놓고 닫았다.

- **grok**: "(바) 즉시 리스폰 후 거리(120타일)에 따라 재개/끊김" — ❌ 지금은 120타일에 닿기 전에 AOI 로 먼저 끊긴다(§4-B). grok 이 죽은 상수를 살아 있는 것으로 전제했다.

## 8. 미해결 · 사람 판단 필요

- **`Err` 반환 시 롤백 여부**를 이 SpacetimeDB 배포에서 실측한 기록이 없다. 권고 9 전에 확인이 필요하다.
- **이끌기 권한** — '파티원 누구나' vs '파티장만'. 라리엔 선례와 코드의 확장 의도로 '누구나'를 권하나 제품 결정이다.
- **배포·재생성 순서** — 권고 8·9 는 `generated/` 재생성을 요구한다. 여러 세션이 같은 디렉토리를 쓰므로 순서 합의가 필요하다.
- **패널 높이** — 12인 파티 + 근처 요원 구역이 함께 뜰 때의 배치는 해상도별 DTD 스크린샷으로 확정해야 한다.
- **추종 중 rejoin 구간의 사냥 공백** — 리더가 계속 이동하면 follower 가 25타일 밖에 머물며 사냥을 거의 못 할 수 있다. 의도된 우선순위지만 체감은 사람이 판단해야 한다.
