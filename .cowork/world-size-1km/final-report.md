# 종합 검토 — world-size-1km

> 요청: 게임 월드의 크기가 가로 1km, 세로 1km 이어야합니다. 그렇게 되어져 있는지 분석하고 수정/보완해주세요.
> 분석: claude · codex · grok(2-pass) · kimi — 4/4 성공
> 종합: 2026-08-04 21:15 · 읽기 전용 검증 — 종합 작성 시점까지 본 세션은 작업공간 미수정
> 재검증(리뷰 반영 시점): 근거를 다시 열어 확인 — 그 사이 **다른 세션이 `iso.dart`·`world.rs` 를 실제로 수정**했다.
> 아래 `파일:줄` 은 모두 재검증 시점 기준으로 갱신했다(§8 마지막 항목 참조).

## 1. 결론

**요구 규격 "가로 1 km × 세로 1 km" 는 충족돼 있다. 크기를 키울 필요는 없다.** `kMetersPerTile = 1.0`
이므로 타일 = 미터이고, `kWorldSizeMeters = 1000.0` 이 한 변 1000 m 를 정의한다. 프로덕션 경로
(`onLoad`·`restart`)는 `LevelMap.generate()` 를 인자 없이 부르므로 런타임에도 규격대로 생성되며,
설계 문서도 같은 값이다. **월드 크기 데이터 경로에는** 규격을 깎아먹는 지점이 없다 — 직접 열어 확인했다.

**따라서 이번 작업의 실체는 "키우기" 가 아니라 "고정·검증" 이다.** 지금 1 km 라는 사실을 지키는
**자동 회귀·SSOT 강제 장치가 없다**: 크기를 못 박는 테스트가 **없고**, 클라이언트와 서버가 1000 을
각자 손으로 적어 두고 주석("클라이언트 `kWorldTiles` 와 같아야 한다", `world.rs:47`)으로만 연결한다.
문서와 양쪽 리터럴 일치라는 **수동** 장치는 있으나 강제력이 없다 — 재검증 중 그 위험이 실제로 발현했다(§8).

여기에 1 km 규모라서 비로소 문제가 되는 결함이 하나 있다 — **웨이브 종료 판정이 웨이브 소속이 아닌
적까지 센다**(§5).

**"1 km 같지 않다" 는 체감의 원인은 크기가 아니라 뷰 스케일이다.** 줌은 화면 세로를 760 px 기준으로
잡고(`action_rpg_game.dart:226-229`, `zoom = screenSize.y / 760`, `0.55~1.6` 클램프), 레이더는 반경
70 m 만 보여 준다(`hud.dart:24`, `_radarRangeTiles = 70`). 한 화면에 들어오는 범위가 월드의 수십 분의
일이라 넓이가 체감되지 않는 것이며, **이를 이유로 크기 상수를 키우면 안 된다.**

## 3. 합의 — 검증 통과

- **월드는 통행 가능 1 km × 1 km 다.** 확인: `lib/game/iso.dart:21,28` — `kMetersPerTile = 1.0`,
  `kWorldSizeMeters = 1000.0`.
- **런타임도 규격대로다.** 확인: `lib/game/action_rpg_game.dart` 의 `onLoad`·`restart` 와 `test/` 4곳 —
  `LevelMap.generate()` 호출부가 **전부 인자 없음**(`level_map.dart:228-230` 기본값 `kWorldTiles`).
  더 작은 맵으로 도는 경로가 없다.
- **서버는 `WORLD_TILES = 1000.0` 이다.** 확인: `spacetimedb/src/world.rs:48`, 월드 중심
  `:344` `(WORLD_TILES/2, WORLD_TILES/2)`. **단, 재검증 시점 클라이언트 격자와 어긋났다(§8).**
- **크기 회귀 테스트가 없다.** 확인: `test/` 전역에 `kWorldTiles`·`widthInMeters`·`map.width ==` 검색
  결과 0건. `test/safe_zone_test.dart:58` 은 `expect(map.safeZone.center, map.worldCenter)` 처럼
  **파생끼리 비교**하므로 크기가 바뀌어도 통과한다 — 회귀를 잡지 못한다.
- **명세 상수의 지배력 문제(당시 진단, 두 상수는 성격이 다르다).**
  - `kWorldSizeMeters` — 종합 시점에 `iso.dart` 밖 참조처가 **0곳**이었다. 명세를 선언한 상수가
    실제 월드를 지배하지 않는 상태였다. → 재검증 시점에는 파생 사슬이 생겨 해소됐다(§8).
  - `kWorldChunks` — 리터럴이 아니라 `kWorldTiles` 에서 **유도된** 상수다(`iso.dart:50`).
    참조처가 없다는 것만 사실이며, "명세가 지배하지 않는다" 는 진단은 여기에 해당하지 않는다.
- **외곽 3칸은 통행 불가다.** 확인: `lib/game/level/level_map.dart:247` — 테두리 두께 3.
  이 테두리는 통행 가능 영역 **바깥에** 덧붙는 것으로 설계돼 있다(`iso.dart:33-38` 주석).

## 4. 이견 — 자료로 판정

### 쟁점 1: 카메라가 월드 밖 허공을 비추는가

- claude: 클램프 범위가 그리드 화면 좌표와 "정확히 일치한다. 이상 없음"
- codex: 마름모가 아닌 외접 직사각형에 clamp 하므로 모서리에서 허공이 보일 수 있다
- **판정: codex 가 맞다.**
- **근거**: `lib/game/action_rpg_game.dart:433-448`. 주석 자체가 *"아이소메트릭이라 월드는 화면에서
  마름모가 되지만, 여기서는 그 마름모를 감싸는 사각형으로 충분하다"* 라고 밝힌다. 외접 사각형과
  마름모의 차집합(네 모서리)에서는 데이터 공백이 화면에 들어온다. 다만 이어지는 주석 *"1 km 월드라
  가장자리에 닿는 일 자체가 드물다"* 대로 **의도된 근사**이며 버그가 아니다. claude 의 "화면 좌표
  범위와 일치" 는 사각형 기준으로는 맞지만 "허공을 안 비춘다" 는 결론이 틀렸다. kimi 의 "마름모 안에
  가둔다" 도 같은 오류다(§6).

### 쟁점 2: 마지막 청크가 월드 밖까지 계산되는가

- codex: `_chunkBounds()` 가 마지막 청크도 32타일로 계산해 좌표를 월드 밖까지 잡는다
- kimi: `math.min(start + kChunkTiles, width)` 로 잘라 오버런이 없다
- **판정: 서로 다른 곳을 보고 둘 다 맞다.**
- **근거**: `lib/game/level/ground_layer.dart:129-133` — `_chunkBounds` 는 `x1 = x0 + kChunkTiles` 로
  **자르지 않는다**(codex 가 맞음). 반면 실제 타일 순회는 `:160-161` 의 `math.min` 으로 `map.width`
  에서 끝난다(kimi 가 맞음). 즉 **그려지는 타일은 정확하고, cull 사각형만 실제보다 크다.** 시각적
  결함은 없고 가장자리 청크에서 컬링이 약간 헐거워지는 정도다.

### 쟁점 3: 서버 `move_to` 클램프의 줄 번호

- claude·grok(자기비판 후): `world.rs:489-490` / kimi: `world.rs:498-499` / 종합 시점 재확인: `505-506`
- **판정: 주장 내용은 사실, 줄 번호는 계속 밀린다. 재검증 시점 실제는 `536-537`.**
- **근거**: `spacetimedb/src/world.rs:536-537` — `let x = grid_x.clamp(0.0, WORLD_TILES);`.
  같은 파일이 종합 이후에도 편집돼 레벨 산출식은 `:386-387`, 몹 스폰 `MARGIN` 은 `:437` 로 이동했다.
  **동시 편집이 실제로 일어난다는 것은 재검증에서 직접 확인된 사실**이며 추측이 아니다(§8).
  줄 번호가 아니라 내용 기준으로 채택한다.

## 5. 고유 통찰 — 결함은 실재하나 인과를 바로잡아야 한다

- **claude(부분 채택)**: 웨이브가 끝나지 않을 수 있다 — **원인은 스폰 폴백이 아니라 종료 판정의 범위다.**
  확인: `action_rpg_game.dart:624`
  ```dart
  // 남은 적이 없으면 웨이브 종료.
  if (enemies.every((enemy) => !enemy.isAlive)) {
  ```
  그런데 `enemies` 에는 웨이브 적(`:654`)뿐 아니라 **스트리밍으로 깨운 상주 몬스터도 들어간다**(`:587`,
  `_refreshMonsterStreaming`). 활성 반경 46 m(`:131`) 안에 살아 있는 상주 몹이 하나라도 있으면 웨이브
  적을 전부 죽여도 종료 조건이 성립하지 않는다. 1 km 월드에 상주 몹을 수천 기 흩뿌린 설계이므로
  **이 경로가 상시적**이다. → **이번 요청 범위 안의 실제 결함**으로 채택한다.
  - 다만 회수 경로(`:547`)는 `_activeMonsters` 만 순회하므로, 상주 몹이 60 m 밖으로 멀어지면 `enemies`
    에서 제거된다(`:561`). 따라서 "영구 정지" 가 아니라 **플레이어가 그 자리에 머무는 동안 정체**한다.
    실제 정체 시간은 실행 측정이 없어 `[추측]` 이다.

- **claude(축소 채택)**: 웨이브 스폰 폴백이 월드 전역을 뽑는다 — 확인:
  `lib/game/systems/wave_director.dart:105-125`. 실제 경로는 **3단**이다.
  ```dart
  for (var attempt = 0; attempt < 220; attempt++) { ... }   // ① 플레이어 반경 9~20 m
  for (var attempt = 0; attempt < 400; attempt++) {          // ② 월드 전역 무작위
    final x = _random.nextDouble() * map.width;
    ...
  }
  return map.nearestWalkable(_pointOutsideSafeZone());       // ③ 안전지대 경계 바로 바깥
  ```
  ①이 220회 모두 실패해야 ②에 도달하므로 **드문 경로**이고, ②마저 400회 실패하면 ③이 안전지대
  근처를 보장한다. 종합 초판이 ③을 생략하고 "영원히 잠든다" 로 단정한 것은 과장이었다.
  - **또한 "활성 반경 46 m 밖이라 잠든다" 는 틀렸다.** 웨이브 적은 `world.add(enemy)`(`:655`)로 직접
    마운트될 뿐 `_activeMonsters` 에 등록되지 않아 스트리밍 회수·수면 대상이 아니다. 계속 `update()`
    된다. 실제 문제는 **어그로 사거리**(`enemy.dart:98-104`, 종별 미터값을 타일로 환산)를 한참
    벗어난 곳에 생겨 플레이어에게 접근하지 않는 것이다. codex 의 반박이 맞다.
  - "맵이 46×46 이던 시절" 이라는 서술은 저장소에서 확인되지 않으므로 삭제한다.

- **grok(자기 비판)**: 1차 분석에서 "실질 통행 994 m" 를 규격 미충족처럼 서술했다가 2차에서 철회하고
  **"격자 1 km 는 충족, 테두리는 의도된 설계"** 로 정정했다. 이 정정이 옳다 —
  `teleport_destinations.dart:40-45` 의 `edgeInset = 30` 주석이 외곽 3칸 `TileType.none` 을 명시적
  전제로 삼고 있어, 테두리는 버그가 아니라 다른 시스템과 정합한 설계다.

- **claude**: 서버 몹 레벨 곡선이 플레이어 만렙 상수를 재사용한다 — `world.rs:386-387` 의
  `1.0 + rim × (MAX_LEVEL - 1)` 에서 `MAX_LEVEL` 은 `leaderboard.rs` 의 **플레이어 만렙**이다(`:116`
  에서 import). 클라이언트 도감은 `monster_codex.dart:283` `maxLevel = 200` 이다.
  → 사실이지만 **크기 문제가 아니고**, 클라이언트가 아직 서버 월드를 읽지 않으므로(§8) 현행 플레이의
  충돌이 아니라 **미연동 소스 간 불일치**다. 되돌리기 비용도 크다(§7 보류).

## 6. 반증 — 근거가 틀린 주장

- **claude(분석)**: 카메라 클램프가 "정확히 일치한다. 이상 없음" — ❌ `action_rpg_game.dart:433-448`
  은 마름모의 **외접 사각형**으로 clamp 한다(주석이 그렇게 밝힌다). 모서리에서는 허공이 노출된다.
  결론("크기 문제 아님")은 유지하되 "이상 없음" 이라는 판정은 채택하지 않는다.
- **kimi(분석)**: `_clampToWorld` 가 카메라를 월드 **마름모** 안에 가둔다 — ❌ claude 와 동일한 사실
  오류다. 근거는 위와 같다.
- **kimi(분석)**: 서버 클램프가 "월드 밖 좌표 서버 수용 불가" — ❌ `clamp(0.0, WORLD_TILES)` 는 상한
  **1000.0 을 포함**하고, 타일 인덱스 유효 상한은 `width - 1` 이다(`level_map.dart:126-129` `_index`).
  좌표 1000.0 은 어느 타일에도 대응하지 않으므로 "수용 불가" 가 아니라 "클라이언트에서 설 수 없는
  좌표를 서버가 받아들인다" 가 맞다.
- **kimi(리뷰 단계)**: `kWorldTiles = kWorldSizeMeters ~/ kMetersPerTile` 는 "`double ~/ double` 이
  `double` 을 반환하므로 타입 오류로 컴파일 불가" — ❌ Dart 의 `~/` 는 `num.operator ~/` 이고 반환
  타입은 `int` 다. 실제로 재검증 시점 코드가 `iso.dart:31` 에서 `const int kWorldPlayableTiles =
  kWorldSizeMeters ~/ kMetersPerTile;` 로 그대로 쓰고 있다. 남는 미확인 사항은 타입이 아니라
  **`double ~/ double` 이 const 문맥에서 평가되는지** 뿐이다(§8).
- **줄 번호 전반**: 네 AI 가 인용한 `world.rs` 클램프 줄 번호(489/498/505)가 모두 현재(536)와 다르다.
  내용은 사실이므로 반증이 아니라 **시점 차이**로 처리한다(§4 쟁점 3).

### 사람 판단으로 확정된 전제 — §8 첫 분기가 해소됐다

사용자가 §8 의 "1 km 의 의미" 질문에 직접 답했다: **"실제로 걸을 수 있는 거리가 가로 1 km,
세로 1 km"**. 이로써 §1 의 결론이 뒤집힌다.

- 종합 시점 판정("규격 충족")은 **격자 기준**이었다. 걷는 거리 기준으로 다시 재면 격자 1000 에서
  외곽 테두리 3칸이 양쪽으로 빠져 **994 m × 994 m** 였고, 요구 규격을 **충족하지 않았다.**
- 따라서 이번 작업은 §7 이 전제한 "고정·검증" 에 더해 **규격 확장**을 포함한다.

### 사람 확인·후속 조치

- **필요(배포)**: 서버 변경은 소스와 빌드까지만 맞췄다. `spacetime publish` 는 되돌리기 어려운 외부
  작업이라 적용하지 않았다. 클라이언트가 아직 `world_player`·`monster` 바인딩을 생성하지 않아
  현재 동작 차이는 없다(§8).
- **필요(검증 재실행)**: 서버에 추가한 대조 테스트 2건은, 적용 직후 다른 세션이 `world.rs`
  (`MONSTER_MAX_LEVEL` 도입, `leaderboard::MAX_LEVEL` import 잔존)와 `character.rs`(`total_xp` 열
  추가)를 편집해 컴파일이 깨진 상태라 **아직 실행되지 못했다.** 그 세션의 작업이 끝나면
  `cargo test` 로 확인해야 한다. 내 변경분은 그 직전 실행에서 31/31 통과를 확인했다.
- **불필요(되돌리기)**: 클라이언트 변경은 값이 자동 파생되므로 `kWorldSizeMeters` 하나만 되돌리면
  전부 원복된다.
- **커밋하지 않았다.** 여러 세션이 동시에 같은 저장소를 편집 중이라(적용 시점에 `lib/`·
  `spacetimedb/` 수십 개 파일이 modified) 지금 커밋하면 타인의 미완성 작업이 함께 들어간다.
  커밋 시점은 사람이 정하는 편이 안전하다.

### 권고에 없었지만 필요해진 변경

- `LevelMap` 에 `playableMin`·`playableMaxX`·`playableMaxY`·`playableWidthInMeters`·
  `playableHeightInMeters` getter 추가. §7-2 의 "통행 가능 폭 == 1000" 을 테스트가 검사하려면
  격자 크기와 걷는 거리를 구분해 노출하는 수단이 있어야 했다.
- 서버 `PLAYABLE_MAX` 상수 추가. `clamp` 는 포함 상한을 요구하는데 통행 구간의 상한은 배타적이라,
  그 차이를 상수 하나로 고정하지 않으면 호출부마다 `- 0.001` 이 흩어진다.

### 9-1. 문서 갱신과 서버 배포 (사용자 지시로 추가 수행)

**`GAME-DESIGN.md` 갱신** — 규격 정의가 "격자" 에서 "걷는 거리" 로 바뀐 것을 반영했다.

| 절 | 갱신 내용 |
|---|---|
| §1 한눈에 보기 | "1 km × 1 km (1000×1000 타일)" → "걸어서 1 km × 1 km (격자 1006×1006 타일)" |
| §5.1 규모와 스트리밍 | 걷는 거리가 규격이고 테두리는 그 **바깥에** 덧붙는다는 점, 상수 유도 사슬(`kWorldSizeMeters` → `kWorldPlayableTiles` → `kWorldTiles`), 서버 대조 테스트의 존재 이유 |
| §7.3 피격과 사망 | 재가동은 전투 상태를 남김없이 되돌린다(클릭 이동 목표 포함) — 남기면 재가동 직후 혼자 안전지대 밖으로 걸어 나간다 |
| §8.2 AI 상태 기계 | 어그로 1~5 m 규격, 계통별 구간 표, 추격 포기 = 어그로 + 2.5 m, 사거리보다 어그로가 짧은 계통의 의미 |
| §8.4 웨이브 | 종료 판정이 웨이브 소속(`seed == null`)만 센다는 점과 그 이유, 스폰 폴백이 기준점 둘레로 넓어진다는 점 |
| §15 밸런스 상수 요약 | 월드 행 갱신, 어그로 행 신설 |

**서버 배포 완료** — `spacetime publish withcenter-cyborg --server maincloud`

- 결과: `Database updated` · program `90839d2a66586987e581afb850cf30ed22372db25f31da23032e70d6729f3f45`
- **배포를 위해 권고에 없던 수정이 하나 필요했다.** 첫 시도가
  `Adding a column total_xp to table leaderboard_entry requires a default value annotation`
  으로 거부됐다. 다른 세션이 리더보드를 누적 경험치 기반으로 개편하며 `LeaderboardEntry.total_xp`
  에 기본값 애노테이션을 빠뜨린 것이다(같은 세션이 `PlayerCharacter::total_xp` 에는 붙여
  뒀고, 그 주석이 `u64` 접미사까지 요구하는 이유를 이미 설명해 두었다). 같은 패턴으로
  `#[default(0u64)]` 을 붙여 해결했다 — 이 표는 캐릭터에서 매번 다시 만들어지는 파생 뷰라
  기본값으로 채워진 옛 행은 다음 갱신에서 실제 값으로 덮인다.
  - 대안이었던 `--delete-data` 는 **쓰지 않았다.** 계정·캐릭터·순위가 전부 지워진다.
- **함께 배포된 것**: 이번 월드 규격 변경 외에 다른 세션이 작업한 서버 변경이 같이 나갔다 —
  `world.rs`(신규: 몬스터·킬 판정·PK·텔레포트), `leaderboard.rs`(만렙 제거, 누적 경험치 순위),
  `character.rs`·`lib.rs`(`total_xp` 열). 배포는 저장소 상태 전체를 올리는 작업이라 분리할 수 없다.
- **영향**: 스키마 변경이라 `All clients will be disconnected` 경고와 함께 접속이 한 번 끊겼다.
  기존 데이터는 자동 마이그레이션으로 **보존**됐다(옛 행의 `total_xp` 는 0으로 채워지고,
  리더보드는 다음 갱신에서 실제 값으로 복원된다).
- 배포 전 검증: `cargo test` 36/36 · wasm 릴리스 빌드 성공 · `flutter analyze` 0건.

**배포 후 남은 문제(내 변경과 무관)**: `test/spacetime_integration_test.dart` 가
