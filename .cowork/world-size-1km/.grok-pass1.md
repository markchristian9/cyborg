## 1. 결론 요약

**게임 월드는 이미 가로 1 km × 세로 1 km(1000×1000 타일, 타일=1 m)로 정의·생성·서버 클램프되어 있다.**  
“1 km로 키워야 한다”는 식의 규모 변경은 **필요 없다.**  
보완이 의미 있는 지점은 (1) **크기 회귀를 막는 단위 테스트 부재**, (2) 서버 좌표 상한 `0..1000` vs 클라이언트 타일 `0..999` **경계 오프바이원**, (3) 외곽 3칸 허공으로 **실질 통행 가능 폭 ≈ 994 m** 인 점의 문서·의도 정리, (4) 서버 상주 몹 240 vs 클라이언트 수천 기 **이중 월드**다.  
이 분석은 읽기 전용이며 파일을 수정하지 않았다. 수정 절차는 §5에만 적는다.

## 3. 상세 분석

### 3.1 규격 해석 (이 작업공간의 단위)

| 축 | 값 | 의미 |
|---|---|---|
| 한 변 미터 | `kWorldSizeMeters = 1000` | 가로·세로 각 1 km |
| 한 변 타일 | `kWorldTiles = 1000` | 면적 100만 칸 = 1 km² |
| 타일 실거리 | `kMetersPerTile = 1.0` | **타일 번호 = 미터** |
| 청크 | 32×32 타일 × 32×32 청크 | 스트리밍 단위 |

요구 “가로 1 km, 세로 1 km”는 이 프로젝트에서 **`kWorldTiles × kMetersPerTile` 이 각 축 1000 m** 와 동의어다. 화면 픽셀(타일 128×64)이 아니라 **그리드 논리 크기**가 권위다 (`GAME-DESIGN.md` §4, `iso.dart`).

### 3.2 데이터 경로 — 실제로 1 km 맵이 만들어지는가

1. SSOT 상수: `iso.dart`의 `kWorldTiles` / `kWorldSizeMeters`.
2. 생성: `LevelMap.generate()` 기본 인자로 1000×1000 `Uint8List` 3장(약 3 MB) 할당.
3. 게임 진입: `ActionRpgGame.onLoad` / `restart` → `LevelMap.generate()`만 호출. 다른 크기 주입 경로 없음.
4. 서버: `WORLD_TILES = 1000.0`, `world_center = (500, 500)`, `move_to`가 같은 격자 범위로 클램프.

문서(`GAME-DESIGN.md`)와 코드가 **일치**한다. “문서만 1 km” 가설은 성립하지 않는다.

### 3.3 1 km를 “감당”하는 구조 (크기가 맞아도 필수인 이유)

100만 칸 객체화는 불가능하므로:

- 지형: 평면 배열 + 청크 `Picture` 캐시 (`ground_layer.dart`, 프레임당 3청크, 캐시 96).
- 구조물: 시야+16타일 청크 마운트 (`action_rpg_game.dart`).
- 몹: 장부 `MonsterSeed` ↔ 근처만 `Enemy` (활성 46 m / 해제 60 m / 상한 140).

즉 **크기 상수는 1 km로 이미 맞고**, 성능 전제도 1 km를 전제로 짜여 있다. 크기를 줄이거나 키우면 스트리밍·개체군 밀도가 같이 움직여야 한다.

### 3.4 “1 km”와 어긋날 수 있는 경계들

| 항목 | 사실 | 판정 |
|---|---|---|
| 격자 한 변 | 1000 타일 = 1000 m | 규격 충족 |
| 통행 가능 영역 | 외곽 3칸 `none` → 대략 3‥996 | **월드 정의**는 1 km, **발 디딜 수 있는 폭**은 약 994 m |
| 서버 좌표 상한 | `clamp(0.0, 1000.0)` inclusive | 클라이언트 타일 인덱스 0‥999와 **끝점 1 차이** 가능 |
| 클라이언트 이동 | walkability만 | 맵 밖은 사실상 차단, 명시 `0 ≤ x < width` 클램프는 없음 |
| 크기 회귀 테스트 | `expect(map.width, 1000)` 류 **없음** | 상수 변경 시 조용히 깨질 수 있음 |
| 서버 vs 클라 몹 | 240 vs 청크당 분대×~1000청크 | **같은 1 km 격자**를 쓰지만 콘텐츠 밀도·권위가 이중 |

### 3.5 범위와 권위

- **월드 기하 크기(SSOT)**: 클라이언트 `iso.dart` + 서버 `WORLD_TILES` (수동 동기, 주석으로만 연결).
- **지형 실체**: 클라이언트 전용 절차 생성(시드). 서버는 지형 타일을 들고 있지 않음 → 몹 스폰은 여백만 피함.
- **MMORPG**: 공유해야 할 것은 “같은 1 km 격자 좌표계”다. 크기는 이미 맞춰 있음. 아직 깨져 있는 것은 크기보다 **몹·전투 권위 이중화**.

### 3.6 “수정이 필요한가”에 대한 직접 답

- **규모를 1 km로 만드는 작업**: 불필요 — 이미 됨.
- **보완**: 회귀 테스트, 서버 clamp 상한(`WORLD_TILES` vs `WORLD_TILES - ε`), 클라·서버 몹 밀도 정렬, (선택) 외곽 마진을 규격에 명시.

## 4. 리스크 · 함정

- **오판 위험**: “1 km가 안 되어 보인다”는 체감은 카메라 줌·70 m 레이더·스트리밍 때문이지 맵 상수가 작아서가 아니다. 크기를 바꾸면 성능·밸런스·텔레포트 가장자리(`edgeInset=30`)가 연쇄 붕괴한다.
- **서버 `clamp(0, WORLD_TILES)`**: 좌표 `1000.0` 허용. 클라 `floor` 시 인덱스 1000 → 맵 밖. 텔레포트·치트·지연 보간에서 끝선 글리치 가능. `clamp(0.0, WORLD_TILES - 1e-3)` 또는 `WORLD_TILES as 한 변 길이` vs `max exclusive` 용어를 맞춰야 한다.
- **이중 진실 공급원**: Dart `kWorldTiles`와 Rust `WORLD_TILES`가 복제. 한쪽만 바꾸면 “1 km 월드” 전제가 무너진다. 자동 동기화/통합 테스트 없음.
- **실질 통행 ≠ 격자 한 변**: 외곽 3 m 허공은 의도된 테두리. “가로 정확히 1000 m를 걸을 수 있어야 한다”로 읽으면 미충족으로 오해할 수 있다 — 현 기획은 **격자 1 km + 테두리 허공**이다.
- **서버 몹 240 vs 클라 수천**: 1 km 공유 월드로 갈 때 어느 쪽이 권위인지 정리 전까지 같은 맵 크기라도 “빈 들판 / 북적이는 맵”이 갈린다.
- **`LevelMap.generate(width:, height:)` 오버라이드**: 테스트·실험용으로 다른 크기를 넣을 수 있으나, 프로덕션 경로는 기본값만 씀. 실수로 작은 맵을 넣으면 스트리밍·인구 공식이 그대로 따라가 밀도만 비정상화된다.
- **메모리**: 1000²×3 바이트 ≈ 3 MB는 모바일에서도 수용 가능 수준으로 설계됨. 한 변을 수 km로 키우면 배열이 제곱으로 증가 — 현 구조의 상한에 가깝다.

## 6. 불확실 · 미확인

- **런타임 프로파일**: 실제 기기에서 1000×1000 생성 시간·메모리 피크는 이 세션에서 측정하지 않음(`[미측정]`). 코드 할당량은 ~3 MB로 추정.
- **maincloud 배포본**의 `WORLD_TILES`가 로컬 `spacetimedb`와 동일한지는 배포 산출물을 읽지 못해 미확인 — 소스 기준만 확인.
- **클라이언트 상주 몹 총수** exact 값은 시드·통행 가능 칸에 따라 달라 고정 상수가 아님. 대략 “청크당 수 기 × ~1000 청크” 수준만 확인.
- 사용자가 “1 km가 안 된다”고 **체감한 증상**(가장자리 텔레포트 실패, 맵이 작게 보임 등)이 있으면 크기 상수 문제가 아닐 가능성이 큼 — 증상 재현 정보가 없어 그 경로는 미추적.
- 타일을 1 m가 아닌 다른 실거리로 바꿀 기획 의는 코드·문서에 없음. 현재 SSOT는 타일=1 m.
