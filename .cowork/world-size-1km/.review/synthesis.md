## 1. 결론

**요구 규격 "가로 1 km × 세로 1 km" 는 충족돼 있다. 크기를 키울 필요는 없다.** `kMetersPerTile = 1.0`
이므로 타일 = 미터이고, `kWorldSizeMeters = 1000.0` 이 한 변 1000 m 를 정의한다. 프로덕션 경로
(`onLoad`·`restart`)는 `LevelMap.generate()` 를 인자 없이 부르므로 런타임에도 규격대로 생성되며,
설계 문서도 같은 값이다. **월드 크기 데이터 경로에는** 규격을 깎아먹는 지점이 없다 — 직접 열어 확인했다.

**따라서 이번 작업의 실체는 "키우기" 가 아니라 "고정·검증" 이다.** 지금 1 km 라는 사실을 지키는
**자동 회귀·SSOT 강제 장치가 없다**: 크기를 못 박는 테스트가 **없고**, 클라이언트와 서버가 1000 을
각자 손으로 적어 두고 주석("클라이언트 `kWorldTiles` 와 같아야 한다", `world.rs:47`)으로만 연결한다.
문서와 양쪽 리터럴 일치라는 **수동** 장치는 있으나 강제력이 없다 — 재검증 중 그 위험이 실제로 발현했다(§8).

여기에 1 km 규모라서 비로소 문제가 되는 결함이 하나 있다 — **웨이브 종료 판정이 웨이브 소속이 아닌
적까지 센다**(§5).

**"1 km 같지 않다" 는 체감의 원인은 크기가 아니라 뷰 스케일이다.** 줌은 화면 세로를 760 px 기준으로
잡고(`action_rpg_game.dart:226-229`, `zoom = screenSize.y / 760`, `0.55~1.6` 클램프), 레이더는 반경
70 m 만 보여 준다(`hud.dart:24`, `_radarRangeTiles = 70`). 한 화면에 들어오는 범위가 월드의 수십 분의
일이라 넓이가 체감되지 않는 것이며, **이를 이유로 크기 상수를 키우면 안 된다.**

## 3. 합의 — 검증 통과

- **월드는 통행 가능 1 km × 1 km 다.** 확인: `lib/game/iso.dart:21,28` — `kMetersPerTile = 1.0`,
  `kWorldSizeMeters = 1000.0`.
- **런타임도 규격대로다.** 확인: `lib/game/action_rpg_game.dart` 의 `onLoad`·`restart` 와 `test/` 4곳 —
  `LevelMap.generate()` 호출부가 **전부 인자 없음**(`level_map.dart:228-230` 기본값 `kWorldTiles`).
  더 작은 맵으로 도는 경로가 없다.
- **서버는 `WORLD_TILES = 1000.0` 이다.** 확인: `spacetimedb/src/world.rs:48`, 월드 중심
  `:344` `(WORLD_TILES/2, WORLD_TILES/2)`. **단, 재검증 시점 클라이언트 격자와 어긋났다(§8).**
- **크기 회귀 테스트가 없다.** 확인: `test/` 전역에 `kWorldTiles`·`widthInMeters`·`map.width ==` 검색
  결과 0건. `test/safe_zone_test.dart:58` 은 `expect(map.safeZone.center, map.worldCenter)` 처럼
  **파생끼리 비교**하므로 크기가 바뀌어도 통과한다 — 회귀를 잡지 못한다.
- **명세 상수의 지배력 문제(당시 진단, 두 상수는 성격이 다르다).**
  - `kWorldSizeMeters` — 종합 시점에 `iso.dart` 밖 참조처가 **0곳**이었다. 명세를 선언한 상수가
    실제 월드를 지배하지 않는 상태였다. → 재검증 시점에는 파생 사슬이 생겨 해소됐다(§8).
  - `kWorldChunks` — 리터럴이 아니라 `kWorldTiles` 에서 **유도된** 상수다(`iso.dart:50`).
    참조처가 없다는 것만 사실이며, "명세가 지배하지 않는다" 는 진단은 여기에 해당하지 않는다.
- **외곽 3칸은 통행 불가다.** 확인: `lib/game/level/level_map.dart:247` — 테두리 두께 3.
  이 테두리는 통행 가능 영역 **바깥에** 덧붙는 것으로 설계돼 있다(`iso.dart:33-38` 주석).

### 쟁점 1: 카메라가 월드 밖 허공을 비추는가

  마름모가 되지만, 여기서는 그 마름모를 감싸는 사각형으로 충분하다"* 라고 밝힌다. 외접 사각형과
  마름모의 차집합(네 모서리)에서는 데이터 공백이 화면에 들어온다. 다만 이어지는 주석 *"1 km 월드라

### 쟁점 2: 마지막 청크가 월드 밖까지 계산되는가

  결함은 없고 가장자리 청크에서 컬링이 약간 헐거워지는 정도다.

### 쟁점 3: 서버 `move_to` 클램프의 줄 번호

## 6. 반증 — 근거가 틀린 주장

- **claude(분석)**: 카메라 클램프가 "정확히 일치한다. 이상 없음" — ❌ `action_rpg_game.dart:433-448`
  은 마름모의 **외접 사각형**으로 clamp 한다(주석이 그렇게 밝힌다). 모서리에서는 허공이 노출된다.
  결론("크기 문제 아님")은 유지하되 "이상 없음" 이라는 판정은 채택하지 않는다.
- **kimi(분석)**: `_clampToWorld` 가 카메라를 월드 **마름모** 안에 가둔다 — ❌ claude 와 동일한 사실
  오류다. 근거는 위와 같다.
- **kimi(분석)**: 서버 클램프가 "월드 밖 좌표 서버 수용 불가" — ❌ `clamp(0.0, WORLD_TILES)` 는 상한
  **1000.0 을 포함**하고, 타일 인덱스 유효 상한은 `width - 1` 이다(`level_map.dart:126-129` `_index`).
  좌표 1000.0 은 어느 타일에도 대응하지 않으므로 "수용 불가" 가 아니라 "클라이언트에서 설 수 없는
  좌표를 서버가 받아들인다" 가 맞다.
- **kimi(리뷰 단계)**: `kWorldTiles = kWorldSizeMeters ~/ kMetersPerTile` 는 "`double ~/ double` 이
  `double` 을 반환하므로 타입 오류로 컴파일 불가" — ❌ Dart 의 `~/` 는 `num.operator ~/` 이고 반환
  타입은 `int` 다. 실제로 재검증 시점 코드가 `iso.dart:31` 에서 `const int kWorldPlayableTiles =
  kWorldSizeMeters ~/ kMetersPerTile;` 로 그대로 쓰고 있다. 남는 미확인 사항은 타입이 아니라
  **`double ~/ double` 이 const 문맥에서 평가되는지** 뿐이다(§8).
- **줄 번호 전반**: 네 AI 가 인용한 `world.rs` 클램프 줄 번호(489/498/505)가 모두 현재(536)와 다르다.
  내용은 사실이므로 반증이 아니라 **시점 차이**로 처리한다(§4 쟁점 3).

## 8. 미해결 · 사람 판단 필요

- **⚠ 재검증 중 작업공간이 실제로 변경됐다 — 클라·서버 월드 격자가 어긋났다.** 이 보고서 종합 이후
  다른 세션이 `iso.dart` 를 리팩터링해, 월드 상수가 `kWorldSizeMeters`(통행 1000 m) →
  `kWorldPlayableTiles`(1000) → `kWorldTiles = kWorldPlayableTiles + kWorldEdgeMarginTiles × 2`
  파생 사슬로 바뀌었다(`iso.dart:28,31,38,41`, `level_map.dart:247` 이 새 상수를 참조).
  - 좋은 점: 권고 6·7 의 취지가 구현됐고, 통행 가능 폭이 정확히 1000 m 가 되어 §8 의 "1 km 의 의미"
    분기가 **통행 기준으로 해소**됐다.
  - 문제: **격자 한 변이 1000 → 1006 으로 커졌는데 서버 `WORLD_TILES = 1000.0` 은 그대로다**
    (`world.rs:48`). 그 결과 월드 중심이 클라이언트 `Vector2(width/2, height/2)`
    (`level_map.dart:69`)와 서버 `world.rs:344` 사이에서 어긋난다. 기존 클라 테스트는 파생끼리
    비교하므로(`safe_zone_test.dart:58`) 이 어긋남을 잡지 못한다 — codex 가 지적한 "클라 전용
    테스트의 한계" 가 그대로 현실화됐다. → **권고 3·4 가 필요한 직접 근거다.**
  - 즉시 플레이 영향은 확인되지 않았다. 클라이언트가 아직 서버 월드를 읽지 않기 때문이다(아래 항목).
  - **이 변경이 컴파일·테스트를 통과하는지 확인하지 않았다**(읽기 전용 검증). `flutter analyze` ·
    `flutter test` 확인이 선행되어야 한다. 특히 `const int = double ~/ double` 의 const 평가 가능
    여부가 여기서 판가름 난다.
- **`.cowork/cowork-prompt.md` 의 전제가 현재 코드와 어긋난다.** 프롬프트는 "몬스터 레벨이라는 개념
  자체가 없다"(`:34,70`), "서버가 전투를 시뮬레이션하지 않는다"(`:84`), "실시간 멀티플레이 동기화는
  아직 없다"(`:22`)를 전제로 못 박는다. 그러나 `monster_codex.dart:283`(레벨 1~200 도감)·`:408`
  (`attackDamage = level.toDouble()`)이 이미 구현돼 있고, `world.rs` 에는 `enter_world`(`:461`)·
  `attack_monster`(`:646`)·`monster_tick`(`:724`)과 `public` 테이블(`:138,232`)이 실재한다.
  claude·codex·kimi 세 리뷰가 공통 지적했고 확인 결과 사실이다. 이 작업공간 규칙상 프롬프트가 최우선
  전제이므로 **프롬프트 갱신 여부가 사람 판단 사항**이며, 권고 9 는 그 정리 전에는 우선순위 근거가 없다.

  서버 월드 관련 수정(권고 3·8·9)의 효과를 클라이언트에서 확인할 수단이 지금은 없다.
  `dart run spacetimedb_sdk:generate` 재실행이 선행되어야 한다. 서버 몹 레벨·밀도와 클라이언트
  값의 차이도 이 때문에 **현행 플레이의 충돌이 아니라 향후 통합 리스크**다.
- **"1 km" 의 의미** — 논리 격자인지, 끝에서 끝까지 걸을 수 있는 거리인지. 위 변경으로 후자 쪽으로
  정리된 것으로 보이나 기획 확인이 필요하다. 엄밀히는 걷는 거리가 통행 폭보다 조금 더 짧다 —
  플레이어 몸 반경 0.28 타일(`player.dart:30`)만큼 첫 통행 칸 경계에 중심이 닿을 수 없고, 절차적
  데이터 공백(`level_map.dart:262`, `n < 0.30`)이 내부에도 뚫려 있기 때문이다.
- **클라이언트 vs 서버 몹 밀도** — 서버 240 마리(`world.rs:59`) vs 클라이언트 상주 개체군
  (`monster_population.dart`). 같은 1 km² 에 두 체계가 공존한다. 크기 문제가 아니라 권위 설계 결정이다.
- **maincloud 배포본이 로컬 `world.rs` 와 같은지 미확인** — 소스 기준으로만 판단했다.
- **줄 번호는 계속 밀린다** — 다른 세션이 같은 저장소를 동시에 편집하고 있음이 재검증에서 확인됐다

  번호도 시간이 지나면 어긋난다. 내용 기준으로 읽을 것.
- **웨이브 정체의 실제 빈도·지속 시간 미측정** — §5 의 구조적 결함은 확정이나, 체감 빈도는 실행
  검증이 필요하다. `flutter test` 만으로는 확인되지 않는다.
- **1000×1000 생성의 실기기 소요 시간·메모리 피크 미측정** — 배열 할당량은 코드 계산값이다.

  무관한 관측이라 결론에 반영하지 않는다.
